# SECURITY_POLICY.md — 개발 단계 보안 기본 정책

## 1. 범위 결정
변경된 진입점(웹 요청/이벤트/배치/파일/외부 메시지), 인증·권한, 데이터 흐름(외부→가공→DB/파일/HTML/외부), 보안 경계, 민감 정보와 실제 사용하는 기술을 확인한다. 적용 점검 항목을 선택하고 N/A·미실행 근거를 명시한다.

## 2. 공통 구현 원칙
- 신뢰할 수 없는 입력은 서버에서 형식·범위·크기·허용 값 검사. 블랙리스트/단순 치환만을 방어책으로 삼지 않는다.
- SQL/쉘/템플릿/LDAP/XML/HTML 등의 서로 다른 해석기에 데이터를 코드와 합치지 않는다. 바인딩·안전 API·컨텍스트별 이스케이프를 사용한다.
- 권한은 매 요청/객체에 적용. 사용자가 ID를 바꾸거나 역할/숨김 필드를 바꿔도 다른 사용자의 자원에 접근할 수 없어야 한다.
- 민감정보는 최소 수집/최소 응답/가명 데이터 시험. 키는 별도 관리. TLS·쿠키 속성·비밀번호 해시·로그 마스킹 검사.
- 파일·URL·XML·역직렬화·동적 코드·의존성·외부 연동은 보안 경계와 허용 목록을 검토한다.
- 보안 설정을 해제하거나 예외를 삼켜서 오류를 숨기지 않는다. 스캔 결과/취약점 조치를 실제 검증한다.

## 3. 검증 단계
1. 설계: 입력·권한·출력/데이터 흐름, 위협/통제 정의.
2. 구현: 관련 49개/웹 28개/OWASP 항목 확인 + 예외/실패 테스트.
3. PR: 자동 검사 결과와 리뷰 증빙 확인, JSP 오탐은 별도 검토.
4. 릴리스: 치명·높음 등급 해결/보완/위험 수용, 접근성 결과, 사용자 승인.

## 4. 결과 상태와 예외
- `PASS`: 실행 또는 충분히 검증된 근거가 있음.
- `FAIL`: 확인된 취약점/접근성 결함.
- `REVIEW`: 결과 해석/수동 검증/승인 대기.
- `NOT_RUN`: 도구/환경/권한 부재.
- `N/A`: 실제 공격 표면/기술 미사용으로 적용 불가. 정확한 범위와 검증 근거 필수.
- `FALSE_POSITIVE_APPROVED`: 탐지 결과가 진짜 위험이 아니라는 검증 후 담당자 승인. 항목 자체를 체크리스트에서 삭제하는 것이 아니라 결과에서 추적 가능하게 별도 표시.

## 5. 실행·자료 보호
외부 DAST/침투/부하 시도는 승인된 도메인·일정·시험 환경에서만 실시. 원본 소스/내부 URL/비밀번호/세션 쿠키/개인정보를 외부 웹검색·공개 SaaS·제3자 분석기로 전송하지 않는다. SAST/AI 분석 도구의 데이터 전송 정책을 확인한다. 테스트 증빙은 민감값 마스킹 후 저장한다.
