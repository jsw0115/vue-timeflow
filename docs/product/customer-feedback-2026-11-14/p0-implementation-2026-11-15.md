# CF-005·CF-007·CF-008 구현 및 검증 기록

2026-11-15. 요청된 최소 범위를 구현하고 로컬 검증을 수행했다. 담당은 Codex다. 현재 상태·공수·QC의 기준은 기존 Excel 관리대장이다. 아래 내용은 이번 구현의 증거이며 제품 출시 승인을 뜻하지 않는다.

## CF-005. 실제 기록 저장과 복구

- `ActualRecordingService`가 기존 `feature_record`의 `ACTUAL_SESSION`을 단일 원본으로 사용한다. 집중 세션이나 `planner_item`에 같은 기록을 다시 생성하지 않는다.
- 시작 시 활동명·시간대·요청 ID를 검증하고 서버 시각을 저장한다. 사용자 행 잠금으로 동시 시작을 직렬화한다. 같은 요청 ID의 재시도는 같은 세션을 반환하고, 변경된 내용이나 별도 진행 중 세션은 충돌로 처리한다.
- 종료는 버전·종료 시각·별도 요청 ID를 검사한다. 종료 시각은 시작 이후, 서버 현재 시각 + 5초 이내여야 한다. 같은 종료 명령은 같은 완료 결과를 반환한다. 중복 생성과 다른 계정 접근을 차단한다.
- 브라우저는 계정별 미확인 명령을 `localStorage`에 먼저 보관하고 서버 응답 후 제거한다. 화면을 나가면 표시용 타이머만 정리한다. 돌아오거나 새로고침하면 서버 세션을 조회하고, 응답이 유실된 종료 명령은 동일 시각·버전·ID로 재시도한다.
- 서버가 입력 오류·충돌로 명시적으로 거절한 명령은 대기 상태를 해제한다. 기존 진행 기록을 다시 조회한 뒤 종료할 수 있으며, 통신 유실은 같은 명령을 보존해 재시도한다.
- 경과 시간은 시각 차이로 계산한다. 저장 오류를 화면에 남기고 완료 후 상세 링크를 제공한다. 완료 목록은 야간 기록도 포함한다. 기존 타임바의 표시 구간은 08~23시다.
- `InsightService`가 완료 기록을 기록의 시간대 기준 날짜 경계로 나누어 실제 시간에 합산한다. 집중 시간에는 중복 합산하지 않는다. 통계는 기존 계약에 맞춰 분 단위이며 각 날짜 구간의 1분 미만은 버림 처리한다.

| API | 동작 |
| --- | --- |
| `GET /api/planner/recordings` | 계정의 실제 기록 목록 |
| `GET /api/planner/recordings/current` | 진행 중 세션과 서버 시각 |
| `GET /api/planner/recordings/{id}` | 소유권을 확인한 상세 |
| `POST /api/planner/recordings/start` | 멱등 시작 |
| `POST /api/planner/recordings/{id}/finish` | 버전 확인·멱등 종료 |

CF-006의 집중 타이머 영속화·자유 타이머 변경은 이 작업의 범위가 아니다. 브라우저 저장 공간을 사용할 수 없을 때는 복구 불가능한 명령을 전송하지 않고 오류를 표시한다. 다른 기기 간 오프라인 명령 조정은 추가 범위다.

## CF-007. 확인된 상태와 시연 표시

- 연동 설정과 동기화 화면이 공통 `IntegrationStatusPanel`에서 서버 capabilities와 sync/status를 읽는다.
- 두 응답 모두 기능 사용 가능을 확인해야 연결·동기화 기능을 표시한다. `available=false`이면 입력에 성공 값이 섞여 있어도 연결됨·성공 시각·시연 이력을 표시하지 않는다.
- 조회 중·미지원/미연결·조회 실패를 텍스트로 구분한다. 실패하면 이전 상태를 지우며, 계정 전환이나 화면 종료 후 늦게 온 응답을 적용하지 않는다.
- 동기화 버튼은 서버가 확인한 사용 가능·연결 상태에서만 동작한다. 로컬 카운터나 가짜 충돌 해결로 성공을 만들지 않는다.
- 집중 화면의 고정 시연 완료 기록을 제거하고, 현재 집중 목록이 임시 시연이며 서버 저장되지 않는다는 점을 표시한다. OS 방해 금지 제어는 미지원으로 명시한다. 실제 OS 권한 요청 자체를 하지 않는다.
- 백업 화면의 고정 성공 시각을 제거하고 서버가 확인한 파일 생성·복원 완료 이력을 사용한다. 서버 파일 생성 시각과 사용자 기기의 파일 저장 여부를 구분한다.

실제 외부 캘린더 제공자 인증·연결·OS 제어 기능을 새로 구현한 것은 아니다.

## CF-008. 수동 백업과 병합 복원

### 포함 범위와 형식

일기·메모·디데이·가계부·회고·완료한 집중 세션·완료한 실제 기록을 포함한다. 현재 계정 소유의 개인 첨부 중 만료되지 않은 파일을 바이너리 내용과 함께 포함한다. 기존 `/api/user/data/export` 계약은 유지하고 별도 백업 API를 사용한다.

브라우저 로컬/시연 자료, 진행 중 기록, 일정·할 일·루틴·기존 플래너 항목·업무·경력·소셜·채팅, 프로필·설정·토큰·비밀키·공유 권한, 공유 그룹/만료 첨부는 제외한다. 화면과 파일에 범위를 명시한다. 자동 백업은 제공하지 않는다.

- 형식 버전은 `schemaVersion=1`이다. 백업 ID·내보내기 시각·시간대·포함/제외 목록·기록·첨부·전체 체크섬을 갖는다.
- 기록 최대 500개, 첨부 최대 50개, 첨부 바이너리 합계 5 MiB, 업로드 JSON 최대 8 MiB다. 한도를 넘으면 일부만 담은 백업을 만들지 않고 거절한다.
- 전체 체크섬은 checksum 필드를 제외한 재귀 키 정렬 JSON의 SHA-256이다. 첨부도 바이너리 SHA-256과 크기를 확인한다. 이는 손상 검사이며 전자서명·신뢰된 발급자 인증이 아니다.
- 백업 파일에는 내용이 평문으로 포함되므로 화면에서 안전한 보관을 안내한다. 공유 권한과 인증 정보는 복원하지 않는다.

### 복원 순서와 충돌 처리

1. JSON 구문·형식 버전·허용 필드·시간·크기·전체/첨부 해시·중복 ID·중복 회고 날짜·본문 첨부 참조를 서버에서 검증한다.
2. 미리보기에서 각 항목을 CREATE 또는 SKIP으로 구분한다. 현재 계정에 같은 원본 ID나 회고 날짜가 있으면 기존 자료를 보존한다.
3. 미리보기 작업은 계정과 파일 체크섬에 묶인다. 같은 파일의 재시도는 같은 작업을 재사용한다.
4. 사용자가 확인한 파일을 다시 보내면 새 기록/첨부 ID와 현재 계정 소유권을 적용한다. 본문의 첨부 다운로드 링크도 새 ID로 치환한다.
5. 파일·기록·작업 완료를 한 트랜잭션으로 저장한다. 미리보기 이후 충돌이 생기면 전체 롤백한다. 응답 유실 뒤 같은 작업을 요청하면 완료 결과만 반환한다.

| API | 동작 |
| --- | --- |
| `GET /api/user/data/backup` | 명시 범위의 JSON 생성. 클라이언트가 다운로드 파일을 만든다. |
| `GET /api/user/data/backup/status` | 서버 파일 생성·복원 완료 이력 |
| `POST /api/user/data/backup/preview` | multipart 파일 검증 및 병합 미리보기 |
| `POST /api/user/data/backup/{jobId}/restore` | 같은 파일·작업으로 원자적 병합 복원 |

`BACKUP_JOB`과 `ACTUAL_SESSION`은 기존 저장 구조를 사용한다. DB 마이그레이션과 신규 패키지 의존성은 추가하지 않았다. JSON에는 저장된 본문을 그대로 포함하며 화면 출력은 Vue 텍스트 바인딩을 사용한다. 파일명은 저장 경로로 사용하지 않는다.

## 관리대장과 인수인계

- 같은 Excel 파일에 이력과 실제 구현 설명을 누적하며 관리 버전을 1.0에서 1.1로 갱신한다. 제품 목표 버전 1.0과 배포 버전은 별개다.
- 세 항목은 채택·검증 중으로 관리한다. 최소 범위 구현과 로컬 QC는 통과했으나 실제 환경 종단 검증·최종 인수 완료를 임의로 확정하지 않는다.
- 공동 착수 관측은 2026-11-15 12:18:51 KST다. 세션 중단·재개가 있었고 항목별 시간을 계측하지 않았으므로 실제 시작·공수·최종 완료 시각은 빈칸으로 남긴다. 17:36 KST는 코드·로컬 회귀 검증 후 관리대장에 개발 종료를 기록한 관측 시각이다. 이후 문서·관리대장 검증·커밋 작업은 포함하지 않는다.
- 미측정 작업 로그를 추가할 때 공수가 0으로 집계되는 것을 방지하도록 실제 시간 합산 조건에 유효한 시작·종료 시각을 추가한다. 빈 시간과 휴게 30분을 뺀 2시간 집계를 각각 검증한다.
- 다음 단계는 실제 MySQL 테스트 환경에서 별도 계정 두 개로 기록 복구와 첨부 포함 병합 복원을 재확인하는 것이다. 운영 자료를 시험 데이터로 사용하지 않는다.

관리대장을 가져와 수정한 후 33개 다른 요구사항과 원문·초기 상세요건이 보존되는지 대조했다. 11개 시트·36개 의견·6개 PASS/66개 NOT_RUN·표 9개·입력 선택지 6개·수식 453개를 OOXML 읽기 전용 검사로 확인했다. 미측정 공수는 빈칸이며 수식 오류 캐시는 없다. LibreOffice 독립 프로필로 재열기·재계산한 임시 결과도 같은 검사를 통과했다. 최종 파일은 Artifact Tool 출력 원본이다. 생성기 프로세스가 마지막 저장·검사 출력을 마친 뒤 종료 코드 1을 반환한 점은 명령 성공으로 표현하지 않고, 별도 검증기의 종료 코드 0과 재계산 결과로 파일을 확인했다.

롤백 시 배포된 코드만 이전 버전으로 되돌리면 된다. 이번 작업은 스키마를 바꾸지 않았다. 새 종류의 저장 행을 삭제하지 않으며, 구버전은 해당 기록을 화면에서 보여주지 못할 수 있다. 데이터 롤백은 별도 보존·검증 절차가 필요하다.
