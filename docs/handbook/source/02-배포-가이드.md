# Timebar Diary 배포 가이드

화면만 게시하려면 GitLab Pages를 사용하고, 로그인과 채팅을 포함한 서버를 운영하려면 Linux 컨테이너 배포를 준비합니다. 기본 파이프라인은 Pages를 게시합니다. 컨테이너 이미지는 별도 옵션을 켜야 생성되며 서버 배포는 수동 명령으로 진행합니다.

## 배포 경로 선택

| 항목 | GitLab Pages | Linux 컨테이너 |
| --- | --- | --- |
| 배포 대상 | Vue 정적 파일 | Vue, Spring Boot, MySQL, Redis |
| 기본 동작 | 기본 브랜치에서 Pages 게시 | ENABLE_CONTAINER_BUILD=true 필요 |
| API 연결 | 외부 HTTPS API를 따로 준비 | Nginx가 같은 출처의 /api로 전달 |
| 라우터 | hash 모드 | history 모드와 SPA fallback |
| 서버 적용 | GitLab Pages 작업 | release.sh 수동 실행 |
| 모바일 설치 파일 | 생성하지 않음 | 생성하지 않음 |

Pages 자체는 Java API나 MySQL을 실행하지 않습니다. 서버가 없는 상태에서는 로컬 시연 화면을 확인하는 범위이며 인증과 실제 채팅은 동작하지 않습니다. API를 추가해도 로컬 저장 화면이 자동으로 서버 저장으로 바뀌지는 않습니다.

## GitLab Pages 게시

GitLab 프로젝트의 기본 브랜치와 Runner 설정을 확인합니다. 로컬 브랜치 이름을 기준으로 추정하지 말고 CI_DEFAULT_BRANCH가 가리키는 실제 기본 브랜치에 병합하세요. 원격 저장소와 변경 파일은 git remote -v, git status --short로 먼저 확인합니다.

로컬에서 frontend 기준으로 빌드를 확인합니다.

```powershell
npm ci
npm run build:pages
npm run preview
```

preview 주소는 명령 출력에서 확인합니다. 화면과 직접 URL 진입을 점검하세요. Pages 빌드는 hash 모드를 강제하고 기본 자산 경로는 ./입니다. /project/ 같은 경로를 쓴다면 PAGES_BASE_PATH는 앞뒤 슬래시를 포함해야 합니다.

| 빌드 변수 | 설정 의미 |
| --- | --- |
| VITE_API_BASE_URL | 외부 HTTPS API 주소. 비워 두면 서버 연결 없는 게시입니다. |
| PAGES_REQUIRE_API | true이면 API 주소가 없을 때 빌드가 실패합니다. |
| PAGES_BASE_PATH | 기본 ./이며 필요한 경우 /프로젝트명/ 형식을 사용합니다. |

로컬 빌드는 frontend/.env.pages.example을 참고하여 .env.production.local을 작성합니다. GitLab 빌드는 Settings의 CI/CD 변수에 같은 공개 빌드 값을 등록합니다. 예를 들어 https://api.example.com을 지정하면 코드가 /api를 붙여 정규화합니다. 이미 /api로 끝나는 주소도 처리합니다. API 주소를 바꾼 뒤에는 다시 빌드하고 게시해야 합니다.

API 서버의 APP_CORS_ALLOWED_ORIGINS에는 실제 Pages 출처를 등록합니다. 출처는 https://호스트 형식이며 /프로젝트명 같은 경로를 포함하지 않습니다. 브라우저에서 공개되는 VITE_ 변수에는 비밀키를 넣지 않습니다.

현재 .gitlab-ci.yml의 build_pages는 npm ci, Pages 빌드, Node 테스트와 API 문서 대조를 수행합니다. pages 작업은 기본 브랜치에서 산출물을 public으로 복사해 게시합니다. 파이프라인 성공 후 GitLab의 Pages 화면에서 실제 게시 URL을 확인하고 접속하세요.

## Linux 이미지와 서버 준비

GitLab CI/CD 변수 ENABLE_CONTAINER_BUILD=true를 설정합니다. .gitlab/ci/linux.yml은 build_linux_web, verify_api, package_images를 활성화합니다. 이미지 게시 작업은 기본 브랜치에서만 수행하며 web과 api 이미지에 같은 전체 커밋 SHA를 붙입니다.

Registry에서 web:<40자리 SHA>와 api:<같은 SHA>가 모두 생성됐는지 확인합니다. latest나 7자리 축약 SHA를 release.sh에 전달하지 않습니다. 이 파이프라인에는 SSH 자동 배포 작업이 없습니다.

Linux 서버에는 Git, Docker Engine, Compose plugin, curl과 OpenSSL이 필요합니다. 기존 배포 안내는 up --wait를 지원하는 Compose 2.20 이상을 전제로 합니다. 저장소를 /opt/timeflow에 체크아웃하고 배포 계정으로 docker ps와 docker compose version을 확인하세요.

Registry에는 read_registry 권한의 Deploy Token으로 로그인합니다. 토큰을 URL이나 저장소 파일에 넣지 않습니다. 서버에서 다음과 같이 .env를 준비하되 이미 파일이 있다면 덮어쓰지 않습니다.

```bash
cd /opt/timeflow
umask 077
test -f infra/deploy/.env || cp infra/deploy/.env.example infra/deploy/.env
chmod 600 infra/deploy/.env
```

| 서버 변수 | 입력할 값 |
| --- | --- |
| REGISTRY_IMAGE | 실제 프로젝트 Registry 경로 |
| IMAGE_TAG | 두 이미지가 생성된 전체 40자리 커밋 SHA |
| MYSQL_PASSWORD | API용 DB 계정 비밀번호 |
| MYSQL_ROOT_PASSWORD | 별도의 DB 관리자 비밀번호 |
| REDIS_PASSWORD | 별도의 Redis 비밀번호 |
| JWT_SECRET | UTF-8 32바이트 이상의 무작위 키 |
| WEB_PORT | 루프백 점검 포트. 기본 8088 |
| APP_DOMAIN 및 APP_ORIGIN | 실제 도메인과 https://도메인 출처 |

비밀값마다 별도로 openssl rand -hex 32를 실행하는 방법을 사용할 수 있습니다. JWT 키를 릴리스마다 바꾸면 기존 토큰이 무효화됩니다. 초기화한 MySQL의 비밀번호는 .env만 바꾼다고 회전되지 않으므로 계정 변경 절차를 별도로 수행해야 합니다.

## 배포와 HTTPS 확인

이미지 생성이 성공한 SHA를 사용합니다. 아래 SHA 자리표시는 실제 값으로 바꾼 뒤 실행하세요.

```bash
cd /opt/timeflow
sh scripts/deploy/release.sh '<성공한 전체 40자리 SHA>'
docker compose --env-file infra/deploy/.env -f infra/deploy/compose.yml ps
curl --fail http://127.0.0.1:8088/healthz
```

release.sh는 Compose 설정 검사, 이미지 pull, 기존 DB 컨테이너가 있을 때 백업, up --wait 순서로 진행합니다. healthy 확인이 끝나야 IMAGE_TAG와 .release-state를 갱신합니다. 실패했다고 전체 작업이 자동으로 이전 상태로 복원되는 것은 아닙니다. 컨테이너 상태와 로그를 확인하세요.

도메인 DNS가 서버를 가리키도록 설정하고 TCP 80과 443을 사용할 수 있게 합니다. DB 3306, Redis 6379, API 8080은 외부 공개하지 않습니다. HTTPS overlay는 Caddy를 추가합니다.

```bash
sh scripts/deploy/release.sh '<성공한 전체 40자리 SHA>' --https
curl --fail https://<실제-도메인>/healthz
docker compose --env-file infra/deploy/.env -f infra/deploy/compose.yml exec -T api \
  wget -q -O - http://127.0.0.1:8080/actuator/health
```

/healthz는 Nginx 웹 상태이고 API와 DB의 정상 동작을 보장하지 않습니다. 내부 actuator 상태, 실제 계정 로그인, 채팅 메시지와 새로고침을 함께 확인합니다. 다른 프록시를 쓴다면 SSE 버퍼링을 끄고 긴 읽기 timeout과 X-Forwarded-Proto 전달을 맞추세요.

현재 Nginx 설정은 /api/admin, Swagger와 actuator의 외부 접근을 차단합니다. 최신 서버에는 ADMIN 권한 검사도 있지만 프록시의 차단은 유지되어 있습니다. 관리자 화면을 게시했다고 관리자 API가 외부에서 열린 것으로 판단하지 마세요.

## 데이터 보존과 롤백

서버가 이미 사용 중이라면 배포 전 DB 백업과 복구 가능성을 확인합니다. 수동 백업 명령은 다음과 같습니다.

```bash
sh scripts/deploy/backup.sh
```

백업은 infra/deploy/backups에 저장됩니다. 같은 서버의 파일만으로 장애 복구가 보장되지 않으므로 별도 보관 위치와 복구 검증을 운영 절차에 포함하세요. 백업 실패 시 배포를 계속하지 않습니다.

새 서버로 기존 데이터를 옮길 때는 API 최초 실행 전에 빈 대상 DB로 덤프를 가져와 스키마와 Flyway 이력을 확인합니다. 기존 DB에 덤프를 덮어쓰지 않습니다. 서로 다른 MySQL 버전 간 덤프 호환성은 검증 DB에서 먼저 확인하세요.

코드 롤백은 현재 스키마와 호환되는 이전 성공 SHA로 release.sh를 실행합니다. DB 마이그레이션은 되돌리지 않으므로 스키마 호환성을 먼저 판단합니다. 데이터 복구는 별도의 백업 복원 절차입니다. 업데이트와 롤백에 docker compose down -v를 사용하면 볼륨이 삭제되므로 사용하지 않습니다.

Flyway clean, 이력 삭제, 적용된 migration 수정으로 오류를 피하지 마세요. 과거 V1에는 교체성 SQL이 있어 수동 재실행하면 데이터가 손실될 수 있습니다.

## 다른 배포 형태와 배포 기록

직접 JAR로 운영할 경우 backend에서 ./gradlew check bootJar를 실행하고 실행용 timeflow-api-0.1.0.jar를 서비스 관리자로 실행합니다. frontend에서는 npm ci와 npm run build:web을 실행해 dist를 정적 서버에 올립니다. DB_URL, DB_USERNAME, DB_PASSWORD, JWT_SECRET와 정확한 CORS 출처를 주입하고 /api 프록시와 history fallback을 구성해야 합니다.

Android와 iOS는 npm run mobile:sync 후 각 IDE에서 서명하여 배포합니다. Electron은 npm run desktop:build를 사용하며 산출물은 frontend/release에 생성하도록 설정되어 있습니다. 현재 패키지의 기본 history 라우터는 Electron file URL의 직접 진입을 별도로 검증해야 합니다. 설치형 클라이언트의 API 주소와 서명은 Pages 및 Linux CI 범위에 포함되지 않습니다.

릴리스 기록에는 커밋 SHA, 이미지 태그, 배포 시각, 환경, 백업 위치, 마이그레이션, 확인 결과와 롤백 후보를 남깁니다. 빌드 성공과 실제 운영 배포 성공을 구분하세요.
