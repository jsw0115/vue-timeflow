# Timebar Diary 프로젝트 구조

이 저장소에는 Vue 웹, Spring Boot API, 모바일 및 데스크톱 포장 프로젝트, 배포 구성과 설계 문서가 함께 있습니다. 화면 변경은 frontend, 서버 처리 변경은 backend, 운영 구성 변경은 infra와 scripts/deploy에서 시작합니다.

## 저장소 전체 구성

```text
vue-timeflow-proj/
  frontend/       웹과 모바일 및 데스크톱 클라이언트
  backend/        Java API와 마이그레이션
  infra/chat/     격리된 로컬 MySQL과 Redis
  infra/deploy/   Linux 이미지와 프록시 및 Compose
  scripts/        기동과 배포 및 검증 도구
  docs/           개발과 제품 및 API 문서
  .gitlab/ci/     선택적인 컨테이너 CI
  .gitlab-ci.yml  기본 Pages CI
  DESIGN.md       제품 디자인 계약
  AGENTS.md       저장소 작업 지침
```

node_modules, frontend/dist, frontend/release, backend/build와 .gradle은 의존성 또는 생성물입니다. 소스 수정 위치로 사용하지 않습니다. .env와 DB 덤프는 개발자별 비밀 설정 또는 데이터이며 저장소에 올리지 않습니다.

## 프런트엔드에서 화면 찾기

frontend/src/main.js가 앱을 시작하고 router/index.js가 경로와 화면을 연결합니다. App.vue와 주변 셸 컴포넌트가 사용자 화면 구성을 담당합니다. 라우터의 navGroups와 adminGroups를 보면 메뉴의 그룹과 실제 경로를 함께 확인할 수 있습니다.

| 경로 | 역할과 읽는 시점 |
| --- | --- |
| src/views/ | 홈, 플래너, 기록, 업무, 공유, 커뮤니티와 설정 화면 |
| src/components/ | 통합 작성 폼, 모달, 입력 필드 등 재사용 UI |
| src/features/auth/ | 가입, 로그인, sessionStorage 세션, 인증 요청 |
| src/features/chat/ | 채팅 화면, API, 상태, SSE 처리와 시연 API |
| src/features/inbox/ | 멘션과 태그를 모으는 통합 보관함 |
| src/store/ | 브라우저 상태와 기능별 로컬 컬렉션 |
| src/utils/ | 날짜, 반복, 작성 검증, 검색 색인과 편집 상태 |
| src/workers/ | 브라우저 검색 워커 |
| src/data/ | 화면 목록과 목업 데이터 |
| tests/ | Node 내장 테스트 러너용 .test.mjs |
| scripts/ | API 문서 생성과 대조, Pages 빌드 |

일정을 고칠 때는 먼저 router/index.js에서 /events와 해당 View를 찾고, View가 import하는 store와 컴포넌트를 읽습니다. 통합 작성은 components/PostComposer.vue와 store/postComposer.js가 중심입니다. 파일명만 보고 API 저장이라고 가정하지 말고 실제 호출을 따라가세요.

localCollection.js는 timeflow.demo.v1. 접두사로 localStorage에 배열을 저장합니다. appState.js의 일정, 할 일, 루틴과 writing.js 등의 데이터는 이 경로를 사용합니다. 별도 브라우저나 기기와의 동기화, 서버 권한, 계정별 저장 격리를 보장하는 저장소가 아닙니다.

features/auth/session.js는 sessionStorage에서 토큰을 복원하고 authorizedFetch로 Bearer 인증을 붙입니다. 401 응답에서 refresh를 시도하고 요청을 재실행합니다. features/chat/api/chatApi.js는 accessToken이 있으면 서버 API를, 없으면 시연 API를 선택합니다.

## 백엔드에서 처리 찾기

기본 Java 패키지는 kr.timebar.diary입니다. HTTP 요청은 Controller에서 받고 서비스가 검증과 권한 확인을 수행한 뒤 JPA 또는 JDBC로 MySQL에 저장합니다. 모든 기능이 같은 영속성 구현을 사용하는 것은 아닙니다.

| Java 패키지 | 책임 |
| --- | --- |
| auth, security | 사용자 인증, JWT, 현재 사용자, ADMIN 접근 제어 |
| planner, event, task, routine | 기존 도메인 API와 JPA, 체크리스트와 플래너 기본 보기 |
| records, feature | 새 개인 기록, 반복 일정, 통계, 첨부와 공통 저장 규칙 |
| work | 업무 기록, WBS, 위키, 경력과 포트폴리오 |
| social | 친구, 공유 그룹, 커뮤니티, 챌린지와 신고 |
| operations | 설정, 운영자 기능과 계정 운영 처리 |
| contract | 기능별 HTTP 계약을 노출하는 컨트롤러 |
| integration | 외부 제공자 미연결 상태와 실행 경계 |
| chat | 채팅 API, 도메인, MySQL 영속성, Redis 이벤트 |
| config, common | DB 검사, Querydsl, 설정, 응답과 공통 오류 |

contract라는 이름의 패키지에도 실제 서비스와 연결된 컨트롤러가 있습니다. 이름만으로 stub이라고 판단하지 않습니다. 최신 처리 흐름은 docs/api/frontend-backend-2026-10-10/catalog.md에서 경로를 찾은 뒤 실제 Controller와 Service로 확인하세요.

backend/src/test/java에는 인증, 플래너, 체크리스트, 개인 기록, 소셜과 운영 기능 등의 테스트가 있습니다. 일부는 H2 또는 mock 저장소를 사용하므로 테스트 통과와 운영 MySQL 검증의 범위를 구분합니다.

## 요청과 데이터 흐름

개발 환경의 인증 요청은 다음 순서로 처리됩니다.

```text
브라우저 화면
  -> features/auth/session.js
  -> /api/auth/login
  -> Vite 프록시
  -> Spring Security와 AuthController
  -> AuthService와 MySQL
  -> 토큰 응답과 sessionStorage 저장
```

일정 작성의 현재 브라우저 흐름은 다릅니다.

```text
PostComposer.vue
  -> postComposer.js 검증과 저장
  -> appState.js의 events
  -> localCollection.js
  -> localStorage
```

서버의 /api/schedules가 구현되어 있어도 위 흐름에서 요청하지 않으면 DB에 기록되지 않습니다. 서버 연동을 추가할 때는 로컬 저장을 API 호출로 연결하고 로딩, 오류, 권한과 충돌 처리를 함께 구현해야 합니다.

서버 채팅의 장기 데이터는 MySQL에 저장하며 Redis는 이벤트 전파, 입력 중 상태와 활성 상태에 사용합니다. 클라이언트는 REST와 SSE로 상태를 맞춥니다. 과거 문서나 커밋 제목의 MongoDB 표기와 현재 구현을 혼동하지 마세요.

## 설정과 DB 마이그레이션

| 경로 | 역할 |
| --- | --- |
| backend/src/main/resources/application.yml | 기본 DB, JWT, Redis, CORS와 업로드 설정 |
| application-chat-local.yml | 격리 개발 DB와 Redis 및 개발 키 |
| db/migration/V1__initial_schema.sql | 체크섬이 보존된 과거 스키마 |
| db/core/ | 안전한 core 추가 마이그레이션 |
| db/workspace/ | 체크리스트와 신규 기능 저장 구조 |
| db/chat/ | 채팅 전용 마이그레이션 |
| db/chat-local-core/ | 격리 개발용 core 초기 구조 |
| backend/src/main/java/db/core/ | Java 기반 계정 ID 폭 마이그레이션 |

기본 설정의 Flyway 경로는 migration, core, workspace이며 채팅은 별도 설정과 이력을 사용합니다. CoreSchemaInspector가 기존 스키마를 확인하고 안전한 초기화 경로를 결정합니다. 경로만 보고 SQL 파일을 직접 순서대로 실행하지 마세요.

현재 기본 JPA 설정은 ddl-auto=validate입니다. 엔티티 수정만으로 운영 테이블이 자동 갱신되지 않으며 필요한 migration과 호환성을 함께 검토해야 합니다. 알려지지 않은 스키마를 감지하면 오류를 먼저 해결하고 clean이나 history 삭제로 우회하지 않습니다.

## 플랫폼과 배포 소스

frontend/android와 frontend/ios는 Capacitor 네이티브 프로젝트입니다. capacitor.config.ts는 dist를 webDir로 사용합니다. 웹 수정 후 mobile:sync로 산출물을 반영합니다. frontend/electron의 main.cjs는 개발 시 Vite 주소, 패키지에서는 dist/index.html을 엽니다. electron-builder.yml은 NSIS, DMG, AppImage 대상을 정의합니다.

infra/deploy의 Dockerfile.api는 빌드된 JAR를, Dockerfile.web은 dist를 이미지에 복사합니다. compose.yml은 DB, Redis, API와 웹을 연결하고 compose.https.yml은 Caddy를 추가합니다. nginx.conf의 history fallback과 SSE 설정은 웹 라우팅 및 실시간 채팅에 영향을 줍니다.

## 작업 종류별 시작점과 근거

| 하려는 작업 | 먼저 읽을 파일 |
| --- | --- |
| 화면이나 메뉴 추가 | frontend/src/router/index.js와 대응 View |
| 작성 종류나 입력 검증 변경 | store/postComposer.js, utils/postValidation.mjs |
| 서버 API 추가 | 대응 Controller와 Service, 최신 API 계약 문서 |
| 채팅 오류 조사 | features/chat/와 backend chat/ |
| 데이터베이스 변경 | 현재 엔티티 및 SQL, config/CoreSchemaInspector.java |
| Pages 배포 변경 | .gitlab-ci.yml과 scripts/build-pages.mjs |
| Linux 배포 변경 | infra/deploy/와 scripts/deploy/ |

구조 확인의 근거는 실제 폴더, 위 표의 소스, backend/build.gradle과 frontend/package.json입니다. 디자인이나 문구를 고치기 전에는 루트 DESIGN.md와 .omd/preferences.md도 읽으세요.
