# Timebar Diary 기능 명세서

Timebar Diary는 오늘의 일정, 할 일과 루틴을 관리하고 계획과 실제 기록을 비교하는 서비스입니다. 이 문서는 신규 개발자가 기능별 화면, 입력 규칙, 대응 API와 저장 범위를 확인하도록 작성했습니다. API 전체 필드 계약은 최신 OpenAPI와 상세 명세를 함께 읽으세요.

## 구현 상태와 공통 규칙

아래의 로컬 화면은 브라우저 상태와 시연 데이터가 중심인 기능, 서버 API는 처리 코드가 있는 기능, 제공자 미연결은 외부 서비스를 아직 호출하지 않는 기능을 뜻합니다. 서버 API가 구현되어도 해당 화면과의 연동은 별도 확인 대상입니다.

| 영역 | 현재 클라이언트 동작 | 서버 범위 |
| --- | --- | --- |
| 인증 | 로그인과 가입에서 서버 요청 | JWT와 계정 API |
| 채팅 | 로그인 시 서버, 비로그인 시 시연 | MySQL, Redis, REST와 SSE |
| 일정과 개인 기록 | 다수 store가 브라우저 로컬 저장 | 별도 CRUD와 통계 API 구현 |
| 업무와 소셜 및 설정 | 로컬 store 및 시연 UI 포함 | 사용자별 저장과 권한 API 구현 |
| 외부 연동 | 설정 또는 미연결 화면 | 상태 조회, 실행 요청 503 경계 |

현재 서버에는 HTTP 매핑 277개가 선언되어 있습니다. 전체 화면의 서버 연결이나 모든 API의 운영 검증이 끝났다는 뜻은 아닙니다. 기존 /events와 신규 /schedules, 기존 /routines와 신규 /routine-records는 저장 모델이 달라 자동 동기화하지 않습니다.

서버의 일반 응답은 success, data, message 필드로 구성됩니다. 인증은 Bearer accessToken을 사용합니다. 개인 데이터의 사용자는 JWT에서 정하며 타인의 owner를 본문으로 지정할 수 없습니다. 일반 생성은 201, 조회와 수정은 200, 삭제는 본문 없는 204이지만 세부 경로별 계약을 우선합니다.

신규 기록의 PUT은 필수 필드와 현재 version을 전달하는 본문 교체 방식입니다. DELETE에도 현재 version이 필요하며 오래된 버전은 409입니다. 기존 /planner/items는 마지막 쓰기가 우선하는 방식이므로 이 규칙을 모든 API에 일괄 적용하지 마세요. 신규 목록은 page가 0부터 시작하지만 기존 배열과 채팅의 커서 응답도 유지됩니다.

## 인증과 계정

화면은 /auth/signup, /auth/login, /settings/profile과 /settings/security입니다. 실제 연결은 features/auth/session.js가 담당하며 토큰은 sessionStorage에 저장합니다. authorizedFetch는 accessToken을 붙이고 401일 때 refresh를 시도합니다.

| 동작 | 대응 API 또는 규칙 |
| --- | --- |
| 가입과 로그인 | POST /api/auth/signup, /api/auth/login |
| 토큰 갱신과 로그아웃 | POST /api/auth/refresh, /api/auth/logout |
| 내 계정 조회 | GET /api/auth/me |
| 프로필과 비밀번호 변경 | /api/user/profile, /api/user/password |
| 로그인 세션과 내보내기 | /api/user/sessions, /api/user/data/export |

계정 정지, 전체 로그아웃과 토큰 폐기를 서버에서 검사합니다. 관리자 API는 현재 계정의 ACTIVE 및 ADMIN 권한을 확인합니다. 비밀번호 분실 화면은 실제 메일 재설정 완료 기능으로 간주하면 안 됩니다. reset token 발급과 메일 제공자 연결은 별도 범위입니다.

가입 및 로그인 후 /api/auth/me의 계정과 토큰을 확인하는 것이 기본 검수입니다. 로그아웃 후 새 요청이 거부되는지, 다른 사용자의 기록을 조회할 수 없는지도 확인하세요.

## 홈과 플래너 및 집중

홈 /, 캘린더 /calendar, 플래너 /planner에서 하루의 계획과 실제 기록을 확인합니다. 플래너는 일간, 주간, 월간과 연간 보기를 제공하며 /planner는 현재 기본 보기로 이동합니다. 기본 보기의 프런트엔드 설정은 localStorage를 사용하며 서버의 /api/planner/preferences와는 별도 저장입니다.

| 기능 | 입력과 동작 | 대응 API |
| --- | --- | --- |
| 플래너 항목 | 날짜, 유형, 시간과 상태로 조회 및 편집 | /api/planner/items |
| 기본 보기 | 일간, 주간, 월간과 연간 선택 | /api/planner/preferences |
| 회고 | 날짜와 본문 저장 | /api/planner/reviews/{date} |
| 템플릿 | 저장한 틀을 실제 항목으로 적용 | /api/planner/templates |
| 프로젝트 캔버스 | 컬럼과 카드, 체크리스트 관리 | /api/planner/canvas |
| 집중 기록 | 모드와 시작 및 종료 시각 저장 | /api/focus/sessions |

서버 캔버스는 개인 singleton이며 중복 카드 ID와 없는 컬럼 참조 등을 거부합니다. 카드의 담당자와 플래너 블록은 참조 메타데이터이며 다른 사용자의 기록을 바꾸는 권한이 아닙니다. 집중 모드는 pomodoro, stopwatch, free이며 duration은 1~1440분입니다. endedAt이 있으면 startedAt 이후여야 합니다.

홈과 통계의 계획 시간은 일정 회차와 ACTUAL이 아닌 플래너 항목, 실제 시간은 ACTUAL 플래너 항목을 기준으로 계산합니다. 같은 시간을 일정과 플래너에 중복 입력하면 자동으로 합치지 않습니다. 루틴 예정 시간과 휴가 시간도 자동 가산하지 않습니다.

## 통합 작성과 일정 및 할 일

통합 작성 창의 종류는 일정, 할 일, 루틴, 다이어리, 메모, D-Day, 머니로그, 회고, 커뮤니티 글, 업무 기록과 업무 위키입니다. postComposer.js가 입력 검증과 저장 대상을 결정합니다. 현재 저장 함수는 각 로컬 store를 갱신합니다.

일정 화면은 /events입니다. 제목, 시작일, 종료일과 시작 및 종료 시간이 필요하며 종료는 시작보다 늦어야 합니다. 서버 신규 일정은 /api/schedules에 저장하고 /api/schedules/occurrences에서 조회 구간에 겹치는 회차를 반환합니다. 최대 일정 기간은 366일입니다.

반복 규칙은 frequency, interval, weekdays, endMode, until, count로 구성합니다. frequency는 none, daily, weekly, monthly, yearly입니다. interval은 1~99, weekly 요일은 일요일 0부터 토요일 6, count는 1~999입니다. endMode는 never, until 또는 count입니다. 존재하지 않는 월말과 윤년 날짜는 다음 유효 회차로 건너뜁니다. 서버 회차 조회 구간은 양 끝 포함 최대 367일입니다.

회차의 sourceId는 원본 ID이며 occurrenceKey는 원본 ID와 회차 시작일로 구분합니다. 현재 서버에는 특정 회차만 바꾸는 예외 API가 없으므로 원본을 수정하면 시리즈 기준이 바뀝니다. 참가자 ID를 넣어도 공유 권한이 생기지는 않습니다.

할 일은 /tasks와 /tasks/:id에서 제목, 마감일, 우선순위, 완료와 체크리스트를 관리합니다. 체크리스트 제목은 비어 있을 수 없으며 항목별 담당자를 지정할 수 있습니다. 서버 /api/tasks와 하위 checklist-items 및 assignees 경로가 대응합니다. 담당자 후보와 변경 권한, 버전 충돌은 서버 계약을 따라야 합니다.

기본 검수는 다일 일정의 캘린더 표시, 월말 반복, 종료 시각 역전 거부, 체크리스트의 빈 제목 거부와 완료 변경입니다. 서버 저장을 구현할 때는 다른 계정의 기록 접근과 오래된 버전의 409도 확인하세요.

## 루틴과 개인 기록

루틴은 /routines와 /routines/history에서 관리합니다. 제목, 반복 요일, 시간, 진행 시간과 목표 수량 및 단위를 입력합니다. 진행 시간은 1~1440분, 목표 수량은 1~9999입니다. 일시 중지한 루틴은 예정 회차에서 제외합니다.

신규 서버 모델은 /api/routine-records이며 날짜별 /history/{date}에서 완료를 저장합니다. 동일한 완료 상태를 반복 요청해도 결과가 중복되지 않습니다. 미래나 예정되지 않은 날짜는 거부합니다. 서버의 rate, streak와 best는 요청 구간의 예정 회차를 기준으로 계산하므로 로컬 시연의 누적 수치와 동일하다고 가정하지 마세요.

| 기능과 화면 | 핵심 입력 및 동작 | 대응 서버 경로 |
| --- | --- | --- |
| 다이어리 /diary | 제목, 날짜, 기분과 본문. 같은 날짜에 여러 건 가능 | /api/diaries, /api/diary/calendar |
| 메모 /memos | 제목과 본문, 할 일 전환 | /api/memos |
| D-Day /dday | 제목, 기준일과 카테고리 | /api/ddays |
| 머니로그 /money | 날짜, 수입 또는 지출, 금액 | /api/money/entries, /api/money/summary |
| 내 글 /my-posts | 종류별 개인 글 모아보기 | 원본 기능과 개인 검색을 참조 |

메모의 서버 할 일 전환은 현재 메모 버전을 확인하고 Task 생성과 메모 삭제를 한 트랜잭션으로 처리합니다. 신규 일기는 날짜마다 여러 건을 허용하며 기존 날짜 키 기반 저장 API는 별도 호환 경로입니다.

머니로그 서버 금액은 KRW 정수이며 수입은 양수, 지출은 음수, 0은 거부합니다. 통합 작성 UI는 양수 금액을 받아 지출 저장 시 음수로 바꿉니다. 서버 요약의 expense는 양수로 반환하고 balance는 income에서 expense를 뺀 값입니다.

## 통계와 검색 및 보관함

/stats와 하위 화면은 일간, 카테고리, 계획과 실제 비교 등으로 기록을 검토합니다. /api/home/summary, /api/stat/dashboard, /api/stat/category, /api/stat/plan-actual와 /api/stat/focus가 대응합니다. 브라우저 통계 화면의 로컬 계산과 서버 집계는 연결 상태에 따라 값이 다를 수 있습니다.

개인 검색 서버는 /api/search와 /api/search/tags를 사용합니다. 브라우저에는 검색 색인과 워커가 있습니다. 채팅 검색은 별도 /api/chat/search이며 사용자가 참여한 방의 접근 범위를 따릅니다. /mentions와 /tags의 통합 보관함은 개인 글과 채팅의 출처를 구분해 다룹니다.

/insight의 AI 보고서 화면과 /api/insight/generate는 제공자 미연결 범위입니다. /api/reports/draft가 만드는 업무 초안은 시간 블록을 조합하는 규칙 기반 결과이며 AI 호출 결과가 아닙니다.

## 업무와 경력 관리

| 화면 | 역할 | 대응 서버 경로 |
| --- | --- | --- |
| /work와 /work/history | 업무 보고와 업무 기록 | /api/reports, /api/work/records |
| /work/labor | 인원과 기간 및 투입률을 이용한 공수 확인 | 보고서 및 업무 데이터 참조 |
| /work/wbs | 계층형 작업과 가중 진행률 | /api/work/wbs |
| /work/wiki | 문서와 이전 버전 관리 | /api/work/wiki |
| /work/career | 경력, 이력서와 포트폴리오 | /api/work/career/projects, /api/work/resume, /api/work/portfolio |

업무 기록의 종류는 연차, 반차, 외근, 출장과 이직입니다. 공통으로 제목, 담당자와 시간 범위를 확인합니다. 반차는 같은 날이어야 하며 연차는 0.5일 단위, 외근과 출장은 장소, 이직은 대상 회사와 직무가 필요합니다. 프런트엔드 검증과 서버의 세부 필드 규칙을 함께 확인하세요.

WBS 부모는 같은 사용자 소유여야 하며 순환과 100단계 초과 계층은 거부합니다. leaf의 md와 progress로 가중 진행률을 계산합니다. 노드 삭제는 하위 노드도 삭제합니다. 위키 수정은 이전 내용을 이력으로 저장하며 부모 문서 삭제 시 자식 문서를 상위로 올립니다.

업무와 경력은 사용자 개인 범위입니다. 공개 포트폴리오는 /api/work/portfolio-links에서 본인 소유 itemIds를 명시해 발급합니다. 원본 토큰은 한 번 반환하고 서버에는 해시를 저장하며 링크는 7일 후 만료합니다. 공개 조회는 /api/public/portfolios/{token}이며 선택한 포트폴리오만 반환합니다. 링크 설정값을 바꾸는 것만으로 실제 링크가 발급되지는 않습니다.

## 공유와 커뮤니티 및 채팅

친구와 공유 그룹은 /share 및 하위 화면에서 관리합니다. 서버는 /api/share/friends, /api/share/blocks와 /api/share/groups를 사용합니다. 친구 요청은 수신자만 수락하거나 거절할 수 있으며 같은 쌍의 중복 초대는 409입니다. 공유 그룹은 초대를 수락한 ACTIVE 회원에게 조회 권한을 부여합니다.

커뮤니티는 /community의 게시판, 회원, 가입 승인, 랭킹과 챌린지 화면을 제공합니다. /api/communities 및 하위 경로가 대응합니다. 공개 메타데이터 조회와 회원 전용 글 작성 권한은 다르며 private 커뮤니티는 허용되지 않은 사용자에게 정보를 숨깁니다. owner가 초대, 승인과 관리를 수행하며 정원은 owner를 포함해 2~500명입니다.

| 채팅 기능 | 동작과 검수 기준 |
| --- | --- |
| 방과 메시지 | 로그인 계정으로 방을 조회하고 메시지를 보내며 이전 기록을 불러옵니다. |
| 읽음과 미읽음 | 읽음 위치를 저장하고 방의 미읽음 수를 갱신합니다. |
| 실시간 상태 | SSE 이벤트, 재연결과 REST 재조회를 사용합니다. |
| 멘션과 태그 | @ 자동완성, 멘션 읽음과 태그 메시지를 확인합니다. |
| 검색과 활성 상태 | 방 권한 안에서 검색하고 Redis 기반 입력 중 및 활성 상태를 표시합니다. |
| 시연과 서버 구분 | 토큰이 없으면 demoChatApi이며 실제 계정 간 통신 검증이 아닙니다. |

서버 채팅은 CHAT_ENABLED=true에서 등록되고 MySQL과 Redis가 필요합니다. 플로팅 버튼은 메신저 진입과 위치 조정을 제공합니다. 같은 브라우저의 여러 탭에서 편집 중 상태가 보이는 기능과 여러 사용자 간 서버 협업 저장을 동일하게 해석하지 마세요.

## 첨부와 설정 및 운영

첨부 서버 /api/attachments는 파일 바이트와 권한 및 보관 기간을 처리합니다. 기본 Spring 파일 한도는 10MB, 요청 한도는 11MB이며 Nginx 요청 본문 한도는 10m입니다. multipart 부가 크기 때문에 프록시 제한이 먼저 걸릴 수 있습니다. 실제 파일 업로드를 배포 경로에서 검수하세요.

환경설정은 /settings/:section?에서 프로필, 모드, 외형, 카테고리와 연동 등을 다룹니다. /api/settings/{section}은 허용된 섹션의 JSON을 저장하지만 저장만으로 예약 자동화, 알림 발송이나 외부 동기화를 실행하지 않습니다.

관리자 화면은 /admin과 하위 경로이며 사용자, 콘텐츠, 공지, 문의와 신고 등을 다룹니다. 서버 ADMIN 권한 검사가 있으며 현재 Linux Nginx는 /api/admin 외부 요청을 차단합니다. /api/support/tickets, /api/notices, /api/content는 사용자 지원과 공개 범위의 콘텐츠를 담당합니다.

## 외부 연동의 제공자 미연결 범위

| 기능 | 현재 서버 상태 |
| --- | --- |
| AI 분석과 음성 인식 | 실제 생성 및 변환 실행은 503 |
| 외부 캘린더 동기화 | 미연결 상태, 실행은 503 |
| 결제와 환불 | 승인과 환불 제공자 호출 없음, 실행은 503 |
| 소셜 로그인과 알림톡 | OAuth 교환과 실제 발송 없음 |
| 공동 집중 영상 | 실제 영상 방 제공자 연결 없음 |
| 2단계 인증 | capabilities는 false이며 활성화 요청은 503 |

/api/integrations/capabilities는 기능별 available=false와 PROVIDER_REQUIRED 상태를 반환합니다. 인증, 권한 또는 입력 검증에 먼저 실패하면 400, 401 또는 403 등으로 응답할 수 있습니다. 유효한 실행 요청이 제공자 경계에 도달했을 때의 상태가 503입니다.

일반 오류는 400 입력 오류, 401 인증 실패, 403 권한 부족, 404 없음 또는 숨겨진 타인 데이터, 409 충돌로 처리합니다. 서버 연결을 구현할 때 이 상태를 사용자에게 구분해서 보여주고 로컬 시연 성공으로 대체하지 마세요.
