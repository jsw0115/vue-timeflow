## 프로젝트와 문제 정의

Timebar Diary는 계획과 실제 기록을 같은 시간축에서 비교하고, 일정·할 일·루틴·개인 기록·업무 경험을 연결하는 시간관리 서비스입니다. 저장소 이름은 vue-timeflow이며 서버 애플리케이션 이름은 timeflow-api입니다. 제품명과 코드 식별자를 임의로 일괄 변경하지 않습니다.

사용자가 해결하려는 문제는 흩어진 계획과 기록, 실제 작업 결과를 다시 문서와 다음 행동으로 연결하기 어려운 상황입니다. 현재 화면·API를 기반으로 데이터의 계정별 영속화를 완성한 다음, 관심 직무·연구 변화와 개인 근거를 연결하는 AI 성장 지원을 단계적으로 검증합니다.

주요 이용자는 개인 일정 사용자, 취업·직무 전환 준비자, 재직자, 연구자와 독립 프로젝트 수행자입니다. 기관·코치 이용은 개인의 명시적 공유를 전제로 한 후속 범위입니다. 구체적 시장 근거와 가설은 [시장·사용자 분석](../product/ai-growth-2026-10-31/01-시장과-사용자.md)에 단일 관리합니다.

## 개발 범위

| 구분 | 범위 | 현재 상태와 완료 기준 |
| --- | --- | --- |
| 계정 | 가입·로그인·갱신·세션·권한 | 서버 구현. 실제 화면 연동과 계정 무효화 테스트 유지 |
| 계획·기록 | 일정·할 일·루틴·메모·다이어리·통계 | 화면과 서버 구현이 함께 있으나 다수 화면은 로컬 저장. API 연결·충돌·오류 복구 필요 |
| 업무·경력 | WBS·위키·경력·이력서·포트폴리오 | 서버 저장·권한 계약 구현, 화면별 연동 완성 필요 |
| 협업 | 친구·그룹·커뮤니티·첨부 | 서버 권한·보관 계약 구현, 화면 연결 상태 개별 확인 |
| 채팅 | REST·SSE·읽음·검색·멘션·활성 상태 | MySQL·Redis 연동 구현, 재연결·권한·재전송 검증 유지 |
| 운영 | 관리·문의·공지·감사·배포 | 내부 API와 운영 구성 존재. 실제 운영 배포·복구 검수는 별도 |
| AI 성장 | 출처 기반 분석·작성 제안·승인한 실행 | 제안 단계. 동의·영속 작업·근거 검증·원가 선행 |
| 유료화 | 이용권·사용량 원장·결제·해지 | 제공자 미연결. 결제 sandbox·대사·정책 검증 후 출시 |

현재 기능의 상세 동작은 [기능 명세서](../handbook/source/05-기능-명세서.md), 앞으로 검수할 약속은 [요구사항 명세](requirements.md)를 기준으로 합니다. 화면이 있다는 이유로 서버 연결이나 외부 제공자 실행을 완료로 표시하지 않습니다.

### 제외 범위

초기 운영에서 자동 입사지원·논문 제출, 채용 후보자 자동 평가, 진료 판단, 개인 전체 기록의 기관 공개, 자체 대형 모델 학습, 무제한 데이터 수집을 제공하지 않습니다. iOS·Android·Electron의 서명된 설치 파일과 스토어 결제는 플랫폼별 후속 검수 대상입니다.

실서비스 도메인·운영 계정·예산·SLA·결제 제공자는 확정되지 않았습니다. 예시값을 승인된 운영 구성으로 취급하지 않습니다.

## RFP 정의와 제안 요청

RFP는 Request for Proposal, 즉 제안요청서입니다. 아래는 내부 개발·협력사 협의에 사용할 요청 기준이며 실제 발주 공고·계약·예산 확정 문서가 아닙니다.

| 요청 영역 | 제안자가 설명할 내용 | 평가할 증거 |
| --- | --- | --- |
| 현재 구조 이해 | Vue·Spring·MySQL·Redis와 로컬 저장의 차이 | 실제 소스·API·마이그레이션 대조표 |
| 개발 제안 | 우선 분야, 범위, 선행 과제와 제외 범위 | 요구사항 ID별 구현·검수 계획 |
| 데이터·AI | 공급자 이용권, 출처, 동의, 작업 복구, 품질 | 계약 확인·평가 세트·실측 비용·실패 사례 |
| 보안·개인정보 | 소유권, 비밀값, 파일·공유·삭제, 운영 접근 | 계정 간 접근 실패·삭제 전파 테스트 |
| 운영·배포 | 환경 분리, migration, 백업·롤백·관찰 | 격리 설치·복원 연습·배포 체크리스트 |
| 일정·비용 | 역할·투입량·의존성·가정·유지보수 범위 | WBS와 명시적 산정 근거 |
| 인수인계 | 코드·명세·테스트·운영·라이선스 | 재현 가능한 저장소와 문서 검증 |

제안 비교에서는 필수 요구 충족과 재현 가능한 증거를 먼저 확인합니다. 점수 가중치·예산·납기는 발주 시 확정하며 현재 문서에 임의로 계약 조건을 만들지 않습니다. 외부 모델·데이터·결제 비용과 개발 인건비는 분리해 제시하도록 요청합니다.

## 역할과 변경 관리

기획 담당은 요구·우선순위·인수 기준, 개발 담당은 소스·DB/API·테스트, 검수 담당은 재현·결과·잔여 위험, 운영 담당은 배포·백업·장애 대응을 맡습니다. 이는 역할 정의이며 실제 담당자 이름이나 인력 확보를 뜻하지 않습니다. 개인 프로젝트라면 한 사람이 역할을 겸할 수 있지만 검수 항목을 생략하지 않습니다.

추가·수정 요청은 [날짜별 작업 원장](../releases/backlog.md)에 먼저 등록합니다. 요구사항 ID·영향·목표 버전·검수 기준을 정한 다음 WBS와 설계를 갱신합니다. 완료된 코드, 검증된 동작, 실제 배포의 세 날짜를 구분해 기록합니다.
