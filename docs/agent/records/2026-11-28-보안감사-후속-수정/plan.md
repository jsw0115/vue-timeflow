# 작업 계획

- 요청: quick 보안 감사(저장소 밖 run-2 산출물)에서 나온 확인 필요(needs_validation) 5건을 1번부터 차례로 고친다. 사용자 결정이 필요한 항목은 먼저 묻는다.
- 현재 확인한 사실:
  1. `AuthService.refresh`는 저장된 refresh 토큰을 읽고 확인한 뒤 따로 폐기했다. 동시에 들어온 두 갱신이 모두 통과할 수 있었고, refresh 토큰에 계정 버전(`av`)이 없어 비밀번호 변경·강제 로그아웃 전 토큰을 거르지 못했다.
  2. 사용자 창이 `window.open`으로 연 관리자 창은 sessionStorage 사본을 가진다. 사용자 창에서 로그아웃해도 관리자 창의 세션과 그 창이 갱신한 refresh 토큰이 남았다.
  3. `POST /api/public/portfolios/{token}/unlock`은 잠금 없이 실패 횟수를 읽고 버전 조건부로 썼다. 동시에 보낸 추측은 409로 빠져 세지지 않아 10회 잠금을 넘을 수 있었다.
  4. `PUT /api/user/password`의 현재 비밀번호 확인에는 시도 제한이 없었다.
  5. 채팅(`ChatService`)은 소셜 차단 목록을 확인하지 않았다.
- 사용자 결정(2026-11-28):
  - 1번: `av`가 없는 옛 refresh 토큰은 거부한다(한 번 다시 로그인).
  - 4번: 로그인과 따로 5회 실패 시 15분 잠금. 잠금은 비밀번호 변경만 막고 로그인은 막지 않는다.
  - 5번: 채팅에도 차단을 적용한다. 찾기는 404, 새 개인·그룹 대화는 거절, 기존 개인 대화의 새 메시지는 거절, 기존 그룹방은 그대로 둔다.
  - 검증: 이 PC에서 관련 테스트를 실행한다. 커밋·푸시는 하지 않는다.
- 범위/제외: 위 5건만 고친다. 기존 사용자 변경(`backend/src/main/resources/application.yml`, `frontend/src/features/career/careerGoal.mjs`, `skills-lock.json`, `docs/agent/records/2026-11-20-Career-OS-개편-적용/`)은 건드리지 않는다. 스키마 변경 없음.
- 성공 기준: 각 건마다 원래 문제를 재현하는 테스트가 수정 후 통과한다. 3번은 수정을 빼면 실패하는지도 확인한다. 기존 관련 테스트도 통과한다.
- 보안 관련 ID/검증: 인증·세션 관리(토큰 재사용·세션 고정), 무차별 대입 제한, 경쟁 조건(TOCTOU), 접근 제어(차단 정책)에 해당한다. `security/SECURITY_POLICY.md`의 공식 ID 매핑은 하지 않았다(REVIEW).
- 접근성 대상/검증: 화면 구조·문구 변경 없음. 관리자 창 자동 닫기만 추가했다. N/A.
- 사용자 요청으로 이미 허용된 작업과 추가 확인이 필요한 작업: 로컬 수정과 테스트 실행은 허용됨. 커밋·푸시·배포는 요청하지 않았다.
