- 1단계 결정: IM-09 설계대로 타이머는 실제 기록 API(`ACTUAL_SESSION`)를 쓴다. FOCUS(`/api/focus/sessions`)는 시작·종료 시각을 화면이 보내 UF-121("서버 시작·종료 시각으로 계산")을 지킬 수 없다.
- 일시정지 저장 방식: 기록 안 `pauses: [{from, to}]`. 일시정지마다 기록을 나누면 통계는 저절로 맞지만, 포모도로 하나가 여러 기록이 되어 챌린지 최소 분에 못 미치고 "13분 기록 하나"(UT-212)와 맞지 않는다.
- 시각: 일시정지·재개는 서버 `Instant.now()`. 종료는 기존처럼 화면이 보낸 시각(현재+5초 이내)을 쓰고, 마지막 일시정지·재개보다 이르면 400이다. 카운트다운 목표 도달 뒤 늦게 종료하는 경우는 화면이 목표 도달 시각을 보내야 한다(2단계).
- 취소: UF-122는 "0초에 취소하면 기록을 만들지 않는다"만 적었다. 실제 기록에 삭제 API가 없어 0초만 허용하면 3초 뒤 잘못 누른 타이머를 지울 수 없다. 끝내기 전이면 언제든 취소(기록·원본 연결 삭제)할 수 있게 했다. 끝낸 기록은 409.
- 모드 없는 기록: 플래너의 "실제 기록" 버튼은 모드를 보내지 않는다. 기존 기록과 같게 모드·목표를 저장하지 않는다(스톱워치로 바꿔 넣지 않음).
- 한 곳 계산: `RecordingTime.seconds(row, from, to)`를 통계(날짜별), 챌린지(시간대), 백업(경과 시간 검사), 종료(`elapsedSeconds`)가 같이 쓴다. 일시정지가 없으면 예전 계산(`Duration.toMinutes`)과 같은 값이다.
- 백업: 복원은 새 ID로 만든다(기존 규칙). 내보내기는 `finishKey`·원본 연결을 빼고 모드·목표·일시정지는 남긴다. 그래서 복원한 타이머 기록은 챌린지 근거가 될 수 없다(기존 규칙과 같음).
- 통계 "집중" 수치: 지금 FOCUS 기록만 센다. 타이머 기록은 "실제 기록"으로 센다(기존 테스트 `midnightActualsAreCountedOnceWithoutAddingFocusMinutes`가 중복을 막는다). 2단계 전에 사용자에게 집중 수치 기준을 물어야 한다.
- 이 PC는 Node 20.18이다(PR-06 대기). `python -I`로 표준 입력 스크립트를 넘겨도 bash heredoc에서는 한글이 깨지지 않았다. 파일 편집 스크립트는 scratchpad에 두었다.

- 화면: 로그아웃 상태 집중 화면은 로그인 안내다. 예전 시연 타이머는 저장하지 않았고, 저장 안 되는 타이머를 남기면 서버 저장으로 오해할 수 있다(CLAUDE.md 1절). 화면 공유·녹화 부분은 손대지 않았다.
- 화면: 포모도로는 기존과 같은 25분 고정. 카운트다운만 분을 입력한다(1~1,440). 취소는 확인 창(`window.confirm`, 챌린지 화면과 같은 방식) 뒤에 한다.
- 목표 도달: 화면이 `targetEndAt`(시작 + 목표 + 닫힌 일시정지)을 종료 시각으로 보낸다. 같은 기록에 한 번만 자동으로 시도하고, 실패하면 오류 문구와 "끝내고 저장" 버튼으로 다시 할 수 있다.
- 결함 1(브라우저 점검): 서버 `Instant.now()`가 나노초(이 PC는 100ns 단위)까지 저장해, 밀리초 정밀도인 화면이 계산한 목표 도달 시각이 서버 기준 59.9995초가 되어 59초로 저장됐다. 같은 이유로 일시정지 직후 끝내면 종료 시각이 일시정지 시각보다 조금 이르다고 400이 될 수 있었다. 서버가 찍는 시각(시작·일시정지·재개)을 밀리초로 잘랐다(`stamp()`). 예전 기록의 나노초 시각은 그대로다.
- 결함 2(브라우저 점검): 일시정지 응답 뒤 시계를 마지막 1초 틱 시각으로 다시 계산해, 그 시각이 서버 일시정지 시각보다 이르면 1초 늦게 보였다가 올랐다. 일시정지 중에는 서버 일시정지 시각까지만 센다(`recordingSeconds`).
