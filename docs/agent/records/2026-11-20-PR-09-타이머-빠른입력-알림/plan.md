# 작업 계획

- 요청: 2026-11-20 "다음 단계 업무를 처리해 주세요." PR-10은 6단계까지 마쳤고(결정 대기 Q-21·Q-22만 남음), 01 처리 순서의 다음 PR-13은 서버 접근 정보(Q-16) 대기라, 바로 진행할 수 있는 PR-09를 시작했다. 1단계를 마치고 테스트를 통과하면 변경 파일 요약과 함께 다음 단계 진행 여부를 묻는다.
- 기준 기획: 09 8절(UF-120~UF-127, UT-210~UT-224), 06 IM-09, 08 UF-23(UT-48·UT-49).
- 현재 확인한 사실(2026-11-20 소스 대조)
  - 집중 화면(`FocusView.vue`)은 저장하지 않는 시연 타이머다. 포모도로 25분·자유 타이머 50분이 고정이고, 끝내면 목표 시간 전체를 세션으로 남긴다.
  - 실제 기록 API(`/api/planner/recordings`, `ActualRecordingService`)는 서버 시각으로 시작하고 멱등 종료·복구를 한다. 모드·목표 시간·일시정지·취소가 없다.
  - 집중 기록 API(`/api/focus/sessions`, FOCUS)는 시작·종료 시각을 클라이언트가 보내고, 스톱워치에도 `duration`(1~1,440분)을 필수로 받는다. 화면에서 부르는 곳이 없다.
  - 실제 기록 시간을 쓰는 곳은 통계(`InsightService.actualBlocks`), 챌린지 인증 근거(`ChallengeService.evidence`), 백업 내보내기·복원(`BackupService`), 플래너 화면(`recordingSeconds`)이다.
  - 빠른 입력 규칙 해석기와 알림 바로 처리 API는 없다(3·4단계에서 다시 대조).
- 단계
  1. 타이머 서버: 실제 기록에 모드(pomodoro·countdown·stopwatch)·목표 시간(1~1,440분)·서버 시각 일시정지/재개·취소. 통계·챌린지·백업이 일시정지 시간을 뺀다. API 계약. UT-210·UT-211·UT-212·UT-214·UT-215(서비스·HTTP).
  2. 타이머 화면: 집중 화면 세 모드를 서버에 연결, 새로고침 복구, 목표 도달 시 목표 시각으로 종료. UT-213(브라우저).
  3. 빠른 입력: 규칙 기반 해석기(날짜·시간·제목, 모호하면 후보), 미리보기 칩, 종류 바꾸기. UT-216~UT-220.
  4. 알림 바로 처리: 할 일 완료·10분 뒤, 만료·이미 완료 확인, 기기 간 처리 상태 갱신. UT-221~UT-224.
- 1단계 범위/제외: 서버·API 계약·문서만. 화면은 2단계. FOCUS API의 스톱워치 duration 필수 규칙과 통계 "집중" 수치의 기준(FOCUS만 셀지, 타이머 기록도 셀지)은 2단계에서 화면과 함께 정한다.
- 성공 기준(1단계): 새 테스트가 수정 전 실패하고 수정 후 통과, 백엔드 전체 테스트 PASS, API 계약 검사 PASS, 기존 실제 기록·통계·챌린지·백업 테스트 PASS.
- 보안: 일시정지·재개·취소는 본인 기록만(소유자 조건 조회, 다른 계정은 404), version으로 경쟁 요청을 막는다. 일시정지 시각은 서버가 찍어 화면이 시간을 지어낼 수 없다. 일시정지 목록 길이를 묶어 저장 크기를 제한한다. 입력 키 허용 목록 유지(ownerId 주입 400).
- 접근성: 1단계는 화면 변경 없음(N/A). 2단계부터 KWCAG 확인.
- 허용 범위: 구현·테스트·문서·의미 단위 커밋. 푸시·배포·운영 DB 변경은 이번 요청에 없어 하지 않는다.
