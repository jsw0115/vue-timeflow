# 결정·근거·인수인계 메모

- 현재 확인된 구현/설정(2026-11-19)
  - 09 3절의 "이미 된 것: version"은 할 일에 맞지 않았다. `/api/tasks`(`TaskEntity`)는 행 잠금(`findOwnedForUpdate`)만 하고 마지막 저장이 덮어썼다. `feature_record` 기록과 체크리스트 항목에는 version이 있다.
  - 기록 API 공통 규칙은 `PUT` 본문 version, `DELETE ?version=`. 프런트 `apiRequest`는 204를 실패로 던졌다(체크리스트·`feature_record` 삭제가 204).
  - 할 일 로컬 목록은 8개 화면이 읽고 5곳이 쓴다. 체크리스트 담당자는 서버 계정만 받는다(로컬 주소록 시연 연락처는 계정이 아님). 2단계에서 다룬다.
- 선택한 대안/이유
  - 단계 나누기: UF-81의 연결 순서를 따르되 공통 기반(어댑터·계정 경계·서버 version)을 1단계로 먼저 뒀다. 할 일 화면 연결(2단계)이 version 없는 API 위에 올라가면 UF-84를 만족할 수 없고, 사용자가 단계마다 확인하기를 요청했다.
  - 할 일 version: PR-01 플래너와 같은 방식이다(Flyway V8 `NOT NULL DEFAULT 0`, 공개 버전 = 저장 + 1, 수정은 본문·상태 변경과 삭제는 쿼리, 누락·1 미만 400, 불일치 409). 새 규칙을 만들지 않고 기존 선례를 따랐다. 기존 행 잠금은 그대로 두어 체크리스트 변경과의 직렬화도 유지된다.
  - 저장 전 엔티티의 version은 null로 둔다(ID를 생성자에서 정하므로 Spring Data가 null version으로 새 엔티티를 판단). `getPublicVersion`은 null을 0으로 본다(단위 테스트의 저장 전 엔티티 대응).
  - 같은 내용의 수정은 JPA가 쓰지 않아 버전이 오르지 않는다. 플래너와 같은 동작이며 API 안내에 적었다.
  - 어댑터(`recordClient.mjs`)는 요청 함수를 주입받는 팩토리로 했다(`recordingClient.mjs`·`backupClient.mjs` 컨벤션). 오류를 `conflict`·`invalid`·`notFound`·`network`·`server`로 나누고, 409면 최신 값을 다시 조회해 `error.latest`에 담는다(UF-84 비교 화면용). 자동으로 덮어쓰지 않는다.
  - 계정별 목록(`useRecordCollection.mjs`)은 `useCapabilityStatus.mjs`처럼 세대 번호로 계정 전환을 감지한다. 요청 중 계정이 바뀌면 결과를 버리고 `stale` 오류를 던진다(UT-127). 충돌이면 목록 항목을 최신 서버 값으로 바꾸고, 404면 목록에서 뺀 뒤 오류를 그대로 알린다(화면이 "다른 곳에서 삭제됨"을 말할 수 있게).
  - `apiRequest`의 204를 성공(null)으로 바꿨다. 공용 모듈이지만 204를 실패로 기대하는 호출부가 없고, 어댑터 삭제(UF-80)에 필요하다.
  - `TaskRequest` 레코드 구성요소 안에 주석을 넣었다가 계약 생성기(`design-docs/current.mjs`)가 쉼표로 구성요소를 나눠 파싱에 실패했다. 기존 레코드처럼 주석을 빼고, 규칙은 `TaskService.requireVersion` 주석과 API 안내에 적었다.

## 2단계(할 일 화면 연결, 2026-11-19)

- 사용자 요청: "2단계 진행해줘. 마지막 단계까지." 단계마다 사용자 확인을 받던 방식을 바꿔 7단계까지 이어서 진행한다. 단계마다 검증하고 커밋한다.
- 선택한 대안/이유
  - 읽는 화면 8곳을 바꾸지 않으려고 `appState.tasks`를 같은 이름의 쓰기 가능한 computed로 바꿨다. 읽기는 로그인이면 서버 목록, 로그아웃이면 로컬 목록이다. 통째로 바꾸기(set)는 로컬에만 쓴다(기존 테스트·로컬 정리 코드 호환).
  - 공통 모듈(`syncedCollection.mjs`)은 4~7단계가 그대로 쓴다. 로그아웃 저장은 지금 동작과 같고(맨 앞에 넣고 숫자 ID), 로그인 저장은 서버 성공 응답 뒤에만 목록에 들어간다.
  - 상세는 편집을 시작한 할 일(base)의 version으로 저장한다. 목록을 다시 불러와 version이 올라가도 그 version을 쓰면 다른 곳의 변경을 모르고 덮어쓴다. 완료 토글도 같은 version으로 보내고, 내 변경이면 기준 version을 따라 올린다.
  - 완료 체크는 `@click.prevent`로 브라우저가 체크 표시를 되돌리게 하고, 서버 성공 뒤 값이 바뀔 때만 체크된다(UF-82). 실패하면 notice로 알리고 던지지 않는다. 토글 충돌은 비교 화면 없이 최신 상태로 바꾸고 다시 누르게 한다(내용 편집이 아니라서).
  - 체크리스트는 서버 할 일 목록 응답에 없어 할 일별로 불러 둔다(목록은 미리보기할 할 일만, 상세는 열 때). 저장은 바뀐 항목만 보내고(추가→이름·담당자→완료→삭제), 중간 실패 시 성공한 결과를 기준(baseline)으로 삼아 다시 시도하면 남은 것만 보낸다. 새 항목은 서버 ID로 바꿔 다시 만들지 않는다. 서버에 일괄 저장 API를 만드는 안은 기획에 없는 API 변경이라 택하지 않았다.
  - 체크리스트 항목은 단건 조회 API가 없어 충돌이면 목록 전체를 다시 불러 비교 화면에 쓴다.
  - 작성 창에서 할 일은 만들었지만 체크리스트가 실패하면 창을 닫지 않고 진행 상태를 들고 있다가, 다시 저장할 때 할 일을 다시 만들지 않는다. 문구는 "할 일은 저장했지만 체크리스트 일부를 저장하지 못했어요."로 무엇이 저장됐는지 먼저 알린다.
  - `savePostDraft`를 async로 바꿨다. 4~6단계에서 대부분 종류가 서버 저장이 되므로 지금 바꾸는 편이 낫다. `writing-flows.test.mjs`에 `await`를 붙였다.
  - 400 오류 응답에 필드 정보가 없어(`ApiResponse`는 success·data·message), 화면이 서버 메시지 낱말(제목·마감)로 입력란을 고른다. 못 고르면 저장 상태 줄에 메시지를 보인다. 오류 응답 형식을 바꾸는 것은 모든 API 계약 변경이라 택하지 않았다.
  - 비교 화면의 두 버튼은 모두 button-secondary다. 상세에 이미 주 액션(저장하기)이 있고, 덮어쓰기를 더 눈에 띄게 하지 않으려는 것이다. 바뀐 값은 굵기로만 구분했다(포인트 컬러를 더 쓰지 않음).
  - 로딩 문구는 빈 상태가 아니라서 `empty-state`가 아니라 `input-field-help`로 둔다(빈 상태 문구 검사 규칙).
  - 메모에서 옮기기는 메모가 6단계까지 로컬이라 서버의 `convert-to-task`를 쓸 수 없다. 고른 문장마다 할 일을 만들고, 일부 실패하면 저장한 문장은 후보에서 빼고 남은 것으로 다시 시도하게 둔다.
  - 기존 `TaskListView`의 쓰이지 않는 `Modal` import는 내 변경과 관계없어 남겼다.
- 확인한 사실
