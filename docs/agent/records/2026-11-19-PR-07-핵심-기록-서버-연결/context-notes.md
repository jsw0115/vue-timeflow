# 결정·근거·인수인계 메모

- 현재 확인된 구현/설정(2026-11-19)
  - 09 3절의 "이미 된 것: version"은 할 일에 맞지 않았다. `/api/tasks`(`TaskEntity`)는 행 잠금(`findOwnedForUpdate`)만 하고 마지막 저장이 덮어썼다. `feature_record` 기록과 체크리스트 항목에는 version이 있다.
  - 기록 API 공통 규칙은 `PUT` 본문 version, `DELETE ?version=`. 프런트 `apiRequest`는 204를 실패로 던졌다(체크리스트·`feature_record` 삭제가 204).
  - 할 일 로컬 목록은 8개 화면이 읽고 5곳이 쓴다. 체크리스트 담당자는 서버 계정만 받는다(로컬 주소록 시연 연락처는 계정이 아님). 2단계에서 다룬다.
- 선택한 대안/이유
  - 단계 나누기: UF-81의 연결 순서를 따르되 공통 기반(어댑터·계정 경계·서버 version)을 1단계로 먼저 뒀다. 할 일 화면 연결(2단계)이 version 없는 API 위에 올라가면 UF-84를 만족할 수 없고, 사용자가 단계마다 확인하기를 요청했다.
  - 할 일 version: PR-01 플래너와 같은 방식이다(Flyway V8 `NOT NULL DEFAULT 0`, 공개 버전 = 저장 + 1, 수정은 본문·상태 변경과 삭제는 쿼리, 누락·1 미만 400, 불일치 409). 새 규칙을 만들지 않고 기존 선례를 따랐다. 기존 행 잠금은 그대로 두어 체크리스트 변경과의 직렬화도 유지된다.
  - 저장 전 엔티티의 version은 null로 둔다(ID를 생성자에서 정하므로 Spring Data가 null version으로 새 엔티티를 판단). `getPublicVersion`은 null을 0으로 본다(단위 테스트의 저장 전 엔티티 대응).
  - 같은 내용의 수정은 JPA가 쓰지 않아 버전이 오르지 않는다. 플래너와 같은 동작이며 API 안내에 적었다.
  - 어댑터(`recordClient.mjs`)는 요청 함수를 주입받는 팩토리로 했다(`recordingClient.mjs`·`backupClient.mjs` 컨벤션). 오류를 `conflict`·`invalid`·`notFound`·`network`·`server`로 나누고, 409면 최신 값을 다시 조회해 `error.latest`에 담는다(UF-84 비교 화면용). 자동으로 덮어쓰지 않는다.
  - 계정별 목록(`useRecordCollection.mjs`)은 `useCapabilityStatus.mjs`처럼 세대 번호로 계정 전환을 감지한다. 요청 중 계정이 바뀌면 결과를 버리고 `stale` 오류를 던진다(UT-127). 충돌이면 목록 항목을 최신 서버 값으로 바꾸고, 404면 목록에서 뺀 뒤 오류를 그대로 알린다(화면이 "다른 곳에서 삭제됨"을 말할 수 있게).
  - `apiRequest`의 204를 성공(null)으로 바꿨다. 공용 모듈이지만 204를 실패로 기대하는 호출부가 없고, 어댑터 삭제(UF-80)에 필요하다.
  - `TaskRequest` 레코드 구성요소 안에 주석을 넣었다가 계약 생성기(`design-docs/current.mjs`)가 쉼표로 구성요소를 나눠 파싱에 실패했다. 기존 레코드처럼 주석을 빼고, 규칙은 `TaskService.requireVersion` 주석과 API 안내에 적었다.

## 2단계(할 일 화면 연결, 2026-11-19)

- 사용자 요청: "2단계 진행해줘. 마지막 단계까지." 단계마다 사용자 확인을 받던 방식을 바꿔 7단계까지 이어서 진행한다. 단계마다 검증하고 커밋한다.
- 선택한 대안/이유
  - 읽는 화면 8곳을 바꾸지 않으려고 `appState.tasks`를 같은 이름의 쓰기 가능한 computed로 바꿨다. 읽기는 로그인이면 서버 목록, 로그아웃이면 로컬 목록이다. 통째로 바꾸기(set)는 로컬에만 쓴다(기존 테스트·로컬 정리 코드 호환).
  - 공통 모듈(`syncedCollection.mjs`)은 4~7단계가 그대로 쓴다. 로그아웃 저장은 지금 동작과 같고(맨 앞에 넣고 숫자 ID), 로그인 저장은 서버 성공 응답 뒤에만 목록에 들어간다.
  - 상세는 편집을 시작한 할 일(base)의 version으로 저장한다. 목록을 다시 불러와 version이 올라가도 그 version을 쓰면 다른 곳의 변경을 모르고 덮어쓴다. 완료 토글도 같은 version으로 보내고, 내 변경이면 기준 version을 따라 올린다.
  - 완료 체크는 `@click.prevent`로 브라우저가 체크 표시를 되돌리게 하고, 서버 성공 뒤 값이 바뀔 때만 체크된다(UF-82). 실패하면 notice로 알리고 던지지 않는다. 토글 충돌은 비교 화면 없이 최신 상태로 바꾸고 다시 누르게 한다(내용 편집이 아니라서).
  - 체크리스트는 서버 할 일 목록 응답에 없어 할 일별로 불러 둔다(목록은 미리보기할 할 일만, 상세는 열 때). 저장은 바뀐 항목만 보내고(추가→이름·담당자→완료→삭제), 중간 실패 시 성공한 결과를 기준(baseline)으로 삼아 다시 시도하면 남은 것만 보낸다. 새 항목은 서버 ID로 바꿔 다시 만들지 않는다. 서버에 일괄 저장 API를 만드는 안은 기획에 없는 API 변경이라 택하지 않았다.
  - 체크리스트 항목은 단건 조회 API가 없어 충돌이면 목록 전체를 다시 불러 비교 화면에 쓴다.
  - 작성 창에서 할 일은 만들었지만 체크리스트가 실패하면 창을 닫지 않고 진행 상태를 들고 있다가, 다시 저장할 때 할 일을 다시 만들지 않는다. 문구는 "할 일은 저장했지만 체크리스트 일부를 저장하지 못했어요."로 무엇이 저장됐는지 먼저 알린다.
  - `savePostDraft`를 async로 바꿨다. 4~6단계에서 대부분 종류가 서버 저장이 되므로 지금 바꾸는 편이 낫다. `writing-flows.test.mjs`에 `await`를 붙였다.
  - 400 오류 응답에 필드 정보가 없어(`ApiResponse`는 success·data·message), 화면이 서버 메시지 낱말(제목·마감)로 입력란을 고른다. 못 고르면 저장 상태 줄에 메시지를 보인다. 오류 응답 형식을 바꾸는 것은 모든 API 계약 변경이라 택하지 않았다.
  - 비교 화면의 두 버튼은 모두 button-secondary다. 상세에 이미 주 액션(저장하기)이 있고, 덮어쓰기를 더 눈에 띄게 하지 않으려는 것이다. 바뀐 값은 굵기로만 구분했다(포인트 컬러를 더 쓰지 않음).
  - 로딩 문구는 빈 상태가 아니라서 `empty-state`가 아니라 `input-field-help`로 둔다(빈 상태 문구 검사 규칙).
  - 메모에서 옮기기는 메모가 6단계까지 로컬이라 서버의 `convert-to-task`를 쓸 수 없다. 고른 문장마다 할 일을 만들고, 일부 실패하면 저장한 문장은 후보에서 빼고 남은 것으로 다시 시도하게 둔다.
  - 기존 `TaskListView`의 쓰이지 않는 `Modal` import는 내 변경과 관계없어 남겼다.
- 확인한 사실
  - 백엔드 chat-local의 CORS 허용 출처는 `127.0.0.1:5173`·`localhost:5173`·`127.0.0.1:15173`이다. 다른 포트의 Vite에서 보낸 브라우저 POST는 403이다(같은 출처 GET은 Origin 헤더가 없어 통과). 8080은 다른 컨테이너가 쓰고 있어 백엔드는 18080, Vite는 15173으로 띄워 점검했다.
- 남은 일과 위험
  - 로그인 사용자의 기존 로컬 할 일은 3단계 전까지 보이지 않는다(지우지 않음). 2·3단계는 함께 배포한다.
  - 홈·캘린더·통계는 로그인 상태에서 서버 할 일을 읽지만, 목록을 다시 불러오는 시점은 할 일 목록 화면 진입이다.
- 사용자 변경과 자체 변경 구분: 사용자 미커밋 `Modal.vue`, `PlannerItemQueryRepositoryImpl.java`, `docs/output/`는 손대지 않았다. 비교 화면은 Modal을 쓰지 않는 인라인 영역으로 만들었다.

## 3단계(로컬 자료 이전, 2026-11-19)

- 선택한 대안/이유
  - 멱등 키는 서비스 계층(`TaskService`·`RecordService`·`WorkService`의 4인자 create)에서 생성과 같은 트랜잭션으로 처리한다. 필터·인터셉터로 응답을 저장하는 방식은 생성 커밋과 키 기록 사이에 틈이 생긴다. 같은 키가 동시에 오면 늦은 쪽은 기본 키 충돌로 409가 되고 그 생성도 되돌린다(H2 동시 요청 테스트).
  - 다시 온 요청에는 저장한 응답 본문이 아니라 처음 만든 기록을 다시 읽어 돌려준다(`resource_id`). 응답 본문을 저장하지 않아 표가 작고, 이후 수정된 최신 값을 준다. 처음 기록을 지웠으면 404로, 다시 만들지 않는다.
  - 요청 해시는 맵 키를 정렬한 JSON의 SHA-256이다. 필드 순서만 다른 본문은 같은 요청이다.
  - 생성 API 8곳(할 일·일정·루틴·다이어리·메모·D-Day·머니로그·경력)에 헤더를 한 번에 더했다. 서버 변경과 V9를 한 단계에 모으고, 4~7단계는 프런트만 바꾸기 위해서다.
  - 7일 정리는 `@Scheduled`이고 `config/SchedulingConfig`로 정기 작업을 켰다. 기존 정기 작업(채팅 3개)은 모두 `app.chat.enabled` 조건부 빈이라 영향이 없다.
  - API 계약 생성기(`design-docs/current.mjs`)가 헤더를 자바 변수 이름으로 적어 실제 헤더 이름(`Idempotency-Key`)과 달랐다. 문자열 값이 있으면 그 값을 쓰게 고치고 컨트롤러에 헤더 이름을 문자열로 적었다. 채팅 SSE의 `Authorization` 헤더 표기도 같이 바뀌었다(소문자 → 실제 이름).
  - 프런트 이전은 기록 종류별 항목(entries)을 모으는 공통 모듈이다. 할 일은 `local:task:{id}`로 보내고, 완료 상태는 생성 뒤 상태 변경으로, 체크리스트는 서버에 같은 제목이 있으면 이미 옮긴 것으로 본다(앞선 시도가 체크리스트 중간에 끊긴 경우). 모두 성공해야 로컬 목록에서 뺀다.
  - 옮긴 기록은 이 브라우저 목록에서 뺀다(복사가 아니라 이동). 남겨 두면 다음 로그인 때 다시 묻고, 7일 뒤 키가 지워지면 중복이 생긴다.
  - "나중에"는 sessionStorage에 계정 ID로 기억한다. 같은 탭의 새로고침은 다시 묻지 않고, 로그아웃하면 지워 다음 로그인 때 묻는다(UT-130).
  - 시연 판단(Q-11)은 `origin: 'demo'` 또는 시드와 ID·제목·마감일이 모두 같을 때다. 시드에 `origin: 'demo'`를 붙였다. 예전 브라우저 자료는 내용 비교로 거른다.
  - 주소록 연락처 담당자는 계정이 아니라서 담당자 없이 옮기고, 안내에 그 수를 보인다(Q-21과 같은 이유).
  - 안내는 결과(옮긴 수·실패 수)를 보일 수 있게 닫을 때까지 둔다. 실패하면 "다시 시도"로 남은 것만 다시 보낸다.
  - 현재 DB 문서는 프로젝트 생성기의 격리 MySQL 캡처(메타데이터만)로 다시 만들었다. 생성기에 새 표 설명을 더했다.
- 확인한 사실
  - 격리 MySQL에 V8(1단계 뒤 첫 bootRun)과 V9가 적용됐다(`flyway_schema_history`).
- 남은 일과 위험

## 4단계(일정 연결, 2026-11-19)

- 선택한 대안/이유
  - 일정 저장소(`scheduleStore.mjs`)는 2단계 공통 모듈을 그대로 쓴다. 서버 허용 필드(`FeatureType.SCHEDULE`)만 보내고, 화면이 쓰는 파생 값(time·date·tag·state)은 응답에서 다시 만든다. 일정을 읽는 화면(홈·캘린더·플래너·다이어리·검색 색인)은 `events` 이름을 유지해 바꾸지 않았다.
  - `/api/schedules` 목록은 `{items,total}` 페이지(최대 100건)라 `recordClient`에 `paged`를 더해 끝까지 모은다. 6·7단계 기록(다이어리 등)도 같은 형식이다.
  - "이 회차부터" 분할은 IM-14 위험 표대로 새 일정을 먼저 만들고 원래 일정의 반복을 전날에서 끝낸다. 뒤 요청이 실패하면 만든 일정을 지운다. 지우지도 못하면 `error.orphan`으로 "회차가 겹칠 수 있어요"를 알린다. 순서를 반대로 하면 실패 때 회차가 조용히 빠져 계획이 사라진다.
  - 회차 변경·건너뛰기·되돌리기와 상세 저장은 상세를 연 때의 일정(base) 위에서 반복 규칙을 계산해 그 version으로 보낸다. 충돌이면 최신 값과 비교하고, "내 내용으로 다시 저장"은 최신 반복 규칙 위에서 같은 동작을 다시 계산한다.
  - 서버는 참석자로 계정 ID 문자열만 받는다(`참석자는 계정 ID 문자열 배열입니다`). 주소록은 이 브라우저의 시연 자료라 Q-21과 같은 이유로 로그인 상태에서는 참석자를 고르지 않게 하고 안내한다. 서버에 이미 있는 계정 ID 참석자는 그대로 둔다. 로컬 일정을 옮길 때 주소록 참석자는 빼고 수를 알린다.
  - 400 입력란 표시는 일정 날짜 입력이 `EventDateFields` 컴포넌트 안에 있어 그 아래에 "종료 시간: 메시지"로 보인다(`role="alert"`). 컴포넌트 안 입력에 `aria-invalid`를 주려면 컴포넌트를 고쳐야 해 이번에는 하지 않았다.
  - 시연 일정은 날짜가 앱을 연 날로 정해져 ID와 제목·시작·종료 시각으로 구분한다(Q-11의 날짜 비교를 일정에는 쓸 수 없음).
  - 캘린더 주소(`/events?id=…&occurrence=…`)로 열 때, 로그인 상태는 목록을 불러온 뒤에 열 수 있어 목록 길이도 지켜보고, 이미 연 일정이면 다시 열지 않는다.
- 남은 일
  - 캘린더 화면 자체는 이번 브라우저 점검에서 열지 않았다(읽기 전용, 같은 `events` 목록).

## 5단계(루틴 연결, 2026-11-19)

- 소스 대조로 찾은 것: `/history` 항목에 수행 기록 version이 없었다. 수행 기록 저장(`PUT /history/{date}`)은 같은 값이 아니면 version이 필요해, 새로고침한 화면은 오늘 완료를 취소할 수 없었다. 서버 `ScheduleService.history` 항목에 `version`(없으면 0)을 더했다(추가 필드라 기존 사용처와 호환).
- 선택한 대안/이유
  - 화면 값(오늘 완료·연속·최고·최근 7일·4주 달성률)은 루틴 정의에 없어 루틴마다 최근 365일 이력을 불러 계산한다. 4주 범위만 부르면 연속 기록이 28일에서 잘린다. 범위는 서버 한도(367일) 안이다.
  - 첫 수치는 최근 4주(오늘 포함 28일) 달성률이고 분모는 완료와 놓친 날뿐이다(Q-05, 서버 rate와 같은 규칙). 연속 일수는 보조로 둔다. 로그아웃 상태는 날짜별 완료 기록이 없어 지금처럼 연속·최근 7일을 보인다.
  - 이력 값은 루틴 정의 응답이 바뀌어도(수정·중지) 이어 붙이도록 저장소 안에 두고, 정의를 저장한 뒤에는 그 루틴 이력만 다시 불러온다(중지·쉬는 날이 회차 계산을 바꾼다).
  - 오늘 완료는 `click.prevent`로 서버 성공 뒤에만 체크된다. 충돌이면 최신 이력으로 바꾸고 알리며, 쉬는 날 같은 400은 서버 메시지를 보인다. `appState.toggleRoutine`을 저장소로 넘겨 홈 화면은 체크 방식만 바꿨다.
  - 쉬는 날 창은 저장할 때마다 목록 항목이 최신 값으로 바뀌므로 대상 루틴을 ID로 찾는다(예전 객체를 들고 있으면 오래된 version으로 보낸다).
  - 중지·쉬는 날·삭제처럼 창 없이 바로 저장하는 동작은 실패하면 안내만 하고, 충돌이면 최신 값으로 바꾼 뒤 다시 하게 한다. 내용 편집인 수정 창만 비교 화면을 쓴다.
  - 로컬 루틴을 옮길 때 오늘 완료했으면 오늘 수행 기록도 옮긴다. 시연 루틴은 날짜가 없어 제목·시각으로 구분한다. 옛 로컬 루틴에 시작일·진행 시간이 없으면 오늘·30분으로 채워 보낸다(서버 필수 값).
- 범위 밖
  - 루틴 히스토리 화면(`RoutineHistoryView`)은 원래 고정 시연 값을 보이는 화면이라 이번에 연결하지 않았다(04 MN-25 로컬 유지).

## 6단계(다이어리·메모·D-Day·머니로그, 2026-11-19)

- 선택한 대안/이유
  - 네 기록은 같은 `feature_record` API라 공통 저장소(`featureStore.mjs`) 하나에 종류별 변환(`featureKinds.mjs`)만 둔다. 읽는 화면은 기존 이름(`diaries`·`memos`·`ddays`·`moneyEntries`)을 유지했다.
  - 기분(Q-07): 코드 5개로 저장하고 서버가 검사한다. 예전 이모지·한국어 값은 화면이 읽을 때 코드로 바꾼다(서버에 남은 예전 값도 같음). 다이어리 작성 화면의 기분 선택은 이모지 글자(키보드로 고를 수 없는 span)에서 문구 버튼(`segmented-tab`, `aria-pressed`)으로 바꿨다. 디자인 계약의 장식 이모지 피하기와 Q-07의 화면 문구를 함께 따른 것이다.
  - D-Day: 로컬 자료의 date는 "8월 31일 · 저녁 식사" 같은 표시 문구라 연도가 없다. 서버로는 ISO 날짜(`isoDate`)를 보내고, 화면 date·남은 날은 응답에서 다시 만든다. 로그아웃 상태 새 D-Day도 `isoDate`를 남긴다. 연도 없는 예전 D-Day는 올해 날짜로 옮기고 그 수를 이전 안내에 보인다(정확한 연도를 알 수 없음을 사용자에게 알리고 상세에서 고치게 함).
  - 남은 날 계산을 `utils/dday.mjs`로 옮기며, 예전 계산이 ISO 날짜를 UTC로 읽어 한국 시간에서 오늘을 D-1로 보이던 것을 바로잡았다(새 서버 표시가 이 계산을 쓰므로 함께 고침).
  - D-Day 상세의 고정은 연 때의 version으로 보내고 기준 version을 따라 올린다. 브라우저 점검에서 고정 뒤 저장이 내 변경과 충돌하는 결함을 찾아 고쳤다(할 일 상세의 완료 토글과 같은 방식).
  - 메모는 편집 화면이 없어(만들기·할 일로 옮기기만) UT-125·UT-126을 다이어리로 실행했다. 메모의 화면 time은 서버 date로 채운다.
  - 머니로그 CSV 가져오기는 로그인 상태에서 행마다 서버에 저장하고 실패한 행 수를 알린다.
- 남은 것
  - 기존 D-Day 목록·관리 화면의 고정 버튼 `aria-label`이 바인딩되지 않은 문자열(`aria-label="d.pinned ? ..."`)이다. 이번 변경과 관계없는 기존 코드라 고치지 않고 기록만 남긴다.
