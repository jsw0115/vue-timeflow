- 기준 기획: 09 3절(UF-80~UF-87, UT-120~UT-131), 06 IM-07, 09 권장 결정 Q-07·Q-11·Q-13, IM-14 3단계.
- 현재 확인한 사실(2026-11-19 소스 대조)
  - 09 3절은 "이미 된 것: 각 기록의 서버 CRUD·version·소유권 검사"라고 적었지만, 할 일 API(`/api/tasks`, `TaskEntity`)에는 version이 없다. 수정은 행 잠금(`findOwnedForUpdate`)만 하고 마지막 저장이 덮어쓴다. UF-80·UF-84와 UT-120·UT-125·UT-126은 할 일의 version을 전제로 한다. 같은 묶음의 다른 기록(`/api/diaries` 등 `feature_record`)과 체크리스트 항목은 version이 있다.
  - 기록 API의 공통 규칙은 `PUT` 본문 `version`, `DELETE ?version=`이다. 할 일 상태 변경(`PATCH /status`)도 같은 규칙으로 맞춘다. 선례는 PR-01 플래너(V7, 공개 버전 = 저장 버전 + 1).
  - 프런트 `apiRequest`는 본문이 없는 204 응답을 실패로 던진다. 체크리스트·`feature_record` 삭제가 204라 공통 어댑터의 삭제가 동작하지 않는다.
  - 할 일 로컬 목록(`appState.tasks`)은 화면 8곳이 읽고 5곳이 쓴다. 체크리스트는 서버에서 별도 API이고, 체크리스트 담당자는 서버 계정만 받는다(로컬 주소록 시연 연락처는 계정이 아니다).
  - 서버 연결 모듈 컨벤션은 `features/<영역>/<이름>Client.mjs`(요청 주입 팩토리)와 반응형 `use<이름>.mjs`, 테스트는 `frontend/tests/*.test.mjs`(가짜 요청)다.

- 1단계 성공 기준
  - 서버: 할 일 수정·상태 변경·삭제에 version이 필요하고, 오래된 version은 409, 다른 계정은 404, version 누락·1 미만은 400, 생성 version은 생략이나 0만 허용. 동시 수정은 하나만 성공. 기존 행은 마이그레이션 뒤 version 0(공개 1).
  - 프런트: 어댑터가 생성 응답의 version을 보관해 수정·삭제에 그대로 보낸다(UT-120). 409·400·404·네트워크·서버 오류를 구분하고 409이면 최신 값을 함께 준다. 계정이 바뀌면 이전 계정 응답을 반영하지 않는다(UT-127). 204 삭제가 성공으로 처리된다.
  - 수정 전 새 테스트 실패 확인, 백엔드 전체·프런트 전체·계약 검사·빌드 통과.
- 보안 관련: 소유권(다른 계정 404, 기존 `findOwnedForUpdate`), 입력 검증(version 범위), 동시 쓰기(낙관적 잠금 + 기존 행 잠금), 계정 전환 시 이전 계정 응답 폐기.
- 접근성: 1단계는 화면 변경 없음(N/A).
- 허용 범위: 구현·테스트·문서·의미 단위 커밋. 푸시·배포·운영 DB 변경은 하지 않는다. Flyway는 새 번호 파일만 추가한다.
