# 결정·근거·인수인계 메모

- 공유 범위는 그룹 멤버 행(`feature_member.share_level`)에 둔다. 일정마다 공유를 고르는 방식보다 단순하고, 그룹마다 다르게 보일 수 있다(UT-193). 처음 값은 none이라 그룹에 들어가기만 해서는 아무것도 보이지 않는다.
- 범위 밖 필드는 서버 응답에서 뺀다. 화면에서 가리면 개발자 도구로 볼 수 있기 때문이다(UF-112). 일정 ID도 담지 않아 다른 API로 원본을 부를 수 없다.
- 미리보기는 고른 멤버를 보는 사람으로 같은 `schedules`를 불러 내 일정만 남긴다. 미리보기와 실제 응답이 어긋날 수 없다(UF-111).
- 사람 찾기 횟수(1분 20번)는 서버 한 대의 메모리에 센다. 서버를 늘리면 공유 저장소로 옮겨야 한다(06 IM-10 위험).
- `UserRepository`는 테스트 설정에서 mock이라 테스트마다 `findByEmail`·`findById`를 정해 준다.
- 사용자 변경과 자체 변경 구분: 작업 시작 때 작업 트리는 깨끗했다(마지막 커밋 115c978). 이 단계의 변경은 모두 자체 변경이다.
- 2단계: 서버 응답에 이름이 없어 화면이 ID만 보일 수밖에 없었다. 이메일은 넣지 않고 닉네임만 더했다(이메일은 아는 사람만 정확히 입력해 찾는다는 Q-24 취지).
- 2단계: 초대받은 사람(INVITED)은 그룹 상세 API가 403이라, 수락·거절은 그룹 목록의 "받은 초대"에서만 한다. 거절은 자기 멤버 행 삭제로 했다(새 API를 만들지 않음).
- 2단계: 로그아웃 상태 공유 화면은 시연 데이터를 보이지 않고 로그인 안내만 보인다. 계정끼리 하는 기능을 로컬로 흉내 내면 서버 저장으로 오해할 수 있기 때문이다(CLAUDE.md 1절).
- 2단계: `.form-note`는 muted 글자에 surface 배경이라 DESIGN.md 대비 기준(4.36:1)에 못 미친다. 바꾼 공유 화면 5곳은 배경 없는 `.input-field-help`로 바꿨다. 다른 화면의 `.form-note`는 부록 B 항목이라 손대지 않았다.
- 2단계: 주소록(`store/contacts.js`)은 주소록·할 일·일정 화면이 계속 쓴다. 공유 화면만 떼어 냈고, 쓰지 않게 된 `addGroup`·`groupById`만 지웠다. 주소록과 공유를 잇는 일은 Q-21 결정 뒤다.
- 2단계 브라우저 점검 중 한글이 든 이메일은 브라우저 `type=email` 검사에 걸려 제출되지 않았다. 점검 스크립트의 계정 이메일을 ASCII로 바꿨다. 실제 가입 이메일 규칙과의 관계는 따로 보지 않았다.
- 다음 작업: 3단계 커뮤니티 화면 연결. 첫 명령은 `grep -n "community" frontend/src/router/index.js`로 커뮤니티 화면 목록을 확인하는 것이다.
