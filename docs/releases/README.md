## 버전의 의미

`MAJOR.MINOR.PATCH`를 변경 범위 설명의 기준으로 사용합니다. 호환성·데이터 이관·운영 영향을 함께 기록하며 0.x라도 예고 없는 계약 변경을 정당화하지 않습니다. 기능 추가는 MINOR, 호환 수정은 PATCH, 계약 파괴는 별도 이행 계획을 포함해 판단합니다. 계획 버전은 실제 package 버전·태그를 올린 것이 아닙니다.

제품 버전·전체 Git SHA·빌드 식별자·DB migration·문서 수정일·실제 배포일을 함께 관리합니다. 같은 0.1.0이라도 SHA가 다르면 다른 코드입니다. 이미지의 latest 대신 전체 SHA를 사용하며 문서 수정만으로 운영 배포를 표시하지 않습니다.

## 개발 중 추가·수정 절차

1. 작업 원장에 ID·접수일·유형·증상/요청·요구 ID를 등록합니다.
2. 영향 화면·API·DB·운영·개인정보·비용·호환성, 수용 기준과 목표 버전을 정합니다.
3. 구현 전에 해당 기준 문서와 WBS를 갱신하고 변경 이유를 남깁니다.
4. 수정 커밋과 실제 테스트 명령·결과·증거·검증일을 기록합니다. 실패 시 미완료로 둡니다.
5. 릴리스 후보를 검증하고 실제 배포한 환경·SHA·일시·승인을 노트에 확정합니다.
6. 릴리스 후 발견한 오류는 새 항목으로 등록해 수정 버전을 연결하고 원래 기록을 보존합니다.

원장은 상태·우선순위·목표일·완료일·수정 버전의 최신 값을 유지하고, 값이 바뀌면 변경 이력도 추가합니다. 자동화되지 않은 정기 갱신을 이미 실행 중이라고 표현하지 않습니다. 개발·리뷰·배포마다 갱신하는 팀 운영 절차입니다.

## 릴리스 노트 양식

```text
버전 / 상태(계획·후보·검증·배포·중단)
작성일 / 변경일 / 계획일 / 실제 검증일 / 실제 배포일
전체 SHA / 웹·API 버전 / 이미지·산출물
추가·수정·폐기한 기능과 요구·작업 ID
API·DB·설정·권한·사용자 행동의 변경
migration·기존 데이터·호환·백업·롤백
실행한 테스트와 결과·실환경 검수
알려진 문제·제약·미검증 범위
배포 환경·담당 역할·승인·후속 일정
```

버전 확정 때 frontend/package.json·잠금파일의 루트 버전, backend/build.gradle, JAR·CI·배포 스크립트의 파일명 참조도 함께 확인합니다. 자동 버전 교체 도구가 있는 것으로 가정하지 않습니다.
