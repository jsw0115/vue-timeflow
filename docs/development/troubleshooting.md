## 기록 원칙

증상·환경·실제 오류·원인·수정·검증·남은 한계를 연결합니다. 코드를 작성했다는 주장보다 재현과 검증 증거를 우선합니다. 문제를 재현하지 못한 경우 추정·확인 대기로 표시합니다. 로그에는 키·사용자 원문을 남기지 않습니다.

## DB 초기화와 기존 데이터 보존

과거 V1 DDL의 생성 문법·이름과 현재 엔티티·기존 DB가 달라 무조건 초기화를 재실행하는 방식이 안전하지 않았습니다. 기존 데이터·스키마·이력을 확인하는 CoreSchemaInspector, 검증한 baseline과 증분 migration으로 처리했습니다.

기존 계정 ID의 UUID와 신규 ULID 호환, 담당자·체크리스트·설정의 추가, 채팅 참조 폭 확장도 반영했습니다. 원본 V1을 다시 쓰거나 history·기존 회원·로그를 삭제하지 않는 경로를 사용했습니다.

상세 증상·조치·실제 DB 보존·HTTP 결과는 [2026-10-03 복구 기록](database-recovery-2026-10-03.md)에 있습니다. 이후 [2026-10-31 빈 DB 검증](documentation-2026-10-31/verification.md)에서 새 격리 환경의 Core V3~V6·Chat V1~V4 기동을 확인했습니다. 임의 운영 DB를 자동 복구할 수 있다는 뜻은 아닙니다.

## planner 생성자와 IDE 진단

2026-10-18에 PlannerItemQueryRepositoryImpl의 Lombok 의존 생성자 처리가 JDT에서 진단 문제를 일으키는 상황을 다뤘습니다. 필드와 명시적 생성자를 맞춰 코드와 에디터 진단의 차이를 줄였습니다. 수정 커밋은 98ae7c7입니다.

[당시 검증](planner-constructor-fix-2026-10-18/verification.md)을 근거로 하며 IDE 경고 하나를 전체 빌드 실패로 확대하지 않습니다. 현재 파일에 남은 사용자 편집은 이번 문서 작업에서 수정하지 않았습니다.

## Pages CI와 과거 계약 검사

현재 Java 계약이 확장된 뒤에도 기본 CI가 과거 목표 설계 스냅샷 검사에 의존해 문서·소스 대조 기준이 맞지 않았습니다. 2026-10-31에 최신 `frontend-api-contract.mjs --check`를 기준으로 정리하고 API inventory 검사는 유지했습니다. 수정 커밋은 a076a6a입니다.

당시 전체 웹 테스트 47개·Pages/웹 빌드·277개 operation과 190개 schema 대조를 통과했습니다. 이번 문서 통합에서도 두 API 소스 검사를 다시 실행했습니다. 실제 GitLab Runner·Registry·Pages 게시까지 실행한 수정이라고 표현하지 않습니다.

## 지원 Node와 기본 실행 환경

프로젝트는 Node >=22.12를 요구하지만 PC 기본값은 20.18.0이었습니다. 2026-10-31 실행 점검은 관리된 Node 24.22.1을 명시해 설치·웹 테스트·빌드를 검증했습니다. 전역 Node/PATH를 바꿔 해결한 것은 아닙니다.

재발 방지는 설치 문서의 요구·실행 경로 확인과 [BUG-001](../releases/backlog.md#bug-001)의 환경 정리입니다. “테스트에 성공했으므로 현재 아무 터미널에서나 기본 Node로 같은 결과가 난다.”라고 주장하지 않습니다.

## DB 문서와 한글·현재성

2026-10-31에 오래된 schema-alignment 문서의 한글이 `??`로 손상된 상태와, 부분 테이블 문서가 이후 구현을 반영하지 못한 것을 확인했습니다. 중복·오래된 본문을 최신 문서 연결로 통합하고 UTF-8 검사를 추가했습니다.

이전 격리 DB에서 information_schema와 Flyway 이력만 읽어 28개 테이블·205개 컬럼·15개 물리 FK를 캡처했습니다. 현재 DB 정의 생성기에는 마이그레이션 소스 해시와 --check를 넣고, 일반 사용자 DB 컨테이너의 캡처를 거부하도록 했습니다. DB 사용자 행·파일 바이트·비밀값은 캡처하지 않았습니다.

스키마 확인 중 잘못 가정한 `flyway_chat_schema_history` 조회는 실제 1146 오류가 났습니다. 실제 테이블 목록과 CoreMigrationStrategy를 확인해 `flyway_chat_history`로 수정했습니다. DB를 바꾸거나 테이블을 새로 만드는 우회는 하지 않았습니다. 이는 문서 조사 명령 오류이며 앱의 migration 버그로 등록하지 않습니다.

## 예상된 오류와 미완료 항목

400·401·403·404·409·503은 계약에 따른 검증 시나리오의 기대 결과일 수 있습니다. 특히 외부 제공자가 없는 유효 실행의 503을 모두 200으로 바꾸는 것은 해결이 아닙니다.

디자인 계약 충돌, Java 헤더 검사 충돌, 업로드 프록시 경계, BYOK 키 보관, 로컬 저장의 서버 연결, 실제 운영·네이티브 검수는 원장에 남아 있습니다. 문서로 확인한 위험을 실제 코드에서 고쳤다고 표시하지 않습니다.

새 기록은 발생/확인일·버전·SHA·재현·정확한 오류·원인 근거·변경·테스트·결과·잔여 위험·후속 ID를 포함합니다. 원문 로그가 길면 비밀값을 제거한 증거 파일로 연결합니다.
