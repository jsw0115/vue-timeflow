## 저장 모델 개요

현재 저장은 세 가지 방식이 함께 있다.

| 방식 | 테이블 | 특징 |
| --- | --- | --- |
| 구형 전용 테이블 | `events`, `task`, `routine`, `routine_log`, `planner_item` | 도메인별 컬럼. 일부는 낙관적 잠금이 없다 |
| 범용 JSON 기록 | `feature_record` | PK `(owner_id, kind, record_id)`, `version`으로 충돌 검사. 신형 일정·다이어리·메모·업무·경력 등을 종류(kind)별 JSON으로 저장 |
| 채팅 전용 | `chat_*` | 채팅 모듈이 소유. 별도 Flyway 이력으로 관리 |

구형 `events`·`routine`·`planner_item`과 신형 `SCHEDULE`·`ROUTINE_RECORD` 기록은 자동 동기화하지 않는다. 두 계약을 함께 쓰면 같은 활동이 중복 저장될 수 있다. 어느 쪽을 쓸지는 [PR-03](01-개발-우선순위.md#pr-03-구형신형-저장-모델-선택과-중복-정책)에서 정한다.

## 마이그레이션 구성과 이력

| 순서 | 위치 | 내용 | 비고 |
| --- | --- | --- | --- |
| V1 | `db/migration/V1__initial_schema.sql` | 과거 `tbl_*` 초기 DDL | 역사적 파일. 체크섬만 보존하고 신규 DB에 수동 재실행 금지 |
| 기준선 2 | `CoreSchemaInspector` | 관리되지 않은 카탈로그의 알려진 Core 컬럼을 확인한 뒤 채택 | 알 수 없는 테이블이 있으면 거부 |
| V3 | `db/core/V3__safe_core_schema.sql` | 누락된 Core 테이블을 `CREATE TABLE IF NOT EXISTS`로 생성 | 추가형 |
| V4 | `db/workspace/V4__task_checklist_and_planner_preferences.sql` | 체크리스트·담당자·플래너 기본 보기 | 추가형 |
| V5 | Java `db.core.V5__account_identifier_width` | 계정 참조 컬럼을 UUID·ULID 폭으로 확장, 영향 FK 복원 | Java migration |
| V6 | `db/workspace/V6__frontend_feature_records.sql` | `feature_record`·`feature_member`·`feature_friend`·`feature_block`·`feature_file`, `auth_version`, 플래너 소유자 | 추가형 |
| V7 | `db/workspace/V7__planner_item_version.sql` | `planner_item.version BIGINT NOT NULL DEFAULT 0` | 진행(미커밋) |
| 로컬 V1~V2 | `db/chat-local-core` | 격리 로컬 개발용 초기화 | chat-local 전용. 업그레이드용 아님 |
| 채팅 V1~V4 | `db/chat` | 채팅 스키마, 멘션·태그, 메시지 검색, 계정 ID 폭 | `flyway_chat_history`로 별도 관리 |

Core·workspace는 한 이력(`flyway_schema_history`)을 공유하므로 다음 번호는 V8이다. 채팅은 별도 이력이므로 다음 번호는 채팅 V5다. 이미 적용된 파일은 수정하지 않고, 원인 확인 전에 `repair`·`clean`을 실행하지 않는다. 상세 규칙은 [DB 환경·이력](../database/environment.md)과 `db/migration/README.md`를 따른다.

## 미해결 설계 쟁점

- `task.event_id`는 문자열이고 `events.id`는 BIGINT다. FK를 새로 만들거나 데이터를 강제 변환하지 않는다. 기록 연결(PR-08)을 설계할 때 함께 정한다.
- `feature_record.payload`는 LONGTEXT다. JSON 형식·허용 필드·크기는 서비스가 검증하며, DB가 내용 무결성을 보장하지 않는다.
- 계정 ID는 구형 UUID(36자)와 신형 ULID(26자)가 섞여 있다. 모든 ID가 26자라고 가정하지 않는다.
- FK가 없는 사용자 참조는 서비스 권한 검사에 의존한다. 새 테이블을 추가할 때 소유권 검사 위치를 구현 방안에 적는다.

## 스키마 변경 절차

1. [06 구현 방안](06-구현-방안.md)에 변경 이유·영향 테이블·롤백 가능성을 적고, 위 예정 변경 표에 DB ID를 추가한다.
2. 해당 경로에 새 번호의 Flyway 파일을 추가하고, 첫 줄에 한국어 역할 주석을 단다. JPA Entity를 함께 고친다.
3. H2 테스트와 격리 MySQL 기동(`docker compose -f infra/chat/compose.yml up -d --wait` 후 chat-local 프로파일)으로 확인한다.
4. [현재 DB 정의](../database/current-database.md)를 메타데이터 생성기로 갱신하고, 이 문서의 마이그레이션 이력과 상태를 고친다.
5. 운영 적용 전에 백업과 별도 복원 검증을 한다. 마이그레이션 이후 이전 이미지로 돌아갈 수 있는지 [07 결과서](07-테스트-시나리오-및-결과서.md)에 기록한다.
