## 작성 규칙

- 항목마다 **현재**, **설계**, **변경 파일**, **위험·대응**, **완료 조건**, **테스트**를 둔다. 테스트는 [07 테스트 시나리오 및 결과서](07-테스트-시나리오-및-결과서.md)의 TS ID로 연결한다.
- 설계가 정해지지 않은 항목은 "결정 필요"와 선택지를 적고, 임의의 값으로 채우지 않는다.
- 구현하면서 설계가 바뀌면 이 문서를 먼저 고치고 변경 이력에 이유를 남긴다. 착수 시점의 상세 메모는 `docs/agent/records/` 작업 폴더에 둔다.

## 공통 원칙

- 사용자는 JWT에서 정한다. 요청 본문의 owner로 다른 사용자를 지정할 수 없다. 다른 계정의 자원은 404로 응답한다.
- 변경 요청은 조회한 version을 요구한다. 오래된 version은 409로 거절하고, 화면은 입력을 보존한 채 다시 조회하도록 안내한다.
- 스키마 변경은 새 번호의 Flyway 파일로만 한다([05 데이터베이스 설계서](05-데이터베이스-설계서.md#스키마-변경-절차)).
- API가 바뀌면 `docs/api/` 명세와 `frontend/scripts/frontend-api-contract.mjs` 계약 검사를 같은 커밋에서 고친다.
- 화면 문구는 [DESIGN.md](../../DESIGN.md) 6장의 담백한 안내형 문장을 따르고, 미완료를 벌점처럼 표현하지 않는다.

## IM-01. 플래너 version 충돌 방지

- **연결**: PR-01, REQ-F07, REQ-N05, DB-01, TS-01~TS-04.
- **현재**: 완료(2026-11-17). 아래 남은 작업을 모두 처리했다.
- **설계**
  - `PlannerItemEntity`에 JPA `@Version Long version`을 둔다. 외부에 보이는 공개 버전은 `version + 1`이다. 그래서 V7 이전에 있던 행(내부 0)도 공개 버전 1부터 시작한다.
  - `POST`는 version을 생략하거나 0이어야 한다. 그 밖의 값은 400이다.
  - `PUT /api/planner/items/{id}`는 본문에, 상태 변경과 `DELETE`는 query `version`에 공개 버전을 받는다. 값이 없거나 1보다 작으면 400, 현재 공개 버전과 다르면 409다.
  - 비교 후 `flush`하므로, 동시에 같은 version으로 들어온 두 요청 중 늦은 쪽은 JPA 낙관적 잠금으로 실패한다.
- **변경 파일**: `planner/PlannerController.java`, `PlannerService.java`, `PlannerItem.java`, `PlannerItemEntity.java`, `PlannerItemQueryRepositoryImpl.java`, `records/RecordActionsController.java`, `db/workspace/V7__planner_item_version.sql`, `db/workspace/README.md`, 테스트 `PlannerPersistenceTest.java`·`PlannerVersionTest.java`, API 명세 4종, `frontend/scripts/frontend-api-contract.mjs`, `frontend/tests/frontend-api-contract.test.mjs`, 기능 명세서.
- **처리 결과**
  1. `PlannerController.java`의 변경 줄 끝 공백을 지웠다.
  2. `PlannerItemQueryRepositoryImpl.java`의 변경은 빈 줄 1개뿐인 기존 사용자 변경이므로 이 작업에서 제외했다.
  3. 동시 요청 409는 `PlannerVersionTest.concurrentSnapshotsCannotBothCommit`으로 확인했다. 예외 처리기는 고치지 않았다.
  4. 저장된 `openapi.json`의 `PlannerItem`·`PlannerItemUpdate` `required`에 `version`이 중복되어 계약 검사가 실패했다. 생성기로 다시 만들어 중복을 없앴다.
  5. 검증 결과는 07의 RUN-13~RUN-18에 기록했다.
- **위험·대응**: version 없이 요청하는 기존 클라이언트는 400을 받는다. 2026-11-17 정적 확인 기준으로 프런트 화면에서 `/api/planner/items`를 호출하는 곳은 없다(관리자 시연 로그 문자열만 있음). 그래서 화면 쪽 영향은 없지만, 운영에 배포할 때는 클라이언트와 DB를 함께 배포한다.
- **완료 조건**: TS-01~TS-04가 PASS이고, 공백 검사를 통과하고, 의미 단위로 커밋되어 있다.

## IM-02. 업로드 크기 한도 정렬

- **연결**: PR-02, REQ-F14, IMP-004, TS-05, TS-06.
- **현재**: 파일 한도는 세 곳에서 서로 다르게 정해져 있다.

| 위치 | 값 |
| --- | --- |
| `records/AttachmentController.java` | 파일 1바이트~10 MiB(`MAX_BYTES`) |
| `application.yml` | `max-file-size: 10MB`, `max-request-size: 11MB` |
| `infra/deploy/nginx.conf` | `client_max_body_size 10m` |

- **설계**: 허용 파일 크기는 10 MiB로 유지한다. multipart 경계와 헤더가 붙을 여유를 두기 위해 프록시를 요청 한도와 같은 `11m`로 올린다. Caddy 경로는 본문 크기 제한이 설정되어 있지 않으므로 앱 한도가 최종 기준이 된다. 화면 안내 문구도 "10 MiB까지"로 맞춘다.
- **변경 파일**: `infra/deploy/nginx.conf`, 첨부 안내 화면 문구(해당 화면을 찾아 수정), [연계 명세](../api/frontend-backend-2026-10-10/integrations.md)나 배포 문서에 한도가 적혀 있으면 그 부분.
- **위험·대응**: 프록시 한도를 올리면 큰 요청을 받는 비용이 조금 늘어난다. 앱이 10 MiB 초과를 400으로 거절하므로 저장 위험은 없다.
- **완료 조건**: 세 위치가 같은 기준을 가리키고, TS-05·TS-06이 PASS다. 실제 프록시 경계 시험은 서버 환경이 있을 때 PR-13에서 한다.

## IM-03. 구형·신형 저장 모델 선택

- **연결**: PR-03, REQ-F03, REQ-F05, REQ-F07, DB-02, TS-07.
- **현재**: 구형 `/api/events`·`/api/routines`·`/api/planner/items`와 신형 `/api/schedules`·`/api/routine-records`가 함께 있고 자동 동기화하지 않는다.
- **결정 필요**: 화면별로 어느 계약을 쓸지 정한다.

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 신형(`feature_record`)으로 통일 | version·소유권 검사가 이미 있고, 화면 연결 방식을 하나로 만들 수 있다 | 구형 반복 일정의 회차 물리화를 다시 구현해야 하고, 구형 데이터 이전이 필요하다 |
| B. 구형 유지, 신형은 새 기능만 | 기존 반복·통계 코드를 재사용한다 | 두 모델이 계속 남고, 통계에서 중복 제외 규칙을 따로 관리해야 한다 |
| C. 도메인별 선택 | 일정은 구형, 루틴 기록은 신형처럼 장점을 고를 수 있다 | 규칙이 복잡해지고 문서화 부담이 크다 |

- **설계 원칙**: 어떤 안을 고르든 시간이 겹친다는 이유만으로 두 기록을 자동 병합하지 않는다. 이전은 원본 ID와 사용자 승인, 멱등 키를 기준으로 한다.
- **산출물**: 화면(MN)별 사용 계약 표를 [04 메뉴기능 목록서](04-메뉴기능-목록서.md)에 추가하고, 통계 집계 규칙을 기능 명세서에 적는다.
- **완료 조건**: 결정과 근거가 기록되어 있고, 통계 중복 제외 테스트 TS-07이 설계되어 있다.

## IM-05. BYOK 키 평문 저장 제거

- **연결**: PR-05, REQ-N03, REQ-F19, IMP-005, TS-08.
- **현재**: `frontend/src/store/aiSettings.js`가 `apiKey`를 포함한 설정을 `localStorage`에 JSON으로 저장한다. 안내 문구는 "키는 이 기기에만 저장"이다.
- **설계**
  1. 저장할 때 `apiKey`를 빼고 저장한다. 읽을 때 기존 값에 `apiKey`가 있으면 지우고 다시 저장한다.
  2. 상용 AI 경로는 서버 키 관리만 허용한다. 서버 AI 제공자가 미연결인 동안 BYOK 선택지는 "준비 중" 상태로 표시하고 실행하지 않는다.
  3. 브라우저 세션 동안만 키를 쓰는 방식이 필요하면 메모리 보관으로 한정하고, 이 문서에 결정을 다시 적는다.
- **위험·대응**: 기존 사용자의 키가 지워진다. 화면에 "보안을 위해 저장된 키를 지웠습니다" 안내를 한 번 보여 준다.
- **완료 조건**: 설정 저장·복원 후 localStorage에 `apiKey`가 없다는 테스트 TS-08이 PASS다.

## IM-07. 핵심 기록 흐름 서버 연결

- **연결**: PR-07, REQ-F02~REQ-F09, IMP-001, WBS-03, WBS-04, DB-03, TS-10~TS-12.
- **선행**: IM-01 완료, IM-03 결정.
- **설계**
  - 공통 클라이언트: `features/auth/apiRequest.js`의 인증 요청 위에 기록 종류별 저장소 어댑터를 둔다. 조회·생성·수정·삭제와 version 보관, 409 처리를 한곳에서 한다.
  - 계정 경계: 로그인 계정이 바뀌면 메모리 상태를 즉시 비운다. P0-1의 상태 조회 무효화 방식과 같은 방식을 쓴다.
  - 저장 실패: 입력을 화면에 남겨 두고 다시 시도할 수 있게 한다. 409이면 서버 값과 내 입력을 나란히 보여 준다.
  - 로컬 자료 이전: 처음 로그인했을 때 로컬 기록이 있으면 이전 여부를 묻는다. 원본 로컬 ID를 멱등 키로 보내 두 번 이전해도 중복되지 않게 한다.
  - 연결 순서: 할 일 → 일정 → 루틴 → 다이어리·메모·D-Day·머니로그 → 경력. 앞 단계의 어댑터를 재사용한다.
- **위험·대응**: 로컬 시연 데이터가 실제 계정에 섞일 수 있다. 시연 데이터는 이전 대상에서 빼고, 사용자가 만든 기록만 고르게 한다.
- **완료 조건**: 재로그인·다른 브라우저·계정 전환·저장 실패·409 시나리오(TS-10~TS-12)가 PASS이고, [04 메뉴기능 목록서](04-메뉴기능-목록서.md)의 저장 방식이 `서버`로 바뀌어 있다.
