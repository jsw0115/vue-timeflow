## 작성 규칙

- 항목마다 **현재**, **설계**, **변경 파일**, **위험·대응**, **완료 조건**, **테스트**를 둔다. 테스트는 [07 테스트 시나리오 및 결과서](07-테스트-시나리오-및-결과서.md)의 TS ID로 연결한다.
- 설계가 정해지지 않은 항목은 "결정 필요"와 선택지를 적고, 임의의 값으로 채우지 않는다.
- 구현하면서 설계가 바뀌면 이 문서를 먼저 고치고 변경 이력에 이유를 남긴다. 착수 시점의 상세 메모는 `docs/agent/records/` 작업 폴더에 둔다.

## 공통 원칙

- 사용자는 JWT에서 정한다. 요청 본문의 owner로 다른 사용자를 지정할 수 없다. 다른 계정의 자원은 404로 응답한다.
- 변경 요청은 조회한 version을 요구한다. 오래된 version은 409로 거절하고, 화면은 입력을 보존한 채 다시 조회하도록 안내한다.
- 스키마 변경은 새 번호의 Flyway 파일로만 한다([05 데이터베이스 설계서](05-데이터베이스-설계서.md#스키마-변경-절차)).
- API가 바뀌면 `docs/api/` 명세와 `frontend/scripts/frontend-api-contract.mjs` 계약 검사를 같은 커밋에서 고친다.
- 화면 문구는 [DESIGN.md](../../DESIGN.md) 6장의 담백한 안내형 문장을 따르고, 미완료를 벌점처럼 표현하지 않는다.

## IM-01. 플래너 version 충돌 방지

- **연결**: PR-01, REQ-F07, REQ-N05, DB-01, TS-01~TS-04.
- **현재**: 완료(2026-11-17). 아래 남은 작업을 모두 처리했다.
- **설계**
  - `PlannerItemEntity`에 JPA `@Version Long version`을 둔다. 외부에 보이는 공개 버전은 `version + 1`이다. 그래서 V7 이전에 있던 행(내부 0)도 공개 버전 1부터 시작한다.
  - `POST`는 version을 생략하거나 0이어야 한다. 그 밖의 값은 400이다.
  - `PUT /api/planner/items/{id}`는 본문에, 상태 변경과 `DELETE`는 query `version`에 공개 버전을 받는다. 값이 없거나 1보다 작으면 400, 현재 공개 버전과 다르면 409다.
  - 비교 후 `flush`하므로, 동시에 같은 version으로 들어온 두 요청 중 늦은 쪽은 JPA 낙관적 잠금으로 실패한다.
- **변경 파일**: `planner/PlannerController.java`, `PlannerService.java`, `PlannerItem.java`, `PlannerItemEntity.java`, `PlannerItemQueryRepositoryImpl.java`, `records/RecordActionsController.java`, `db/workspace/V7__planner_item_version.sql`, `db/workspace/README.md`, 테스트 `PlannerPersistenceTest.java`·`PlannerVersionTest.java`, API 명세 4종, `frontend/scripts/frontend-api-contract.mjs`, `frontend/tests/frontend-api-contract.test.mjs`, 기능 명세서.
- **처리 결과**
  1. `PlannerController.java`의 변경 줄 끝 공백을 지웠다.
  2. `PlannerItemQueryRepositoryImpl.java`의 변경은 빈 줄 1개뿐인 기존 사용자 변경이므로 이 작업에서 제외했다.
  3. 동시 요청 409는 `PlannerVersionTest.concurrentSnapshotsCannotBothCommit`으로 확인했다. 예외 처리기는 고치지 않았다.
  4. 저장된 `openapi.json`의 `PlannerItem`·`PlannerItemUpdate` `required`에 `version`이 중복되어 계약 검사가 실패했다. 생성기로 다시 만들어 중복을 없앴다.
  5. 검증 결과는 07의 RUN-13~RUN-18에 기록했다.
- **위험·대응**: version 없이 요청하는 기존 클라이언트는 400을 받는다. 2026-11-17 정적 확인 기준으로 프런트 화면에서 `/api/planner/items`를 호출하는 곳은 없다(관리자 시연 로그 문자열만 있음). 그래서 화면 쪽 영향은 없지만, 운영에 배포할 때는 클라이언트와 DB를 함께 배포한다.
- **완료 조건**: TS-01~TS-04가 PASS이고, 공백 검사를 통과하고, 의미 단위로 커밋되어 있다.

## IM-02. 업로드 크기 한도 정렬

- **연결**: PR-02, REQ-F14, IMP-004, TS-05, TS-06.
- **현재**: 파일 한도는 세 곳에서 서로 다르게 정해져 있다.

| 위치 | 값 |
| --- | --- |
| `records/AttachmentController.java` | 파일 1바이트~10 MiB(`MAX_BYTES`) |
| `application.yml` | `max-file-size: 10MB`, `max-request-size: 11MB` |
| `infra/deploy/nginx.conf` | `client_max_body_size 10m` |

- **설계**: 허용 파일 크기는 10 MiB로 유지한다. multipart 경계와 헤더가 붙을 여유를 두기 위해 프록시를 요청 한도와 같은 `11m`로 올린다. Caddy 경로는 본문 크기 제한이 설정되어 있지 않으므로 앱 한도가 최종 기준이 된다. 화면 안내 문구도 "10 MiB까지"로 맞춘다.
- **변경 파일**: `infra/deploy/nginx.conf`, 첨부 안내 화면 문구(해당 화면을 찾아 수정), [연계 명세](../api/frontend-backend-2026-10-10/integrations.md)나 배포 문서에 한도가 적혀 있으면 그 부분.
- **위험·대응**: 프록시 한도를 올리면 큰 요청을 받는 비용이 조금 늘어난다. 앱이 10 MiB 초과를 400으로 거절하므로 저장 위험은 없다.
- **완료 조건**: 세 위치가 같은 기준을 가리키고, TS-05·TS-06이 PASS다. 실제 프록시 경계 시험은 서버 환경이 있을 때 PR-13에서 한다.
- **처리 결과(2026-11-17)**
  1. `infra/deploy/nginx.conf`를 `client_max_body_size 11m`로 바꾸고 이유를 주석으로 남겼다.
  2. 세 위치의 정렬을 `frontend/tests/upload-limits.test.mjs`로 고정했다. 수정 전 실행에서 Nginx 검사가 실패하는 것을 먼저 확인했다.
  3. `FeatureHttpTest.uploadAcceptsExactlyTenMebibytesAndRejectsEmptyOrLargerFiles`로 정확히 10 MiB 허용, 1바이트 초과·0바이트 400을 확인했다. 다른 계정·만료 파일 404는 기존 테스트가 다룬다.
  4. 첨부 화면은 아직 로컬 저장이고 한도 안내 문구가 없다. 안내 문구는 첨부 화면을 서버에 연결하는 IM-10에서 추가한다.
  5. Caddy는 Nginx 앞에서 본문 한도 없이 프록시하므로 고치지 않았다. 로컬 Nginx 이미지가 없어 `nginx -t`는 실행하지 않았다.

## IM-03. 구형·신형 저장 모델 선택

- **연결**: PR-03, REQ-F03, REQ-F05, REQ-F07, DB-02, TS-07.
- **현재**: 완료(2026-11-18). 사용자가 결정을 위임해 A안을 채택했다([09 Q-01](09-잔여-개발-항목-기획서.md#권장-결정)). 1~4·6단계를 구현했고, 5단계(구형 자료 이전)와 7단계(구형 제거)는 PR-21로 넘겼다. 결과는 아래 [처리 결과](#처리-결과)에 있다.

### 기능 설명

일정과 루틴을 서버에 저장하는 방식이 두 가지로 나뉘어 있다. 이 작업은 화면이 쓸 기준 계약을 하나로 정한다. 다른 쪽은 신규 쓰기 중단, 자료 이전, 제거 순서로 정리한다. 통계는 같은 기록을 두 번 세지 않도록 집계 출처를 하나로 맞춘다. IM-07(핵심 기록 흐름 서버 연결)이 이 결정을 기다리고 있다.

### 현재 구조(소스 확인)

| 구분 | 구형 | 신형 |
| --- | --- | --- |
| 일정 | `/api/events`. `EventService`, `events` 테이블, Long ID. 반복은 회차마다 행을 만들고 `seriesId`로 묶는다 | `/api/schedules`. `ScheduleController`, `feature_record`(kind `SCHEDULE`), ULID. 반복 규칙을 저장하고 회차는 `/api/schedules/occurrences`에서 계산한다 |
| 루틴 | `/api/routines`. `RoutineService`, `routine`·`routine_log`, 상태 `done`/`missed` | `/api/routine-records`. `ROUTINE_RECORD`, 날짜별 완료 `ROUTINE_COMPLETION`(키 `{id}@{date}`), `history` 조회 |
| version | 일정·루틴 모두 없다. 마지막 저장이 덮어쓴다 | `feature_record.version`. 수정·삭제할 때 필수다 |
| 시간 블록 | `/api/planner/items`(`planner_item`, PLAN/ACTUAL). PR-01에서 version을 적용했다 | 해당 없음 |
| 실제 기록 | planner ACTUAL | `ACTUAL_SESSION`(`/api/planner/recordings`) |

확인한 사실은 다섯 가지다.

1. 화면은 구형도 신형도 호출하지 않는다. 일정·루틴은 `frontend/src/store/appState.js`의 `localCollection('events')`, `localCollection('routines')`로 브라우저에만 저장된다.
2. 로컬 일정 필드(`title body category startDate endDate startTime endTime color attendeeIds recurrence`)는 신형 `SCHEDULE` 필드(`feature/FeatureType.java`)와 같다. 로컬 루틴 필드(`title category time days goal notify paused recurrence startDate`)도 `ROUTINE_RECORD` 필드와 같다.
3. 중복 집계 지점이 있다. `records/InsightService.stats()`는 계획 시간(`plannedMinutes`)에 구형 일정(`aggregation.range().events()`), 신형 일정 회차(`schedules.occurrences`), planner PLAN을 모두 더한다. 같은 일정을 두 모델에 넣으면 두 번 집계된다. `/api/stat/dashboard`·`/stat/category`·`/stat/plan-actual`·`/stat/focus`, `/api/home/summary`, `ReportController`가 같은 값을 쓴다.
4. `InsightService.summary()`는 구형 루틴(`aggregation.daily`의 `routines`)과 신형 `routineRecords`를 함께 응답한다. 홈에 루틴 목록이 두 벌 나올 수 있다.
5. 통계 서비스를 검증하는 테스트가 없다(`*Insight*Test`, `*Stats*Test` 파일 없음).

### 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 일정·루틴을 신형(`feature_record`)으로 통일 | version·소유권 검사가 이미 있다. 화면 필드와 같아 IM-07 어댑터가 단순하다. 화면 쪽 이전 비용이 없다 | 구형 서버 자료가 있으면 이전해야 한다. JSON 저장이라 기간 조회를 메모리에서 거른다(PR-18 규모 측정 대상) |
| B. 구형 유지, 신형은 새 기능만 | 테이블 컬럼 기반이라 조회 쿼리가 단순하다 | 구형 일정·루틴에 version을 새로 넣어야 한다(Flyway 추가, IM-01과 같은 작업). 화면 필드와 달라 변환 계층이 필요하다. 신형을 제거하거나 중복 제외 규칙을 따로 관리해야 한다 |
| C. 도메인별 선택 | 도메인마다 장점을 고를 수 있다 | 규칙이 복잡해지고 문서화 부담이 크다. 통계가 두 출처를 계속 읽는다 |

v1.2까지 A안의 단점으로 적었던 "회차 물리화 재구현"은 사실과 다르다. 신형은 `ScheduleService.occurrences`와 `RecurrenceRule`로 회차를 이미 계산하고 있어서 다시 구현할 필요가 없다.

### 권장안. A안(사용자 결정 대기)

- 일정과 루틴의 기준 계약은 신형 `/api/schedules`, `/api/routine-records`로 한다.
- `planner_item`(시간 블록)과 `ACTUAL_SESSION`(실제 기록)은 이번 결정에서 바꾸지 않는다. 일정은 "언제 무엇이 있는가", 시간 블록은 "그 시간을 어떻게 쓸 계획인가"를 뜻하므로 서로 다른 기록으로 본다.
- 일정과 시간 블록이 시간대가 겹쳐도 자동으로 병합하지 않는다. 둘을 서로 연결하는 기능은 IM-08에서 다룬다.
- B안이나 C안을 고르면 이 절 아래를 다시 쓴다.

### 구현 단계

## IM-05. BYOK 키 평문 저장 제거

- **연결**: PR-05, REQ-N03, REQ-F18, REQ-F19, IMP-005, BUG-002, TS-08, 08 문서 UF-63·UF-64·Q-09.
- **현재**: 완료(2026-11-19). 아래 계획은 2026-11-18 소스 대조 결과이고, 구현에서 달라진 점은 [처리 결과](#처리-결과im-05)에 있다.

### 기능 설명

설정 > 자동화 > AI 연동 화면에서 "내 API 키 사용(BYOK)"을 고르면, 사용자가 입력한 AI 서비스 키가 브라우저 `localStorage`에 평문으로 저장된다. 같은 기기를 쓰는 다른 사람, 브라우저 확장 프로그램, 화면에 주입된 스크립트(XSS)가 이 키를 읽을 수 있다. 이 작업은 브라우저에서 키를 지우고, 앞으로도 저장되지 않게 한다. 함께, 실제로 연결되지 않은 AI를 "연동됨"으로 보여 주는 표시도 서버 제공 상태 기준으로 바꾼다.

### 현재 구조(소스 확인)

| 위치 | 현재 동작 |
| --- | --- |
| `store/aiSettings.js` | `provider`·`apiKey`·`scope`·`enabled`·`allowSensitive`·`redactNames`·`keepHistory`를 `timeflow.ai.v1` 키로 `localStorage`에 통째로 저장한다(`watch` deep). 주석은 "API 키는 저장하되 이 기기 밖으로 나가지 않는다"이다 |
| `AI_PROVIDERS` | `byok` 설명이 "내 키로 직접 호출해요 · 키는 이 기기에만 저장"이다 |
| `isAiReady()` | `provider`가 `none`이 아니고, BYOK이면 키가 비어 있지 않으면 참이다. 서버 제공 상태를 보지 않는다 |
| `views/settings/SettingsAutomationView.vue` | 비밀번호 입력란으로 키를 받는다(27행 배지, 50~53행 입력과 안내). `isAiReady()`가 참이면 배지가 "AI 연동됨"이 된다 |
| `views/work/WbsView.vue`, `views/work/CareerDocsView.vue` | `isFeatureOn()`이 참이면 "AI 초안 생성이 켜져 있어…", "AI 문장 다듬기가 켜져 있어요"라고 표시한다 |
| 서버 | `/api/integrations/capabilities`의 `ai`는 `available=false`이고, `/api/insight/generate`는 503이다. `/api/settings`는 `apiKey` 같은 이름의 필드를 이미 거부한다 |

확인한 사실은 네 가지다.

1. **저장된 키를 쓰는 코드가 없다.** `apiKey`를 읽는 곳은 `isAiReady()`의 빈 값 검사뿐이다. AI 서비스를 호출하는 프런트 코드도 없다. 키를 지워도 사용자가 잃는 기능이 없고, 저장해 둔 위험만 남아 있다.
2. **"AI 연동됨" 표시가 사실과 다르다.** 기본 제공(서버)을 고르거나 BYOK 키를 아무 값으로 넣기만 해도 배지가 "AI 연동됨"이 된다. 하지만 서버 AI는 미연결이다. 작업 원장의 BUG-002가 이 문제이며, 01 문서에는 REVIEW로 남아 있다. P0-1에서 AI 리포트 화면(`AiInsightView`)은 `CapabilityStatusPanel`로 고쳤지만, 설정 화면과 업무 화면은 아직 로컬 판단을 쓴다.
3. **백업 파일에는 키가 들어가지 않는다.** 수동 백업은 서버 `feature_record` 기준이며 `localStorage`를 읽지 않는다(`features/backup` 확인). 정리 대상은 `localStorage`의 `timeflow.ai.v1` 하나다.
4. **이 설정 파일을 검사하는 테스트가 없다**(`frontend/tests`에서 `aiSettings` 검색 결과 없음).

### 선택지

| 선택지 | 내용 | 판단 |
| --- | --- | --- |
| A. BYOK 저장 제거, 선택지는 "준비 중" | 키를 저장하지 않고 기존 값도 지운다. BYOK는 고를 수 없게 하고 "준비 중"으로 표시한다 | 권장. 키를 쓰는 코드가 없어 잃는 기능이 없다. 새 라이브러리도 필요 없다 |
| B. 메모리에만 보관 | 새로고침하면 사라지는 메모리 값으로만 키를 둔다 | 키를 쓰는 호출 경로가 없어 보관할 이유가 없다. 같은 화면에 주입된 스크립트에는 여전히 노출된다 |
| C. 기기 보안 저장소 | Electron `safeStorage`, Capacitor 보안 저장 플러그인을 쓴다 | 웹에는 해당 기능이 없다. 새 의존성은 라이선스 확인이 필요하다. AI 호출 경로가 생기는 PR-15에서 다시 검토한다 |

상용 AI 경로는 서버 키 관리만 허용한다는 원칙(IMP-005)은 어느 안이든 유지한다.

### 권장안. A안

- `apiKey`는 저장하지도 않고 상태에도 두지 않는다.
- 이미 저장된 키는 앱이 시작할 때 한 번 지운다.
- BYOK는 "준비 중"으로 보이고 고를 수 없다.
- "AI 연동됨" 같은 표시는 서버 `ai` 제공 상태가 `true`일 때만 보인다.

### 화면 표시 규칙

| 서버 `ai` 제공 상태 | 설정 화면 배지 | 업무 화면 안내 |
| --- | --- | --- |
| 확인 중(`null`, 조회 중) | "제공 상태 확인 중" | 표시하지 않음 |
| 조회 실패 | "제공 상태를 확인하지 못했어요" + 다시 시도 | 표시하지 않음 |
| `false`(현재) | "AI 준비 중" | "AI 기능은 준비 중이에요. 지금은 규칙 기반으로 만들어요." |
| `true`이고 사용자가 기능을 켬 | "사용 가능" | 기존 "켜져 있어요" 문구 |

- 사용자가 고른 데이터 범위, 민감 정보 동의, 이름 가리기 설정은 지금처럼 저장하고 화면에서 바꿀 수 있다. 이 값들은 비밀값이 아니고, PR-15에서 그대로 쓴다.
- 배지 색은 기존 `badge`, `badge ok` 클래스만 쓴다. 새 색을 만들지 않는다(DESIGN.md 2장).
- 비로그인 상태는 `useCapabilityStatus`가 돌려주는 안내("로그인 후 제공 상태를 확인할 수 있습니다.")를 그대로 쓴다.

### 구현 단계

1. **테스트를 먼저 작성.** `frontend/tests/ai-settings.test.mjs`(신규)를 만든다. 테스트는 `globalThis.localStorage`를 가짜 저장소로 바꾼 뒤 `aiSettings.js`를 동적 import한다. 지금 코드에서 실패하는 것을 먼저 확인한다(TS-08).
   - 기존 값에 `apiKey`가 있으면, 불러온 직후 저장소와 상태 모두에 `apiKey`가 없다.
   - 설정을 바꿔 저장해도 저장소에 `apiKey`가 없다.
   - 키를 지웠으면 "지웠다"는 결과값이 참이고, 키가 없던 사용자는 거짓이다.
   - 기존 `provider: 'byok'` 값은 `none`으로 바뀌고, 나머지 설정(`scope`, `allowSensitive` 등)은 유지된다.
   - 서버 제공 상태가 `false`나 `null`이면 `isAiReady`와 `isFeatureOn`이 거짓이다.
2. **`aiSettings.js` 수정.**
   - `load()`에서 읽은 객체의 `apiKey`를 지우고, `provider`가 `byok`이면 `none`으로 바꾼 뒤 즉시 다시 저장한다. 지웠는지 여부는 `clearedLegacyKey` 같은 내보내기 값으로 남긴다.
   - 기본값과 `watch` 저장 값에서 `apiKey`를 뺀다. 저장할 때 허용 필드(`provider scope enabled allowSensitive redactNames keepHistory`)만 골라 쓰면, 나중에 누가 필드를 추가해도 비밀값이 섞이지 않는다.
   - `AI_PROVIDERS`의 `byok`에 `disabled: true`를 두고, 설명을 "준비 중 · 키를 브라우저에 저장하지 않아요"로 바꾼다.
   - `isAiReady(available)`와 `isFeatureOn(id, available)`가 서버 제공 상태를 인자로 받는다. `available === true`가 아니면 거짓이다.
   - 잘못된 주석("API 키는 저장하되…")을 지운다.
3. **설정 화면 수정(`SettingsAutomationView.vue`).** `useCapabilityStatus(() => 'ai')`로 제공 상태를 받아 위 표대로 배지를 표시한다. API 키 입력란과 "서버로 보내지 않아요" 안내를 지우고, BYOK 버튼은 `disabled`와 `aria-disabled`를 단다. `clearedLegacyKey`가 참이면 "보안을 위해 이 브라우저에 저장된 API 키를 지웠어요."를 한 번 보여 준다.
4. **업무 화면 수정(`WbsView.vue`, `CareerDocsView.vue`).** 같은 제공 상태를 받아 `isFeatureOn(id, available)`로 바꾼다. 미연결이면 "준비 중"을 안내한다. 경력 문장은 지금처럼 규칙 기반으로 만든다.
5. **검증.** 새 테스트와 기존 Node 테스트 전체, `npm run build:web`을 실행한다. 브라우저에서는 기존 키가 남아 있는 상태로 시작해 개발자 도구의 저장소에서 키가 사라졌는지 확인한다. 결과는 07 문서에 RUN으로 남긴다.

- **소스 대조로 바뀐 전제(2026-11-20)**
  - 생성 API(메모·할 일)는 PR-07 3단계부터 `Idempotency-Key`를 받는다. 수정(PUT)은 받지 않아, 응답을 잃은 수정을 다시 보내면 version이 이미 올라 409가 됐다. 대기열의 "같은 요청 ID 재전송"이 수정에서는 성립하지 않았다.
  - 화면에서 메모를 고치는 곳은 없다(작성 창의 메모는 생성만). 할 일 수정은 상세 화면의 `saveDetail`이고 체크리스트 저장이 함께 있다.
  - 실제 계정 로그아웃은 채팅 화면의 `signOut` 한 곳뿐인데, 그 버튼은 화면에 나오지 않는다. `/chat`은 App이 채팅 화면 대신 안내 문구를 보이고, 떠 있는 채팅 창(`embedded`)은 로그아웃 버튼을 숨긴다. 앱에서 로그아웃할 방법이 없었다.
- **설계**
  - 서버: 메모 `PUT /api/memos/{id}`, 할 일 `PUT /api/tasks/{id}`가 `Idempotency-Key`를 받는다. 같은 키·같은 본문(기록 ID 포함)이면 처음 결과의 기록을 돌려주고, 다른 본문이면 409다. 키는 생성과 같은 `idempotency_key`에 상태 코드 200으로 남는다.
  - 다시 보낸 수정의 응답은 그 기록의 현재 값이다. 그 사이 다른 기기가 고쳤으면 응답 version이 "보낸 version + 1"이 아니므로, 대기열은 이를 충돌로 보고 그 기록의 다음 변경을 멈춘다. 다른 기기의 수정을 조용히 덮지 않기 위해서다.
  - 대기열(2단계): 계정별로 IndexedDB에 둔다. 항목은 요청 ID(멱등 키), 종류, 생성·수정, 대상(서버 ID 또는 오프라인 임시 ID), 기준 version, 본문, 상태(전송 대기·확인 필요)다. 같은 기록의 변경은 넣은 순서대로 보내고, 생성이 끝나면 뒤 항목의 대상을 서버 ID로, 다음 수정의 기준 version을 응답 version으로 바꾼다. 연결 실패·5xx는 멈추고 다음에 다시 보낸다. 409·400·404는 "확인 필요"로 두고 다른 기록은 계속 보낸다. 다른 계정의 항목은 읽지도 보내지도 않는다.
  - 화면(3단계): 메모·할 일 저장이 연결 실패로 끝나면 대기열에 넣고 목록에 "전송 대기"로 보인다. 연결·화면 복귀·로그인 때 자동으로 보낸다. 대기 목록과 충돌 비교, 로그아웃 안내를 둔다.

### 기능 설명

루틴을 하루 쉬거나 휴가 기간 동안 멈춰도 연속 기록이 무너지지 않게 한다. 쉬는 날은 반복 규칙 안의 예외 목록 하나로 표현하고, 일정과 루틴이 같은 구조를 쓴다. 같은 구조를 알림 건너뛰기(PR-09)와 일정의 회차 변경(Q-03)이 이어서 쓴다.

### 현재 구조(소스 확인)

- 회차 계산은 서버 `feature/RecurrenceRule.dates()`와 프런트 `utils/recurrence.mjs`의 `occurrenceDates()` 두 곳이다. 둘 다 예외가 없었다.
- 서버 루틴 회차 판정(`records/ScheduleService`)은 반복 규칙이 none이 아니면 규칙을, none이면 `days`를 쓴다. `paused`면 모든 날짜가 회차에서 빠진다.
- 서버 `history()`는 완료하지 않은 회차를 오늘·미래여도 놓친 날로 세었다. 오늘 아직 하지 않은 루틴이 있으면 연속 기록이 항상 0이었다.
- 루틴 알림을 실제로 보내는 코드는 서버·브라우저 모두 없다. 화면은 알림 설정값만 저장한다.
- 루틴 화면은 로컬 시연 저장이다. `done`·`streak`·`history`(7칸)는 날짜와 무관한 카운터라 날짜별 달성률을 계산할 자료가 없다.

### 설계

| 항목 | 규칙 |
| --- | --- |
| 저장 위치 | 반복 규칙 JSON 안 `exceptions: [{date, action}]`. 새 테이블과 Flyway 변경은 없다 |
| action | `skip`(쉬는 날)과 `override`(회차 하나만 변경). `override`는 일정에서만 받고 `title`·`startTime`·`endTime` 중 원본과 다른 필드만 담는다(하나 이상). 날짜는 바꾸지 않는다. 루틴은 `skip`만 받는다(2단계) |
| 제한 | 반복마다 최대 366개, 한 날짜에 예외 하나. 쉬는 날의 키는 `date`·`action`만이고, 회차 변경은 여기에 `title`·`startTime`·`endTime`을 더한다. 회차 변경의 제목은 공백 제외 1~200자, 시각은 HH:mm, 바뀐 시각을 합친 종료는 시작 이후다(종료 시각은 회차 종료일 기준). 서버 `RecurrenceRule.MAX_EXCEPTIONS`·`OVERRIDE_FIELDS`와 프런트 `MAX_EXCEPTIONS`·`OVERRIDE_FIELDS`가 같은 값이다 |
| 회차 계산 | 쉬는 날은 회차에서 뺀다. 횟수 종료(count)의 회차 수에는 포함해 반복이 뒤로 늘어나지 않는다. 여러 날 일정은 회차 시작일로 판단한다. frequency가 none이어도 쓸 수 있다(요일만 있는 루틴) |
| 루틴 완료 | 쉬는 날의 완료 기록은 400 "쉬는 날로 정한 날짜입니다." 미래 날짜를 쉬는 날로 정하는 것은 허용한다(UT-238) |
| 쉬는 기간 | 별도 구조 없이 기간 안의 예정 회차마다 `skip`을 넣는다. 화면은 오늘 이후 날짜만 받고 기간은 최대 366일이다 |
| 알림 | 발송 기능이 아직 없다. PR-09에서 발송을 만들 때 서버는 `ScheduleService`의 회차 판정과 쉬는 날을, 화면은 `isRoutineToday()`를 써서 쉬는 날을 뺀다 |
| 회차 변경 적용 | 회차 응답(서버 `ScheduleService.occurrences`, 프런트 `eventOccurrences`)에서 그 회차에만 바뀐 필드를 덮고 `overridden: true`를 둔다. 통계 계획 시간도 이 값을 쓴다(2단계) |
| 이 회차부터 | 예외가 아니라 분할이다(`splitRecurrence`). 원래 반복은 `endMode: until`, `until = 회차 전날`로 끝낸다. 새 일정은 회차 날짜에서 시작하고, 횟수 종료면 쉬는 날을 포함한 앞선 회차 수를 뺀 남은 횟수를 쓴다. 회차 날짜 이후의 예외는 새 일정으로 옮긴다. 첫 회차면 전체 수정과 같다(2단계) |
| 화면 | 캘린더의 반복 일정 회차는 `/events?id=…&occurrence=YYYY-MM-DD`로 연결하고, 일정 화면은 그 회차를 "이 회차만 / 이 회차부터 / 전체 반복" 범위로 연다. 목록에서 열면 전체 반복 수정이고, 회차 예외 목록에서 하나씩 되돌린다(저장할 때 반영)(2단계) |

루틴 history 계산(Q-05)은 항목마다 상태를 붙인다.

| status | 뜻 | 달성률 분모(total) | 연속 기록 |
| --- | --- | --- | --- |
| `done` | 완료 | 넣는다 | 1 늘린다 |
| `missed` | 오늘 이전의 미완료 회차 | 넣는다 | 끊는다 |
| `skipped` | 쉬는 날 | 넣지 않는다 | 유지한다 |
| `pending` | 오늘·미래의 미완료 회차 | 넣지 않는다 | 유지한다 |

반복에 없는 날은 항목에 넣지 않는다. 오늘 기준은 `Asia/Seoul`이고, 사용자 시간대(Q-06)는 PR-08에서 바꾼다. 쉬는 날에 이미 완료 로그가 있으면 `completed`는 로그 값을 그대로 보이고 상태는 `skipped`로 계산한다. 화면은 완료한 오늘을 쉬는 날로 정하지 못하게 막는다.

화면에서는 루틴 목록의 각 행에 "쉬는 날" 버튼을 둔다. 대화상자에서 시작일·종료일을 정해 추가하고, 예정된 쉬는 날을 하나씩 해제한다. 오늘이 쉬는 날인 루틴은 오늘 목록·홈·오늘 진행률에서 빠지고 "쉬는 중" 필터에 나온다. 기존 무기한 중지 버튼 "쉬기"는 "쉬는 날"과 헷갈리므로 "중지"로 이름을 바꿨다.
