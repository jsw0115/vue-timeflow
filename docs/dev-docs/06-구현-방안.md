## 작성 규칙

- 항목마다 **현재**, **설계**, **변경 파일**, **위험·대응**, **완료 조건**, **테스트**를 둔다. 테스트는 [07 테스트 시나리오 및 결과서](07-테스트-시나리오-및-결과서.md)의 TS ID로 연결한다.
- 설계가 정해지지 않은 항목은 "결정 필요"와 선택지를 적고, 임의의 값으로 채우지 않는다.
- 구현하면서 설계가 바뀌면 이 문서를 먼저 고치고 변경 이력에 이유를 남긴다. 착수 시점의 상세 메모는 `docs/agent/records/` 작업 폴더에 둔다.

## 공통 원칙

- 사용자는 JWT에서 정한다. 요청 본문의 owner로 다른 사용자를 지정할 수 없다. 다른 계정의 자원은 404로 응답한다.
- 변경 요청은 조회한 version을 요구한다. 오래된 version은 409로 거절하고, 화면은 입력을 보존한 채 다시 조회하도록 안내한다.
- 스키마 변경은 새 번호의 Flyway 파일로만 한다([05 데이터베이스 설계서](05-데이터베이스-설계서.md#스키마-변경-절차)).
- API가 바뀌면 `docs/api/` 명세와 `frontend/scripts/frontend-api-contract.mjs` 계약 검사를 같은 커밋에서 고친다.
- 화면 문구는 [DESIGN.md](../../DESIGN.md) 6장의 담백한 안내형 문장을 따르고, 미완료를 벌점처럼 표현하지 않는다.

## IM-01. 플래너 version 충돌 방지

- **연결**: PR-01, REQ-F07, REQ-N05, DB-01, TS-01~TS-04.
- **현재**: 완료(2026-11-17). 아래 남은 작업을 모두 처리했다.
- **설계**
  - `PlannerItemEntity`에 JPA `@Version Long version`을 둔다. 외부에 보이는 공개 버전은 `version + 1`이다. 그래서 V7 이전에 있던 행(내부 0)도 공개 버전 1부터 시작한다.
  - `POST`는 version을 생략하거나 0이어야 한다. 그 밖의 값은 400이다.
  - `PUT /api/planner/items/{id}`는 본문에, 상태 변경과 `DELETE`는 query `version`에 공개 버전을 받는다. 값이 없거나 1보다 작으면 400, 현재 공개 버전과 다르면 409다.
  - 비교 후 `flush`하므로, 동시에 같은 version으로 들어온 두 요청 중 늦은 쪽은 JPA 낙관적 잠금으로 실패한다.
- **변경 파일**: `planner/PlannerController.java`, `PlannerService.java`, `PlannerItem.java`, `PlannerItemEntity.java`, `PlannerItemQueryRepositoryImpl.java`, `records/RecordActionsController.java`, `db/workspace/V7__planner_item_version.sql`, `db/workspace/README.md`, 테스트 `PlannerPersistenceTest.java`·`PlannerVersionTest.java`, API 명세 4종, `frontend/scripts/frontend-api-contract.mjs`, `frontend/tests/frontend-api-contract.test.mjs`, 기능 명세서.
- **처리 결과**
  1. `PlannerController.java`의 변경 줄 끝 공백을 지웠다.
  2. `PlannerItemQueryRepositoryImpl.java`의 변경은 빈 줄 1개뿐인 기존 사용자 변경이므로 이 작업에서 제외했다.
  3. 동시 요청 409는 `PlannerVersionTest.concurrentSnapshotsCannotBothCommit`으로 확인했다. 예외 처리기는 고치지 않았다.
  4. 저장된 `openapi.json`의 `PlannerItem`·`PlannerItemUpdate` `required`에 `version`이 중복되어 계약 검사가 실패했다. 생성기로 다시 만들어 중복을 없앴다.
  5. 검증 결과는 07의 RUN-13~RUN-18에 기록했다.
- **위험·대응**: version 없이 요청하는 기존 클라이언트는 400을 받는다. 2026-11-17 정적 확인 기준으로 프런트 화면에서 `/api/planner/items`를 호출하는 곳은 없다(관리자 시연 로그 문자열만 있음). 그래서 화면 쪽 영향은 없지만, 운영에 배포할 때는 클라이언트와 DB를 함께 배포한다.
- **완료 조건**: TS-01~TS-04가 PASS이고, 공백 검사를 통과하고, 의미 단위로 커밋되어 있다.

## IM-02. 업로드 크기 한도 정렬

- **연결**: PR-02, REQ-F14, IMP-004, TS-05, TS-06.
- **현재**: 파일 한도는 세 곳에서 서로 다르게 정해져 있다.

| 위치 | 값 |
| --- | --- |
| `records/AttachmentController.java` | 파일 1바이트~10 MiB(`MAX_BYTES`) |
| `application.yml` | `max-file-size: 10MB`, `max-request-size: 11MB` |
| `infra/deploy/nginx.conf` | `client_max_body_size 10m` |

- **설계**: 허용 파일 크기는 10 MiB로 유지한다. multipart 경계와 헤더가 붙을 여유를 두기 위해 프록시를 요청 한도와 같은 `11m`로 올린다. Caddy 경로는 본문 크기 제한이 설정되어 있지 않으므로 앱 한도가 최종 기준이 된다. 화면 안내 문구도 "10 MiB까지"로 맞춘다.
- **변경 파일**: `infra/deploy/nginx.conf`, 첨부 안내 화면 문구(해당 화면을 찾아 수정), [연계 명세](../api/frontend-backend-2026-10-10/integrations.md)나 배포 문서에 한도가 적혀 있으면 그 부분.
- **위험·대응**: 프록시 한도를 올리면 큰 요청을 받는 비용이 조금 늘어난다. 앱이 10 MiB 초과를 400으로 거절하므로 저장 위험은 없다.
- **완료 조건**: 세 위치가 같은 기준을 가리키고, TS-05·TS-06이 PASS다. 실제 프록시 경계 시험은 서버 환경이 있을 때 PR-13에서 한다.
- **처리 결과(2026-11-17)**
  1. `infra/deploy/nginx.conf`를 `client_max_body_size 11m`로 바꾸고 이유를 주석으로 남겼다.
  2. 세 위치의 정렬을 `frontend/tests/upload-limits.test.mjs`로 고정했다. 수정 전 실행에서 Nginx 검사가 실패하는 것을 먼저 확인했다.
  3. `FeatureHttpTest.uploadAcceptsExactlyTenMebibytesAndRejectsEmptyOrLargerFiles`로 정확히 10 MiB 허용, 1바이트 초과·0바이트 400을 확인했다. 다른 계정·만료 파일 404는 기존 테스트가 다룬다.
  4. 첨부 화면은 아직 로컬 저장이고 한도 안내 문구가 없다. 안내 문구는 첨부 화면을 서버에 연결하는 IM-10에서 추가한다.
  5. Caddy는 Nginx 앞에서 본문 한도 없이 프록시하므로 고치지 않았다. 로컬 Nginx 이미지가 없어 `nginx -t`는 실행하지 않았다.

## IM-03. 구형·신형 저장 모델 선택

- **연결**: PR-03, REQ-F03, REQ-F05, REQ-F07, DB-02, TS-07.
- **현재**: 대기. 아래 계획은 2026-11-18 소스 대조 결과다. 권장안을 채택할지는 사용자가 결정한다.

### 기능 설명

일정과 루틴을 서버에 저장하는 방식이 두 가지로 나뉘어 있다. 이 작업은 화면이 쓸 기준 계약을 하나로 정한다. 다른 쪽은 신규 쓰기 중단, 자료 이전, 제거 순서로 정리한다. 통계는 같은 기록을 두 번 세지 않도록 집계 출처를 하나로 맞춘다. IM-07(핵심 기록 흐름 서버 연결)이 이 결정을 기다리고 있다.

### 현재 구조(소스 확인)

| 구분 | 구형 | 신형 |
| --- | --- | --- |
| 일정 | `/api/events`. `EventService`, `events` 테이블, Long ID. 반복은 회차마다 행을 만들고 `seriesId`로 묶는다 | `/api/schedules`. `ScheduleController`, `feature_record`(kind `SCHEDULE`), ULID. 반복 규칙을 저장하고 회차는 `/api/schedules/occurrences`에서 계산한다 |
| 루틴 | `/api/routines`. `RoutineService`, `routine`·`routine_log`, 상태 `done`/`missed` | `/api/routine-records`. `ROUTINE_RECORD`, 날짜별 완료 `ROUTINE_COMPLETION`(키 `{id}@{date}`), `history` 조회 |
| version | 일정·루틴 모두 없다. 마지막 저장이 덮어쓴다 | `feature_record.version`. 수정·삭제할 때 필수다 |
| 시간 블록 | `/api/planner/items`(`planner_item`, PLAN/ACTUAL). PR-01에서 version을 적용했다 | 해당 없음 |
| 실제 기록 | planner ACTUAL | `ACTUAL_SESSION`(`/api/planner/recordings`) |

확인한 사실은 다섯 가지다.

1. 화면은 구형도 신형도 호출하지 않는다. 일정·루틴은 `frontend/src/store/appState.js`의 `localCollection('events')`, `localCollection('routines')`로 브라우저에만 저장된다.
2. 로컬 일정 필드(`title body category startDate endDate startTime endTime color attendeeIds recurrence`)는 신형 `SCHEDULE` 필드(`feature/FeatureType.java`)와 같다. 로컬 루틴 필드(`title category time days goal notify paused recurrence startDate`)도 `ROUTINE_RECORD` 필드와 같다.
3. 중복 집계 지점이 있다. `records/InsightService.stats()`는 계획 시간(`plannedMinutes`)에 구형 일정(`aggregation.range().events()`), 신형 일정 회차(`schedules.occurrences`), planner PLAN을 모두 더한다. 같은 일정을 두 모델에 넣으면 두 번 집계된다. `/api/stat/dashboard`·`/stat/category`·`/stat/plan-actual`·`/stat/focus`, `/api/home/summary`, `ReportController`가 같은 값을 쓴다.
4. `InsightService.summary()`는 구형 루틴(`aggregation.daily`의 `routines`)과 신형 `routineRecords`를 함께 응답한다. 홈에 루틴 목록이 두 벌 나올 수 있다.
5. 통계 서비스를 검증하는 테스트가 없다(`*Insight*Test`, `*Stats*Test` 파일 없음).

### 선택지

| 선택지 | 장점 | 단점 |
| --- | --- | --- |
| A. 일정·루틴을 신형(`feature_record`)으로 통일 | version·소유권 검사가 이미 있다. 화면 필드와 같아 IM-07 어댑터가 단순하다. 화면 쪽 이전 비용이 없다 | 구형 서버 자료가 있으면 이전해야 한다. JSON 저장이라 기간 조회를 메모리에서 거른다(PR-18 규모 측정 대상) |
| B. 구형 유지, 신형은 새 기능만 | 테이블 컬럼 기반이라 조회 쿼리가 단순하다 | 구형 일정·루틴에 version을 새로 넣어야 한다(Flyway 추가, IM-01과 같은 작업). 화면 필드와 달라 변환 계층이 필요하다. 신형을 제거하거나 중복 제외 규칙을 따로 관리해야 한다 |
| C. 도메인별 선택 | 도메인마다 장점을 고를 수 있다 | 규칙이 복잡해지고 문서화 부담이 크다. 통계가 두 출처를 계속 읽는다 |

v1.2까지 A안의 단점으로 적었던 "회차 물리화 재구현"은 사실과 다르다. 신형은 `ScheduleService.occurrences`와 `RecurrenceRule`로 회차를 이미 계산하고 있어서 다시 구현할 필요가 없다.

### 권장안. A안(사용자 결정 대기)

- 일정과 루틴의 기준 계약은 신형 `/api/schedules`, `/api/routine-records`로 한다.
- `planner_item`(시간 블록)과 `ACTUAL_SESSION`(실제 기록)은 이번 결정에서 바꾸지 않는다. 일정은 "언제 무엇이 있는가", 시간 블록은 "그 시간을 어떻게 쓸 계획인가"를 뜻하므로 서로 다른 기록으로 본다.
- 일정과 시간 블록이 시간대가 겹쳐도 자동으로 병합하지 않는다. 둘을 서로 연결하는 기능은 IM-08에서 다룬다.
- B안이나 C안을 고르면 이 절 아래를 다시 쓴다.

### 통계 집계 규칙(A안 기준)

| --- | --- | --- |

### 구현 단계

1. **결정 기록.** 사용자가 고른 안과 근거를 이 절과 `docs/agent/records/` 작업 폴더의 context-notes에 남긴다.
   - 확인: 01·05 문서의 PR-03·DB-02 상태가 바뀌어 있다.
2. **통계 회귀 테스트를 먼저 작성.** `InsightServiceTest`(신규)에 구형 일정, 신형 일정, PLAN 블록을 같은 시간대로 넣고 `stats()`를 호출한다. 수정 전에는 구형까지 더해진 값이 나와 실패하는 것을 확인한다(TS-07).
3. **집계 출처 정리.** `InsightService.stats()`에서 `aggregation.range().events()` 합산을 뺀다. `summary()`의 구형 루틴 목록을 신형 기준으로 바꾼다. 할 일(`view.tasks()`) 완료 수는 이번 범위가 아니므로 그대로 둔다.
   - 확인: 2단계 테스트 PASS, 백엔드 전체 테스트 PASS.
4. **구형 쓰기 중단 표시.** `EventController`, `RoutineController`에 `@Deprecated`를 붙이고 응답에 `Deprecation: true` 헤더를 넣는다. 읽기와 쓰기는 이전이 끝날 때까지 유지한다. 바로 막으면 기존 API 클라이언트와 테스트가 깨지기 때문이다.
   - 확인: `docs/api/` 명세에 폐지 예정이 표시되고, `frontend/scripts/frontend-api-contract.mjs` 계약 검사가 통과한다.
5. **구형 서버 자료 이전 도구(조건부).** 운영 DB에 구형 자료가 있는지는 저장소만으로 알 수 없다. 자료가 있으면 사용자별로 승인받아 이전한다.
   - 멱등 키는 `legacy:event:{seriesId 또는 id}`, `legacy:routine:{id}`다. 이 값을 신형 `record_id`로 쓰므로 두 번 실행해도 `FeatureStore.create`가 중복을 거절한다.
   - 구형 반복 일정은 `seriesId`로 묶인 회차를 반복 규칙 하나로 되돌린다. 회차마다 다르게 수정된 행은 단일 일정으로 따로 옮긴다.
   - `routine_log`의 `done`은 `ROUTINE_COMPLETION`의 `completed: true`로, `missed`는 `completed: false`로 옮긴다.
   - 확인: 같은 자료로 두 번 이전해도 건수가 같고, 원본 행 수와 이전 행 수가 맞는다.
6. **문서 반영.** 04 문서에 화면별 계약 표, 05 문서에 DB-02 결정, 기능 명세에 통계 규칙, 07 문서에 TS-07 절차와 결과를 적는다.
7. **구형 제거(별도 작업).** 이전이 끝나고 한 릴리스 동안 구형 호출이 없는 것을 확인한 뒤, 구형 컨트롤러·서비스를 지우고 새 번호의 Flyway로 테이블을 정리한다. 이 작업은 PR-03 완료 조건에 넣지 않고 새 PR 항목으로 등록한다.

## IM-05. BYOK 키 평문 저장 제거

- **연결**: PR-05, REQ-N03, REQ-F19, IMP-005, TS-08.
- **현재**: `frontend/src/store/aiSettings.js`가 `apiKey`를 포함한 설정을 `localStorage`에 JSON으로 저장한다. 안내 문구는 "키는 이 기기에만 저장"이다.
- **설계**
  1. 저장할 때 `apiKey`를 빼고 저장한다. 읽을 때 기존 값에 `apiKey`가 있으면 지우고 다시 저장한다.

- **위험·대응**: 기존 사용자의 키가 지워진다. 화면에 "보안을 위해 저장된 키를 지웠습니다" 안내를 한 번 보여 준다.
- **완료 조건**: 설정 저장·복원 후 localStorage에 `apiKey`가 없다는 테스트 TS-08이 PASS다.
