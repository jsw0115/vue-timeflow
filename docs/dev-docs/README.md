## 기준 원문과의 관계

이 폴더는 개발 진행용 작업본이다. 주제별 기준 원문은 [문서 기준 규칙](../project/document-register.md)에 정한 위치를 유지한다. 내용이 충돌하면 실제 소스·설정이 가장 우선이고, 다음이 아래 기준 원문이며, 이 폴더는 그 다음이다. 충돌을 발견하면 원문과 이 폴더를 같은 커밋에서 함께 고친다.

| 이 폴더 문서 | 기준 원문 | 이 폴더에만 두는 내용 |
| --- | --- | --- |
| 01 개발 우선순위 | [작업 원장](../releases/backlog.md), [WBS](../planning/wbs.md), [우선 구현 계획](../agent/records/2026-11-16-검토보고서-우선구현/plan.md) | 원장·WBS·검토보고서·구매자 의견을 합친 단일 처리 순서 |
| 02 요구사항 명세서 | [요구사항](../planning/requirements.md) | 요구별 남은 작업과 구매자 의견(CF) 연결 |
| 03 기능개발 목록서 | [기능 명세](../handbook/source/05-기능-명세서.md) | 서버·화면·검증 층별 진행 상태 |
| 04 메뉴기능 목록서 | [화면 경로 목록](../product/screen-catalog.md), [화면 명세](../product/screen-design.md) | 메뉴 그룹 구조와 메뉴별 저장 방식 |
| 05 데이터베이스 설계서 | [현재 DB 정의](../database/current-database.md), [DB 환경·이력](../database/environment.md) | 마이그레이션 순서, 예정 변경, 미해결 설계 쟁점 |
| 06 구현 방안 | [모듈 설계](../architecture/modules-and-interfaces.md), [API 기준](../api/README.md) | 우선순위 항목별 구현 설계 |

구매자 의견 36개(CF-001~CF-036)의 실시간 상태 원본은 [Excel 통합관리대장](../../outputs/timebar-diary-management-20261115/Timebar_Diary_Management.xlsx)이다. 이 폴더는 CF ID를 참조만 하고 상태를 따로 확정하지 않는다.

요구 ID(REQ), 테스트 ID(TC), 작업 ID(WBS)는 기준 원문에서만 새로 만든다. 이 폴더에서 새로 쓰는 ID는 우선순위(PR), 기능(FD), 메뉴(MN), 구현 방안(IM), 시나리오(TS), 실행 결과(RUN)뿐이다. 한 번 쓴 ID는 삭제 후 재사용하지 않는다.

## 버전 관리 규칙

- 모든 문서는 첫 줄 아래에 `문서 버전`, `작성일`, `수정일`을 두고, 끝에 `변경 이력` 표를 둔다.
- 버전은 `v주.부` 형식이다. 항목 추가·상태 변경·결과 추가는 부 번호를 올린다(v1.0 → v1.1). 문서 구조나 ID 체계를 바꾸면 주 번호를 올린다(v1.x → v2.0). 오탈자 수정은 버전을 올리지 않고 변경 이력에만 남긴다.
- 문서 버전은 제품 버전(현재 0.1.0)과 별개다. 제품 버전과 릴리스는 [릴리스 원장](../releases/README.md)에서만 확정한다.
- 변경은 Git 커밋으로 남긴다. 기능 변경과 함께 문서를 고치면 같은 커밋에 넣고, 문서만 고치면 `docs(dev-docs): ...` 형식으로 커밋한다.
- 과거 상태를 지우지 않는다. 상태가 바뀌면 표의 값을 갱신하고, 바뀐 이유를 변경 이력에 적는다. 테스트 결과는 덮어쓰지 않고 새 행으로 추가한다.

## 갱신 절차

1. 작업을 시작할 때 [01 개발 우선순위](01-개발-우선순위.md)에서 항목을 고르고, `python scripts/start_task.py --task 작업명`으로 작업 기록을 만든다.
2. 구현 전에 [06 구현 방안](06-구현-방안.md)의 해당 IM 항목을 작성하거나 고친다.
3. 구현하면서 바뀐 API·DB·메뉴를 기준 원문과 02·03·04·05 문서에 반영한다.
4. 검증을 실행하고 명령·종료 코드·결과를 [07 테스트 시나리오 및 결과서](07-테스트-시나리오-및-결과서.md)의 결과 기록에 추가한다.
5. 01 문서의 상태를 바꾸고, 바꾼 문서의 버전과 변경 이력을 갱신한 뒤 커밋한다.

## 상태·결과 표기

| 구분 | 값 | 의미 |
| --- | --- | --- |
| 작업 상태 | 대기 | 착수 전 |
| 작업 상태 | 진행 | 코드나 문서를 수정하는 중. 커밋되지 않은 변경이 있을 수 있다 |
| 작업 상태 | 검증 | 구현은 끝났고 검증 결과를 기록하는 중 |
| 작업 상태 | 완료 | 수용 기준을 충족하고, 실행 증빙과 커밋이 있다 |
| 작업 상태 | 보류 | 외부 계약·승인·결정 대기. 재개 조건을 함께 적는다 |
| 검증 결과 | PASS / FAIL / REVIEW / NOT_RUN / N/A | 실행 증빙이 있을 때만 PASS를 쓴다 |

소스 정적 확인만으로 상태를 정한 항목은 "정적 확인"이라고 적는다. 로컬 시연 저장 화면을 계정별 서버 저장이 끝난 기능으로 표시하지 않는다. 외부 제공자(AI·음성·결제·외부 캘린더)는 연결 전까지 503 경계 상태로 표시한다.
