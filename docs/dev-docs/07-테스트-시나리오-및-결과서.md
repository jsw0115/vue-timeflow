## 기록 규칙

- 결과는 `PASS / FAIL / REVIEW / NOT_RUN / N/A`로 적는다. PASS는 명령·종료 코드·증빙이 있을 때만 쓴다.
- 결과 기록은 덮어쓰지 않고 아래에 새 RUN 행을 추가한다. 같은 시나리오를 다시 실행하면 새 RUN ID를 쓴다.
- H2·MockMvc·모의 응답 결과를 실제 MySQL·Redis·SSE·외부 제공자의 성공으로 적지 않는다. 환경 열에 실제 실행 환경을 적는다.
- 로컬 경로·계정·비밀값·사용자 기록 원문은 결과서에 적지 않는다.
- 시나리오가 실패하면 원인과 후속 RUN ID를 비고에 남기고, 결함은 [작업 원장](../releases/backlog.md)에 BUG로 등록한다.

## 시나리오 상세

### TS-01. 오래된 version 거절

- **사전 조건**: 사용자 A가 플래너 항목을 만들고 조회해 공개 버전 1을 받는다. 한 번 수정해 공개 버전 2가 된다.
- **절차**: version 1로 `PUT`, `PATCH`(상태 변경), `DELETE`를 각각 보낸다.
- **기대 결과**: 세 요청 모두 409이고, 저장된 항목은 버전 2 내용 그대로다.
- **자동화**: `PlannerVersionTest`.

### TS-02. 입력·소유권 경계

- **절차**: version 없이, version 0, version -1로 변경 요청을 보낸다. 사용자 B의 토큰으로 A의 항목을 변경한다. `POST`에 version 1을 넣는다.
- **기대 결과**: version 누락·0·음수는 400, `POST`의 version 1도 400, B의 요청은 404이고 A의 데이터는 바뀌지 않는다.

### TS-03. 동시 쓰기

- **절차**: 같은 공개 버전으로 두 수정 요청을 동시에 보낸다.
- **기대 결과**: 한 건은 200, 다른 한 건은 409다. 최종 버전은 1만큼만 증가한다.

### TS-04. 계약·빌드·공백

- **절차**: `node scripts/frontend-api-contract.mjs --check`, `npm run build:web`, `git diff --check`를 실행한다.
- **기대 결과**: 모두 종료 0. 단, 작업 전부터 있던 사용자 변경(`Modal.vue`)의 공백 경고는 별도로 표시한다.

### TS-05. 업로드 경계

- **절차**: 10 MiB 파일, 10 MiB + 1바이트 파일, 0바이트 파일을 업로드한다. 가능하면 Nginx 경유와 앱 직접 호출을 모두 한다.
- **기대 결과**: 10 MiB는 성공, 초과와 0바이트는 400이다. 프록시에서 413이 나오면 FAIL이다.

### TS-06. 파일 권한

- **절차**: 다른 계정 파일 다운로드, 만료된 파일 다운로드, 공유 철회 후 다운로드를 한다.
- **기대 결과**: 모두 404이고 바이트가 노출되지 않는다.

### TS-07. 통계 중복 제외

- **사전 조건**: IM-03 결정. 2026-11-18 A안으로 결정했다.
- **절차**: 같은 시간대(2026-11-18 10:00~11:00)에 구형 일정 60분, 신형 일정 60분, 플래너 계획 블록 30분을 넣고 하루 통계를 조회한다. 홈 요약도 구형·신형 루틴을 하나씩 두고 조회한다.
- **기대 결과**: 계획 시간 90분(신형 60 + 계획 블록 30). 구형 일정은 빠지고, 일정과 계획 블록은 시간이 겹쳐도 각각 센다. 홈 요약의 루틴은 신형 1개만 나온다.
- **자동 테스트**: `backend`의 `kr.timebar.diary.records.InsightServiceTest`.

### TS-08. BYOK 키 미저장

- **절차**: BYOK 선택 후 키를 입력하고 저장, 새로고침, 기존 키가 남아 있는 localStorage 값으로 시작한다.
- **기대 결과**: 저장 직후와 이전 값을 읽은 뒤 모두 localStorage에 `apiKey`가 없다.
- **자동 테스트**: `frontend/tests/ai-settings.test.mjs`(09 UT-110~UT-117). 서버 `ai`가 `false`일 때 설정·WBS·경력 화면에 "연동됨"·"켜져 있어요"가 없는지(BUG-002 회귀)도 함께 본다.
- **브라우저 점검**: Vite 개발 서버와 헤드리스 Chrome에서 CDP `Fetch`로 `/api/integrations/capabilities` 응답만 바꿔 `false`·실패·`true`를 확인한다. 가로채기 패턴은 `http://127.0.0.1:5173/api/*`처럼 API 경로로 좁힌다. `*/api/*`는 앱 모듈 `features/chat/api/chatApi.js`까지 잡아 앱이 뜨지 않는다(RUN-60).

### TS-09. 지원 Node 환경

- **절차**: 지원 Node 버전에서 `node -v`, `npm ci`, Node 테스트, `npm run build:web`을 실행한다.
- **기대 결과**: 버전이 `>=22.12.0`이고 모든 명령이 종료 0이다.

### TS-10~TS-12. 서버 연결 공통

- **TS-10**: 기록을 저장하고 로그아웃한 뒤 다시 로그인하거나 다른 브라우저로 로그인한다. 같은 기록이 보여야 한다.
- **TS-11**: A로 기록한 뒤 B로 전환한다. A의 기록이 화면·메모리·localStorage 어디에도 보이지 않아야 한다.
- **TS-12**: 서버를 끊은 상태로 저장하고, 오래된 version으로 저장한다. 입력이 남아 있고 다시 시도할 수 있어야 한다.

### TS-18. 쉬는 날 예외

- **사전 조건**: IM-14 1단계. 기준 날짜는 테스트 안에서 고정한다(서비스의 `history(..., today)`).
- **절차**: 월~금 루틴에서 수요일을 쉬는 날로 두고 나머지 4일을 완료한다(UT-236). 매일 루틴에 11-20~11-22를 쉬는 날로 두고 11-19~11-23을 조회한다(UT-237). 내일 완료 기록과 내일 쉬는 날 추가를 시도한다(UT-238). 오늘 미완료 회차가 있는 구간을 조회한다. 예외 366·367개, 같은 날짜, `override`, 잘못된 날짜를 넣는다. 횟수 종료 일정에서 한 회차를 쉰다. 화면에서 오늘을 쉬는 날로 정한 루틴을 둔다.
- **기대 결과**: 달성 4/4·연속 4. 쉬는 기간은 `skipped`, 앞뒤 회차는 그대로다. 내일 완료는 400, 내일 쉬는 날 추가는 성공한다. 오늘·미래 미완료는 `pending`이고 분모와 연속 기록에 영향이 없다. 366개만 허용하고 나머지는 400이다. 횟수 종료 일정은 쉰 회차만 빠지고 뒤로 늘어나지 않는다. 오늘 쉬는 루틴은 홈과 오늘 목록에서 빠진다.
- **자동 테스트**: `backend`의 `kr.timebar.diary.records.RecurrenceExceptionTest`, `frontend/tests/recurrence-exceptions.test.mjs`, `frontend/tests/writing-flows.test.mjs`의 UF-134 테스트.

### TS-19. 디자인 토큰 계약

### TS-22. 일정 회차 변경·분할

### TS-23. 할 일 version 계약과 공통 저장 어댑터

- **사전 조건**: PR-07 1단계. 서버는 H2와 MockMvc, 프런트는 가짜 요청으로 확인한다. 화면은 바꾸지 않았다.
- **절차**: 할 일을 만들고 수정·상태 변경·삭제를 오래된 version과 최신 version으로 보낸다. version 누락·0·음수, 생성 version 9, 다른 계정의 수정·상태 변경·삭제를 보낸다. 같은 version으로 동시에 두 번 수정한다. 기존 행이 있는 표에 V8을 적용한다. 프런트 어댑터로 생성→수정→상태 변경→삭제를 하며 보낸 요청을 본다(UT-120). 409·400·404·연결 실패를 만든다. 목록 조회를 늦춘 채 계정을 바꾸고, 저장 중에 계정을 바꾼다(UT-127). 204 삭제 응답을 받는다.
- **기대 결과**: 생성 1, 수정마다 1씩 오른다. 오래된 version은 409이고 최신 내용이 남는다. 누락·1 미만은 400, 생성은 생략이나 0만 허용, 다른 계정은 404다. 동시 수정은 하나만 성공한다. 기존 행은 version 0(공개 1)이고 NULL이 될 수 없다. 어댑터는 응답 version을 다음 요청에 보내고, 409이면 최신 서버 값을 함께 준다. 이전 계정의 응답은 목록에 들어오지 않는다. 204는 성공이다.
- **자동 테스트**: `backend`의 `kr.timebar.diary.task.TaskVersionTest`, `TaskMutationLockTest`, `frontend/tests/record-client.test.mjs`.

### TS-24. 할 일 화면 서버 연결

- **사전 조건**: PR-07 2단계. Node는 가짜 요청, 브라우저는 격리 MySQL·Redis와 chat-local 백엔드, Vite 개발 서버, 헤드리스 Chrome 두 프로필로 확인한다.
- **절차**: 로그아웃 상태로 할 일을 만든다(UT-131). 로그인해 작성 창에서 체크리스트가 있는 할 일을 만들고, 목록에서 완료를 누른다. 상세에서 응답을 2초 늦춰 저장하고(UT-122), 요청을 끊어 저장한 뒤 다시 시도하고(UT-123), 400 응답을 받는다. 두 탭에서 같은 할 일을 연 뒤 차례로 저장하고(UT-125) 비교 화면에서 두 선택지를 고른다(UT-126). 다른 프로필과 다른 계정으로 로그인한다. 체크리스트 일부 요청이 실패한 뒤 다시 저장한다.
- **기대 결과**: 로그아웃 상태는 이 브라우저에 저장하고 서버를 부르지 않으며 "이 브라우저에만 저장돼요"가 보인다. 로그인 상태는 서버 성공 응답 뒤에만 목록·완료가 바뀐다. 요청 중에는 "저장하는 중"만, 성공 뒤에 "저장했어요"가 보인다. 실패하면 입력이 남고 다시 시도할 수 있다. 400 메시지는 관련 입력란 옆에 보인다. 충돌이면 두 내용이 나란히 보이고 고르기 전에는 서버 값이 그대로다. 다시 저장은 최신 version으로 보낸다. 체크리스트는 바뀐 항목만 보내고 이어서 저장할 때 할 일이나 항목을 다시 만들지 않는다. 다른 프로필에서는 같은 할 일이 보이고, 다른 계정에서는 보이지 않는다.
- **자동 테스트**: `frontend/tests/task-store.test.mjs`. 브라우저 점검은 작업 폴더 밖 임시 스크립트로 했다(RUN-72).

### TS-25. 로컬 자료 이전과 멱등 키

"나중에"를 고르고 새로고침, 로그아웃 후 다시 로그인한다(UT-130). 두 번째 이전 요청을 서버에 저장한 뒤 브라우저에는 실패로 돌려주고 다시 시도한다(UT-129).
- **기대 결과**: 같은 키·같은 내용은 처음 기록을 돌려주고 하나만 있다. 다른 내용은 409, 잘못된 키는 400, 다른 계정은 별도 기록, 지운 기록은 404(다시 만들지 않음), 동시 요청은 하나만 생긴다. 7일 지난 키만 지운다. 이전 안내에는 사용자 할 일 2건만 보이고, "나중에"는 같은 로그인 동안만 기억한다. 다시 이전해도 서버에는 2건이고 완료 상태와 체크리스트가 함께 옮겨지며, 옮긴 할 일은 이 브라우저 목록에서 빠진다.
- **자동 테스트**: `backend`의 `kr.timebar.diary.feature.IdempotencyHttpTest`, `TaskVersionTest`의 멱등 키 테스트, `frontend/tests/local-migration.test.mjs`. 브라우저 점검은 작업 폴더 밖 임시 스크립트로 했다(RUN-77).
