## 기록 규칙

- 결과는 `PASS / FAIL / REVIEW / NOT_RUN / N/A`로 적는다. PASS는 명령·종료 코드·증빙이 있을 때만 쓴다.
- 결과 기록은 덮어쓰지 않고 아래에 새 RUN 행을 추가한다. 같은 시나리오를 다시 실행하면 새 RUN ID를 쓴다.
- H2·MockMvc·모의 응답 결과를 실제 MySQL·Redis·SSE·외부 제공자의 성공으로 적지 않는다. 환경 열에 실제 실행 환경을 적는다.
- 로컬 경로·계정·비밀값·사용자 기록 원문은 결과서에 적지 않는다.
- 시나리오가 실패하면 원인과 후속 RUN ID를 비고에 남기고, 결함은 [작업 원장](../releases/backlog.md)에 BUG로 등록한다.

## 실행 명령

```powershell
# 백엔드 (backend)
.\gradlew.bat test --console=plain
.\gradlew.bat test --console=plain --tests "kr.timebar.diary.planner.*"
# 프런트엔드 (frontend)
$testFiles = (Get-ChildItem tests/*.test.mjs).FullName; node --test --test-concurrency=1 $testFiles
node scripts/frontend-api-contract.mjs --check
node scripts/api-inventory.mjs --check
npm run build:web
# 가로 넘침 점검: npm run dev 후 아래 주소를 열어 결과 JSON을 본다(w는 320·375·768·1024 등)
#   http://127.0.0.1:5173/scripts/dev/overflow-sweep.html?w=320
#   헤드리스 예: chrome --headless=new --virtual-time-budget=400000 --dump-dom "<위 주소>"
#   --window-size로 좁힌 캡처는 창 최소 폭(약 526px) 때문에 판단에 쓰지 않는다
# 문서·키트 (루트)
python scripts/docs/verify_documentation.py
python -B scripts/verify_agent_kit.py
git diff --check
```

## 시나리오 상세

### TS-01. 오래된 version 거절

- **사전 조건**: 사용자 A가 플래너 항목을 만들고 조회해 공개 버전 1을 받는다. 한 번 수정해 공개 버전 2가 된다.
- **절차**: version 1로 `PUT`, `PATCH`(상태 변경), `DELETE`를 각각 보낸다.
- **기대 결과**: 세 요청 모두 409이고, 저장된 항목은 버전 2 내용 그대로다.
- **자동화**: `PlannerVersionTest`.

### TS-02. 입력·소유권 경계

- **절차**: version 없이, version 0, version -1로 변경 요청을 보낸다. 사용자 B의 토큰으로 A의 항목을 변경한다. `POST`에 version 1을 넣는다.
- **기대 결과**: version 누락·0·음수는 400, `POST`의 version 1도 400, B의 요청은 404이고 A의 데이터는 바뀌지 않는다.

### TS-03. 동시 쓰기

- **절차**: 같은 공개 버전으로 두 수정 요청을 동시에 보낸다.
- **기대 결과**: 한 건은 200, 다른 한 건은 409다. 최종 버전은 1만큼만 증가한다.

### TS-04. 계약·빌드·공백

- **절차**: `node scripts/frontend-api-contract.mjs --check`, `npm run build:web`, `git diff --check`를 실행한다.
- **기대 결과**: 모두 종료 0. 단, 작업 전부터 있던 사용자 변경(`Modal.vue`)의 공백 경고는 별도로 표시한다.

### TS-05. 업로드 경계

- **절차**: 10 MiB 파일, 10 MiB + 1바이트 파일, 0바이트 파일을 업로드한다. 가능하면 Nginx 경유와 앱 직접 호출을 모두 한다.
