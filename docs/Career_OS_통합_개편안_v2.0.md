# Timebar Diary 통합 커리어 관리 플랫폼 개편안

- 문서 버전: v2.0 제안안
- 작성 기준일: 2026-11-20
- 대상 저장소: `vue-timeflow`
- 문서 성격: 기존 서비스 개요·요구사항·메뉴·기능개발 문서를 개편하기 위한 통합 제안서
- 적용 원칙: 기존 기능·ID·라우트·구현 상태를 보존하고, 새 커리어 기능은 별도 요구로 추가한다.

> **중요한 상태 구분**  
> 이 문서는 제품 방향과 추가 개발 범위를 제안한다. 기존 문서에 기록된 서버·화면·검증 상태를 새로 확인한 것은 아니며, 이 문서만으로 신규 기능이 구현되었다고 간주하지 않는다. 신규 기능의 상태는 요구사항 원문과 기능개발 목록서에 등록하기 전까지 `제안/설계`로 취급한다.

## 1. 서비스 개요

### 1.1 서비스 정의

Timebar Diary(저장소 `vue-timeflow`)를 **취업 준비부터 직장생활, 프로젝트 수행, 경력 축적과 이직 준비까지 개인의 경험을 지속적으로 기록하고 활용하는 통합 커리어 관리 플랫폼**으로 확장한다.

이 서비스는 이력서 작성기나 채용공고 모음 서비스에 한정되지 않는다. 사용자가 일상·학습·회사 업무·아르바이트·인턴·개인 프로젝트·커뮤니티 활동에서 수행한 일을 한곳에 축적하고, 필요한 경험을 선택해 이력서·자기소개서·경력기술서·포트폴리오·업무보고서로 재구성하도록 돕는다.

기존 Timebar Diary의 핵심인 **계획(Plan)과 실제 기록(Actual)을 같은 시간축에서 비교하는 시간관리 기능**은 제거하지 않는다. 일정·할 일·루틴·집중 시간·실제 작업 기록은 사용자의 실행 습관과 프로젝트 진행 과정을 파악하는 기반 데이터로 유지한다. 즉, 기존 시간관리 기능은 커리어 관리와 분리된 낡은 기능이 아니라, 커리어 경험이 실제로 수행되었는지를 기록하는 핵심 기반으로 재정의한다.

### 1.2 서비스 한 줄 정의

**내가 해 온 일을 기록하고, 증거로 보관하고, 경력과 포트폴리오로 발전시키는 개인 커리어 운영 플랫폼**

### 1.3 핵심 가치

1. **기록한다**: 업무·학습·프로젝트·커뮤니티·취업 활동을 시간순으로 축적한다.
2. **증명한다**: 문서·이미지·링크·GitHub 활동·프로젝트 산출물 등 근거를 기록에 연결한다.
3. **관리한다**: 일정·루틴·WBS·목표·지원 현황·프로젝트를 관리한다.
4. **연결한다**: 기존 기록, 커뮤니티, 팀 프로젝트, GitHub 및 승인된 클라우드 서비스를 연결한다.
5. **활용한다**: 누적된 경험을 선택해 이력서·자기소개서·경력기술서·포트폴리오·업무보고서로 변환한다.
6. **성장한다**: 보유 역량과 목표 직무의 차이를 확인하고 다음 학습·프로젝트 목표를 수립한다.

### 1.4 제품 차별화

일반 취업 서비스는 채용공고와 입사지원에, 문서 도구는 기록·정리에, 개발자 플랫폼은 코드와 협업 이력에, 프로젝트 도구는 일정·작업 관리에 각각 강점이 있다. Timebar Diary는 이 데이터를 **개인의 누적 경험 원장(Career Activity Ledger)**으로 연결한다.

차별화의 중심은 AI 문서 생성 자체가 아니다. 핵심은 다음 연결 흐름이다.

`실제 활동 → 원본 기록 → 증거 자료 → 개인의 역할·기여도 → 역량·성과 → 제출 문서·포트폴리오`

AI는 이 흐름을 돕는 보조 수단이며, 사용자의 실제 경험을 대신 만들어 내거나 증거가 없는 성과를 사실처럼 생성해서는 안 된다.

## 2. 주요 타깃과 사용자 시나리오

### 2.1 핵심 타깃

| 구분 | 사용자 | 주요 목표 | 우선 기능 |
|---|---|---|---|
| 1차 타깃 A | 취업준비생(신입·졸업예정자 포함) | 활동·교육·팀 프로젝트를 정리하고 취업 준비를 체계화 | 경력·활동 기록, 프로젝트, 포트폴리오, 이력서·자소서, 지원 관리, 루틴 |
| 1차 타깃 B | 이직 준비 직장인 | 회사 업무와 성과를 누적하고 다음 이직에 활용 | 업무·성과 기록, 경력기술서, 포트폴리오, JD 분석, 지원·면접 관리 |
| 2차 타깃 A | 직무 전환 준비자 | 기존 경험을 새 직무의 역량으로 재해석 | 역량 태그, 스킬 갭 분석, 직무별 포트폴리오, 학습 계획 |
| 2차 타깃 B | 프리랜서·아르바이트·인턴 경험자 | 프로젝트와 근무 경험을 누락 없이 보관 | 근무 이력, 수행 업무, 고객·프로젝트별 산출물, 성과 기록 |
| 확장 타깃 | 커뮤니티 기반 팀 프로젝트 참여자 | 동료를 찾고 협업 결과를 개인별 경력으로 정리 | 직무 커뮤니티, 팀원 모집, 협업 WBS, 기여도 및 공동 포트폴리오 |

### 2.2 주요 사용자 시나리오

#### 시나리오 A. 취업준비생

1. 관심 직무와 목표 기업 유형을 설정한다.
2. 교육·자격증·동아리·공모전·개인 프로젝트·커뮤니티 활동을 기록한다.
3. 커뮤니티에서 팀 프로젝트를 찾고 지원해 팀에 참여한다.
4. WBS에서 담당 작업과 마감일을 관리하고 결과물·GitHub·문서를 연결한다.
5. 프로젝트가 끝나면 본인의 역할과 기여 내용을 확인하고 포트폴리오 후보로 등록한다.
6. 지원하려는 채용공고를 저장하고 이력서·자기소개서를 해당 공고용 버전으로 만든다.
7. 지원·면접·합격 결과와 제출 문서를 함께 보관한다.

#### 시나리오 B. 이직 준비 직장인

1. 회사·부서·직무·재직 기간과 담당 업무를 경력으로 등록한다.
2. 일간 업무 기록 또는 주간 업무보고로 수행 업무와 문제 해결 내용을 누적한다.
3. 업무 기록에서 기술·역할·성과·증거 자료를 추출해 경력 항목으로 연결한다.
4. 회사 기밀 또는 공개 불가 자료는 비공개로 유지하고, 공개 가능한 결과만 포트폴리오에 선택한다.
5. 목표 채용공고의 요구 역량과 본인 경력을 비교한다.
6. 부족한 경험·기술을 학습 루틴과 개인 프로젝트 WBS로 계획한다.
7. 기업별 제출 문서 버전을 보관하고 이직 진행 상황을 관리한다.

#### 시나리오 C. 커뮤니티 공동 프로젝트

1. 사용자가 직무·기술·기간·목표가 포함된 프로젝트 모집 글을 게시한다.
2. 참여 신청과 역할 협의를 거쳐 팀을 만든다.
3. 팀 전용 프로젝트 공간에서 WBS·채팅·문서·파일·일정을 관리한다.
4. 작업별 담당자, 완료 상태, 리뷰·테스트·기획·문서화 기여를 기록한다.
5. 프로젝트 종료 시 팀 결과물과 개인별 기여 기록을 분리한다.
6. 참여자가 동의한 항목만 각자의 커리어 기록과 포트폴리오에 연결한다.

## 3. 기존 서비스의 핵심 기능과 보존 원칙

### 3.1 기존 기능은 유지한다

아래 기능은 새 서비스 방향과 별개로 삭제하지 않는다. 기능의 목적·메뉴 위치·표현은 개선할 수 있지만, 기존 사용자 데이터와 API 계약 및 사용자 흐름을 검토하지 않고 제거해서는 안 된다.

|---|---|---|---|
| 계정 | 이메일 가입·로그인, JWT 갱신·로그아웃, 계정·ADMIN 권한 | 모든 커리어 데이터의 소유권·접근 제어 | REQ-F01·F02·F15 유지 |

| 플래너 | 일간·주간·월간·연간 계획, 템플릿, 프로젝트 캔버스 | 취업 준비·학습·업무·프로젝트의 시간 계획 | 기존 MN-10~14 유지. 서버/시연 상태 구분 |

### 3.2 Plan / Actual 시간관리의 재정의

Plan / Actual은 커리어 관리의 하위 데이터이자 차별화 기능으로 유지한다.

- Plan: 일정·할 일·WBS·학습 목표 등 사전에 계획한 작업
- Actual: 실제 수행 시간과 완료 이력
- Record Link: 일정·할 일·프로젝트 작업과 실제 기록의 연결
- Career Link: 실제 수행 기록을 경력 활동·프로젝트·포트폴리오 항목에 연결

기존 기록을 커리어 활동으로 자동 승격하지 않는다. 사용자가 연결하거나 자동 추천을 확인·승인한 경우에만 경력 자산으로 등록한다.

### 3.3 하루 모드(J형·P형·밸런스형) 처리

기존 문서에는 J형·P형·밸런스형 하루 모드가 정의되어 있으나, 사용자가 앞서 언급한 `P/B 기능`과 정확히 같은 대상을 뜻하는지는 현재 제공된 문서만으로 확정할 수 없다.

따라서 본 개편안에서는 다음을 제안한다.

- J/P/밸런스 모드는 기존 사용자 경험과 설정 데이터 호환을 위해 즉시 삭제하지 않는다.
- 핵심 서비스 소개와 신규 사용자 온보딩의 중심에서는 내리고, 필요할 때 선택하는 `작업 스타일/화면 구성 설정`으로 유지한다.
- 실제로 별도의 P/B 메뉴나 기능이 존재한다면 해당 기능의 메뉴 ID·라우트·데이터·사용 여부를 확인한 뒤 폐기 또는 대체한다.
- 기존 하루 모드를 삭제하기로 최종 결정하면 저장 데이터 이전, 기본값 결정, 화면·테스트·문서 변경을 별도 요구로 등록한다.

## 4. 신규 핵심 기능

### 4.1 커리어 활동 원장(Career Activity Ledger)

서비스의 중심 데이터다. 회사 경력뿐 아니라 아르바이트·인턴·프리랜서·개인 프로젝트·교육·자격·공모전·커뮤니티 활동·기술 기여를 시간순으로 통합한다.

**기본 필드 제안**

| 항목 | 설명 |
|---|---|
| 활동 유형 | 직장 경력, 아르바이트, 인턴, 프리랜서, 개인 프로젝트, 팀 프로젝트, 커뮤니티, 교육, 자격, 수상, 기타 |
| 소속·주체 | 회사·기관·커뮤니티·프로젝트·개인 |
| 기간 | 시작일·종료일·현재 진행 여부 |
| 역할·직무 | 직무, 직책, 담당 역할, 책임 범위 |
| 수행 내용 | 문제·목표·업무·구현·운영 내용 |
| 기술·역량 | 기술 스택, 도구, 업무 역량, 협업 역량 |
| 성과 | 정량·정성 결과, 개선 전후, 사용자·비용·시간 등 지표 |
| 증거 | 파일, 이미지, 문서, GitHub URL, 외부 시스템 URL, 결과물 |
| 공개 범위 | 비공개, 선택 공유, 공개 포트폴리오 |
| 원본 출처 | 기존 WBS·업무 기록·게시글·프로젝트·외부 연동 자료 등 |

기존 데이터를 새 테이블로 무조건 복제하지 않는다. 우선 원본 기록을 유지하고, 커리어 원장에서 원본 종류·ID를 참조하는 연결 구조를 설계한다. 원본이 수정·삭제되거나 권한이 바뀌는 경우 커리어 화면의 참조 상태도 일관되게 처리한다.

### 4.2 회사·아르바이트·인턴 경력 관리

- 회사·기관·근무처와 재직/근무 기간 관리
- 부서·직급·직무·고용 형태·근무 형태 관리
- 담당 업무와 주요 프로젝트 연결
- 월별·분기별 업무 성과 및 회고
- 이직·퇴사·계약 종료 등 경력 상태 관리
- 경력 공백이나 기간 중복을 확인하는 안내
- 공개하지 않을 회사명·고객명·내부 시스템명 비식별 처리

### 4.3 프로젝트 및 포트폴리오

개인 프로젝트, 회사 프로젝트, 커뮤니티 팀 프로젝트를 모두 지원한다.

**프로젝트 기본 항목**

- 프로젝트명·목표·설명·기간·상태
- 개인/팀/회사 프로젝트 구분
- 팀원·담당 역할·책임 범위
- 기술 스택·도구·아키텍처
- WBS·작업·일정·마일스톤
- GitHub Repository·Commit·Pull Request·Issue 링크
- 문서·이미지·파일·시연 URL
- 문제 상황·해결 과정·성과·회고
- 개인별 기여 내역 및 증거

**포트폴리오 생성**

- 프로젝트와 경력 항목을 선택해 포트폴리오 구성
- 직무·기업·공개 목적별 포트폴리오 버전 생성
- 웹 공개 페이지, PDF, 추후 DOCX 등 출력 형식 제공
- 항목별 공개·비공개 설정, 공개 링크 만료·회수·비밀번호 설정 검토
- 공개 페이지에 원본 회사 기밀·개인정보·비공개 Repository 내용을 노출하지 않음
- 팀 프로젝트는 전체 결과와 개인별 기여를 분리해 표시

### 4.4 취업·이직 지원 관리

| 기능 | 세부 내용 |
|---|---|
| 공고 보관 | 회사·직무·채용 URL·공고 원문/요약·마감일·요구 기술 |
| 지원 파이프라인 | 관심·준비 중·지원 완료·서류 통과·면접·최종 합격·불합격·철회 |
| 문서 스냅샷 | 해당 지원에 제출한 이력서·자기소개서·포트폴리오 버전 고정 |
| 면접 준비 | 면접 일정·질문·답변 초안·후기·후속 연락 |
| 기업 비교 | 직무·근무 형태·연봉 정보·복지·우선순위 등 사용자가 확인한 정보 |
| 알림 | 지원 마감·면접·과제·회신 예정일 |
| 결과 분석 | 지원 결과와 준비 활동을 기간별로 돌아보기 |

외부 채용 플랫폼에 자동 로그인하거나 지원서를 자동 제출하는 기능은 초기 범위에서 제외한다. 우선 공고 URL·사용자 입력·공식 API가 허용하는 데이터로 관리하고, 자동 수집은 서비스 약관·권한을 확인한 뒤 별도 심사한다.

### 4.5 커뮤니티 활동의 커리어 전환

기존 커뮤니티 게시글·댓글·챌린지·채팅은 그대로 유지한다. 다만 사용자가 원할 때 자신이 작성한 글, 답변, 기술 공유, 챌린지 활동 또는 커뮤니티 프로젝트를 커리어 활동 후보로 등록할 수 있게 한다.

- 게시글·답변을 경력 활동 초안으로 가져오기
- 원본 커뮤니티 게시물 링크와 작성 시점 보존
- 작성자 본인의 기여인지 확인
- 공동 작업·팀 활동은 본인 역할을 별도로 입력
- 커뮤니티 활동을 개인 포트폴리오에 노출할 때 원 게시물의 공개 범위와 커뮤니티 규칙 확인
- 원본 게시물 삭제·수정·비공개 전환 시 연결 항목 상태 표시
- 게시글을 경력으로 전환하는 것은 사용자 명시 동의 후 수행

### 4.6 직무별 팀 프로젝트 협업

기존 커뮤니티 기능을 기반으로 팀 프로젝트 기능을 추가한다.

- 프로젝트 모집 글: 목표·기술·역할·기간·모집 인원·진행 방식
- 참여 신청·승인·취소·팀원 초대
- 팀 역할 및 담당 작업 지정
- 프로젝트 전용 WBS·일정·파일·위키·채팅
- 작업 상태·마감·의존 관계·마일스톤
- 코드 리뷰·테스트·기획·디자인·문서화 작업 기록
- 프로젝트 종료·회고·결과물 등록
- 팀 결과물과 개인별 기여 기록 분리
- 공동 포트폴리오 생성 및 개인 포트폴리오로 선택 복사

기여도를 Commit 수나 작업 개수 하나로 계산하지 않는다. 기획·설계·리뷰·테스트·운영·문서화 등 비코드 작업을 기록할 수 있게 하고, 점수화가 필요하면 산정 기준과 팀원 확인 절차를 별도로 정한다.

### 4.7 WBS·루틴·기간 통합 관리

기존 WBS·일정·루틴 기능은 보존하며 업무·취업·학습·개인 프로젝트를 동일한 실행 흐름에서 관리하도록 연결한다.

- 일간·주간·월간·연간 목표 및 일정
- 목표에서 작업·하위 작업·WBS로 분해
- 프로젝트별 간트·칸반·목록 보기
- 작업 담당자·우선순위·마감·의존 관계·진척도
- 루틴·집중 기록·실제 수행 시간 연결
- 계획 대비 실제 소요 시간 비교
- 지연·미완료·과부하 알림
- 기간별 회고 및 다음 기간 목표 생성

현재 주간·월간·연간 플래너 등 시연 상태인 화면은 서버에 연결된 것으로 표현하지 않는다. 기능 확장 시 기존 API·데이터 계약과 통계의 중복 집계 방지 규칙을 먼저 확인한다.

AI 서버가 준비되기 전에는 규칙 기반 템플릿·문서 편집 기능을 우선 제공하고, AI 기능은 실제 제공자 연결 및 서버 상태가 확인된 경우에만 사용 가능으로 표시한다.

### 4.9 GitHub 로그인 및 데이터 연동

GitHub 관련 기능은 다음 두 가지를 반드시 분리한다.

1. **GitHub 로그인(SSO/OAuth)**: GitHub 계정으로 가입·로그인하거나 기존 서비스 계정에 GitHub 계정을 연결한다.
2. **GitHub 데이터 연동**: 사용자가 허용한 범위에서 프로필·Repository·Commit·Pull Request·Issue 등 프로젝트 자료를 가져와 관련 프로젝트에 연결한다.

설계 원칙:

- 로그인 기능과 Repository 접근 권한을 별도 동의·권한으로 관리
- 최소 권한 원칙 적용, 불필요한 쓰기 권한 요청 금지
- 공개 Repository와 비공개 Repository 접근 범위를 명확히 표시
- 비공개 자료는 사용자가 명시적으로 선택하고 동의한 경우에만 가져오기
- GitHub 이벤트를 곧바로 경력 성과로 확정하지 않고 프로젝트·개인 기록과 연결한 뒤 사용자 확인
- 토큰 만료·권한 철회·연결 해제·재인증 지원
- Commit 수만으로 개인 기여도를 확정하지 않음

### 4.10 클라우드 및 네이버 서비스 연동

클라우드 연동은 파일 보관·조회와 서비스 게시를 구분한다.

| 연동 후보 | 목적 | 검토 원칙 |
|---|---|---|
| NAVER MYBOX | 개인 포트폴리오·문서·첨부 파일 보관 | 공식 API의 인증 방식·허용 범위·쿼터·파일 제한 확인 후 어댑터 구현 |
| NAVER Blog | 사용자가 선택한 포트폴리오 콘텐츠 게시 | MYBOX 파일 보관과 별개 기능으로 취급. 공식 게시 API 및 약관 확인 전 자동 게시 약속 금지 |
| Google Drive | 문서·프로젝트 파일 보관 | OAuth 최소 권한·파일 선택·권한 철회 |

공통 기능:

- 연결·재인증·해제·토큰 만료 상태 표시
- 사용자가 가져올 폴더·파일 선택
- 파일 원본 위치와 마지막 동기화 시각 표시
- 중복 파일·동일 파일 버전 처리
- 권한 철회 시 동기화 중단 및 기존 복사본 처리 안내
- 연동 오류와 재시도 내역
- 저장소별 용량·파일 크기·확장자 제한 안내

### 4.11 승인된 사이트·메신저로 업무보고 전송

AI가 만든 업무보고를 외부 메신저나 사이트에 전송하는 기능은 관리자 승인 목록을 통과한 대상만 허용한다.

**권장 실행 절차**

1. 사용자가 업무보고의 기간·프로젝트·업무 기록을 선택한다.
2. AI 서버가 보고서 초안을 생성한다.
3. 사용자가 내용·첨부·수신 대상·공개 범위를 검토한다.
4. 관리자 승인 목록에 등록된 대상인지 확인한다.
5. 공식 API·웹훅 등 허용된 방식으로 전송한다.
6. 성공·실패·재시도·사용자 승인 시각을 기록한다.

**관리자 승인 목록 관리 항목**

- 서비스명·도메인·공식 API 주소
- 허용된 연동 방식(API·Webhook 등)
- 소유자·운영 담당자·등록 사유
- 허용 데이터 종류·전송 필드
- 인증 방식 및 비밀값 보관 위치
- 사용자별 활성화·권한 범위
- 전송 빈도·용량·비용 제한
- 승인·만료·중지·폐기 상태
- 연동 테스트·장애·감사 로그

관리자 승인 목록에 없는 사이트는 전송하지 않는다. 사용자가 쓰는 AI 프로그램이라고 해서 모든 제품의 웹 화면을 자동 조작할 수 있다고 가정하지 않는다. 공식 API가 없는 서비스는 별도 보안·약관 검토 대상으로 두며, 브라우저 자동화는 초기 기본 방식으로 사용하지 않는다.

## 6. 권장 메뉴 구조 개편안

### 6.1 메뉴 개편 원칙

- 기존 메뉴 ID(MN-01~MN-127)와 기존 라우트는 호환을 위해 유지한다.
- 신규 상위 메뉴 그룹은 사용자 목적에 따라 재배치한다.
- 기존 메뉴를 새 그룹으로 옮기더라도 기능 ID와 저장 계약을 바꾸지 않는다.
- 기존 기능을 삭제하지 않고, 메뉴 위치·명칭·설명만 개선할 수 있다.
- 메뉴 ID를 새로 발급할 때는 04 메뉴기능 목록서의 ID 등록 절차를 따른다.
- 아래 신규 MN ID는 충돌 여부를 확인하기 전까지 **후보 ID**다.

| 관찰·비용 | AI·클라우드·외부 API 호출량, 실패율, 지연, 비용 상한과 사용자별 사용량 추적 |

**보안 기본 원칙**

- 외부 서비스 토큰·AI API 키를 브라우저 `localStorage` 또는 일반 설정값에 평문 저장하지 않는다.
- 기존 IM-05의 BYOK 평문 제거 원칙을 유지한다. AI 서버가 별도여도 비밀값은 서버 측 비밀 저장소와 암호화 정책에 따른다.
- AI 서버에는 목적에 필요한 최소 데이터만 전송한다.
- 회사명·고객명·사내 URL·개인정보 등은 사용자가 허용하지 않으면 AI 요청에서 마스킹한다.
- AI 초안 작성과 외부 전송·공개·수정 작업을 분리한다. 외부에 영향을 주는 행동은 명시적 승인을 받는다.
- 관리자 권한으로 개인 커리어 기록을 임의 열람하지 않도록 운영 권한과 감사 정책을 별도로 설계한다.

## 9. 데이터·시스템 아키텍처 제안

### 9.1 논리 구성

```text
[Web / Mobile]
      |
      v
[Main Backend API]
  ├─ Auth / Account / Permission
  ├─ Planner / Schedule / Routine / Actual
  ├─ Career Activity / Experience / Resume / Portfolio
  ├─ Application / Project / WBS / Community
  ├─ File Metadata / Backup / Notification
  └─ Integration Gateway
      |
      +---------------------> [Relational DB]
      |
      +---------------------> [Object/File Storage]
      |
      +---------------------> [Job Queue]
                                  |
                                  v
                            [Separate AI Server]
                              ├─ Career Analysis
                              ├─ Resume / Cover Letter
                              ├─ Career Statement
                              ├─ Portfolio Draft
                              ├─ Work Report
                              ├─ JD / Skill Gap
                              └─ Translation
      |
      +---------------------> [External Provider Adapters]
                                ├─ GitHub
                                ├─ NAVER MYBOX
                                ├─ Google Drive
                                ├─ OneDrive
                                └─ Admin-approved API / Webhook
```

### 9.2 데이터 설계 원칙

- 기존 `feature_record`, `record_link`, `task`, WBS, 커뮤니티, 채팅 등 현재 도메인 저장소를 이유 없이 통합하거나 교체하지 않는다.
- 커리어 활동 원장은 기존 데이터를 참조하는 연결 테이블/도메인 모델을 우선 검토한다.
- 외부 원본은 제공자·외부 ID·동기화 시각·권한 범위를 저장하고, 같은 자료를 중복 생성하지 않도록 외부 키와 멱등 정책을 둔다.
- 지원 건은 제출 문서의 불변 스냅샷을 참조한다. 현재 이력서가 수정되어도 과거 제출본은 바뀌지 않는다.
- 포트폴리오 공개 링크는 공개 항목의 스냅샷 또는 공개 버전을 사용하고, 원본 비공개 데이터가 실수로 노출되지 않게 한다.
- 팀 프로젝트는 팀 소유 자료와 개인 커리어 자료를 분리한다. 개인 포트폴리오에 복사할 때 권한·기여자 동의를 확인한다.

### 9.3 클라이언트와 서버 역할

| 구성 | 책임 |
|---|---|
| 웹 | 상세 편집·WBS·간트·문서 작성·관리자 설정 |
| 모바일 | 빠른 기록·사진/파일 첨부·알림·채팅·프로젝트 현황 |
| 메인 백엔드 | 사용자·권한·데이터 저장·연동 토큰·외부 요청 통제 |
| AI 서버 | 승인된 데이터에 대한 분석·문서 초안·번역·요약 |
| 제공자 어댑터 | GitHub·클라우드·승인된 외부 서비스별 API 차이를 격리 |
| 작업 큐 | 대용량 동기화·AI 생성·보고서 전송의 비동기 처리 |

웹·모바일은 동일한 계정과 서버 API를 사용한다. 초기에는 반응형 웹/PWA를 먼저 안정화할 수 있지만, 푸시·카메라·파일 공유 등 네이티브 기능의 필요성이 확인되면 모바일 앱을 별도 배포한다.

### 10.1 MVP 권장 범위

초기 공개 버전에서 모든 연동과 AI 자동화를 동시에 완성하려 하지 않는다. 다음을 MVP의 중심으로 권장한다.

1. 기존 로그인·시간관리·일정·루틴·WBS·커뮤니티 기능 보존
2. 경력·경험을 통합하는 커리어 타임라인

6. 포트폴리오 항목 선택·비공개 기본값·PDF/공개 링크

GitHub·클라우드 연동, AI 서버, 외부 업무보고 자동 전송, 다국어는 보안·제공자 계약·비용을 확인한 후 단계적으로 추가한다. 단, API 연동을 위한 공통 구조는 MVP 설계 단계에서 고려한다.

## 13. 성공 지표 제안

단순 방문 수보다 사용자가 실제로 커리어 자료를 축적하고 재활용하는지를 측정한다.

| 지표 | 의미 |
|---|---|
| 주간 활성 기록 사용자 | 주간에 경력·업무·프로젝트 기록을 하나 이상 남긴 사용자 |
| 활동→경력 연결률 | 일반 활동 중 커리어 항목으로 연결된 비율 |
| 증거 연결률 | 경력·프로젝트 항목 중 파일·링크·원본 기록이 연결된 비율 |
| 문서 생성 후 수정·확정률 | AI/템플릿 초안을 사용자가 검토하고 확정한 비율 |
| 지원 건별 문서 보관률 | 지원 이력에 제출 문서 스냅샷이 연결된 비율 |
| 포트폴리오 완성률 | 필수 항목과 공개 범위가 설정된 포트폴리오 비율 |
| 프로젝트 완료율 | 팀 프로젝트 중 완료·회고·산출물 등록까지 마친 비율 |
| 연동 성공률 | GitHub·클라우드·외부 서비스의 정상 동기화 비율 |
| 데이터 복구 성공률 | 백업·복원 테스트의 성공 비율 |

성과 지표는 사용자에게 벌점이나 과도한 비교를 주는 점수로 보여주기보다, 본인의 활동과 성장 흐름을 파악하는 용도로 우선 제공한다.

## 부록 A. 제품 기획 결론

Timebar Diary의 기존 기능을 버리고 취업 플랫폼으로 새로 만드는 방향은 권장하지 않는다. 기존에 구현된 시간관리·기록·업무·협업 기능은 이미 축적된 개발 자산이며, 커리어 관리 플랫폼이 실제 사용자의 일상과 업무를 기록할 수 있게 해 주는 기반이다.

따라서 제품의 중심은 다음과 같이 바꾼다.

- **기존 중심**: 계획과 실제 기록을 비교하는 개인 시간관리 서비스
- **개편 중심**: 활동·업무·프로젝트의 결과를 축적하고, 이를 경력·문서·포트폴리오로 전환하는 통합 커리어 관리 플랫폼
- **계속 유지할 차별점**: 계획과 실제 기록, 루틴, WBS, 커뮤니티, 채팅, 공유, 백업, 사용자 통제
- **새로운 핵심 자산**: 커리어 활동 원장, 증거 자료, 지원별 문서 스냅샷, 프로젝트 개인 기여 기록
- **AI의 역할**: 기록 정리·분석·초안 생성·번역을 돕되 사실 확인과 외부 행동 승인은 사용자에게 둔다.

최우선 개발 흐름은 `커리어 활동 원장 → 경험·프로젝트 연결 → 문서·지원 관리 → 포트폴리오 공개`로 한다. GitHub·클라우드·AI 자동화는 이 데이터 구조와 보안 경계가 확정된 다음 단계적으로 연결한다.
