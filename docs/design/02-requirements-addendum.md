## 1. 기존 요구사항 보존

기존 `REQ-F01~REQ-F23`, `REQ-N01~REQ-N10`은 삭제하거나 이 문서에서 재정의하지 않는다. 특히 인증·소유권·일정·할 일·루틴·기록·WBS·경력·커뮤니티·채팅·파일·백업·연동 상태 표시·AI 동의·AI 승인·결제·자동 재분석 요구는 기존 원문과 추적 관계를 유지한다.

기존의 수용 기준 원문은 `../planning/requirements.md`에 둔다. 새 요구사항 ID의 정식 발급도 해당 원문에서만 수행한다. 아래 REQ-F24 이후 번호는 **등록 후보**이며 아직 정식 ID가 아니다.

## 5. 수용 기준 공통 원칙

- 사용자 소유 리소스는 JWT subject를 기준으로 권한을 결정한다. 요청 본문의 `userId`를 신뢰하지 않는다.
- 수정 가능한 자원은 version 또는 동등한 낙관적 잠금 정책을 유지하고, 충돌 시 입력을 보존한다.
- POST/비동기 작업/외부 업로드에는 멱등 키 또는 provider event ID를 적용한다.
- 외부 연결은 연결됨, 권한 부족, 만료, 제공자 장애, 미연결을 구분한다.
- 파일·문서 공개는 비공개 기본값이며, 공개 전 소유권과 기밀 가능성을 안내한다.
- AI 생성 결과는 초안이다. 제출·공개·외부 게시 전 사용자 승인을 요구한다.
- API·화면·테스트·문서가 같은 커밋/PR에서 함께 갱신되어야 한다.

## 6. 요구 변경 절차

1. 신규 요구와 수용 기준을 원본 `../planning/requirements.md`에 정식 ID로 추가한다.
2. 해당 요구를 기존 요구 추적표 및 개발 우선순위 문서에 연결한다.
3. 메뉴가 추가되면 메뉴 문서에 새 MN ID를 정식 발급한다. 삭제된 ID는 재사용하지 않는다.
4. 개발 단위는 기능개발 목록에 FD ID로 등록하고 기존 구현과 중복 여부를 확인한다.
5. 테스트 계획에 검증 시나리오를 추가하고 실행 결과서에 실제 증빙을 남긴다.
6. 문서 버전과 변경 이력을 갱신한다.

## 7. 범위 제외 또는 결정 필요

- 별도 P/B 기능의 정확한 의미는 제공된 원문만으로 식별할 수 없다. J/P/B 하루 모드는 기존 메뉴 문서에 명시된 기능이므로 별도 결정 전 유지한다.
- 유료 구독·결제는 핵심 경력관리 가치가 검증된 이후 별도 사업 요구로 결정한다.
- 채용공고 자동 수집·지원 자동 제출은 약관·법률·사이트 차단 및 사용자 승인 문제 때문에 초기 범위에서 제외한다.
- 기업·기관용 다중 사용자 관리와 코치 대시보드는 개인 데이터 공유 동의 체계가 먼저 확정된 후 검토한다.
