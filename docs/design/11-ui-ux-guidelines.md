# UI/UX 개편 가이드 — 웹·모바일 공통

- 문서 버전: v2.1
- 기준일: 2026-11-20
- 상위 디자인 기준: 저장소 루트 `DESIGN.md`

## 1. 목적

기존 Timebar Diary의 시간관리 흐름과 시각 디자인을 보존하면서, 사용자가 취업·이직·업무·프로젝트·경력 자료를 한눈에 관리할 수 있도록 정보구조와 화면 우선순위를 재설계한다.

## 2. 기존 디자인 시스템 우선

- `DESIGN.md`를 최우선 디자인 기준으로 한다.
- 기존 `design-system/tokens.css`, `components.css`와 공통 컴포넌트를 우선 재사용한다.
- 색상 토큰·타이포그래피·간격·모서리·shadow·focus ring 규칙을 임의로 새로 만들지 않는다.
- 사용자 제공 문서에 기록된 테마(라이트·다크·세피아·고대비 및 색상 분위기)는 기존 구현 상태를 확인한 뒤 유지한다.
- 화면 개편 시 공통 컴포넌트와 상태 문구를 먼저 고치고 각 화면을 점진 전환한다.

## 3. 정보 계층

화면은 다음 3계층으로 정보 우선순위를 구분한다.

1. 현재 사용자의 목표와 가장 중요한 행동: 오늘 할 일, 지원 마감, 프로젝트 작업, 빠른 기록.
2. 진행 상황과 상태: 경력 기록 수, 문서 미완성, WBS 지연, 외부 연결 만료.
3. 상세 데이터와 분석: 기술·성과·이력·파일·통계.

대시보드에 모든 통계를 한꺼번에 노출하지 않는다. 사용자의 온보딩 유형과 위젯 설정으로 노출 범위를 조정한다.

## 4. 핵심 화면 가이드

### 4.1 커리어 대시보드

- 상단: 현재 목표(취업/이직/성장), 다음 마감, 오늘의 주요 행동.
- 중단: 최근 활동 타임라인, 경력 경험 요약, 프로젝트 진행.
- 하단: 문서 완성 상태, 지원 파이프라인, 보유 기술/학습 목표.
- 숫자에는 기간·분모·데이터 출처를 함께 표시한다.
- “경력 점수 93점”처럼 근거가 불명확한 평가를 기본 위젯으로 사용하지 않는다.

### 4.2 활동 타임라인

- 날짜별로 직장 업무·개인 프로젝트·학습·커뮤니티 등 유형을 구분한다.
- 기존 Plan/Actual은 일정·실제 수행 시간으로 남기고 커리어 활동은 설명·성과·근거를 보완한다.
- 한 활동을 경력, 프로젝트, 문서에 연결할 수 있다.
- 동일 원천 활동을 여러 번 복사해 중복 집계하지 않도록 연결 관계를 보여준다.

### 4.3 프로젝트 상세

- 프로젝트 개요, 목표, 기간, 팀 구성, 내 역할, 기술, WBS, 산출물, 기여 내역을 탭/섹션으로 구분한다.
- “팀 전체 성과”와 “내가 담당한 내용”을 시각적으로 분리한다.
- 파일과 GitHub 링크의 실제 접근 상태를 표시한다.
- 프로젝트 완료 시 포트폴리오로 전환하는 행동을 제공하되 자동 공개하지 않는다.

### 4.4 문서 편집기

- 템플릿 선택 → 근거 활동 선택 → 초안 생성 → 근거 확인 → 수정 → 버전 저장 → 내보내기 순서로 구성한다.
- AI가 추가한 문장과 사용자가 직접 작성한 문장을 구분할 수 있어야 한다.
- 근거가 부족한 문장은 “확인 필요”로 표시한다.
- 회사별 지원 문서 버전과 일반 마스터 이력서를 구분한다.

### 4.5 취업·이직 지원

- 칸반 보드와 표/캘린더 보기를 제공한다.
- 지원 마감, 면접 일정, 후속 연락 시점을 쉽게 파악한다.
- 기업별 카드에는 회사·직무·지원 단계·마감·마지막 작업을 우선 표시한다.
- 제출 당시 문서 버전을 다시 열 수 있게 한다.

## 5. 웹과 모바일의 역할

| 기능 | 웹 우선 | 모바일 우선 |
|---|---|---|
| 경력/문서 상세 편집 | 장문 편집, 비교, 버전 | 간단 수정, 검토, 공유 |
| WBS/간트 | 계층 구조·대량 편집 | 내 작업 확인·상태 변경 |
| 프로젝트 | 팀·산출물·기여 분석 | 알림·작업 업데이트·파일 첨부 |
| 빠른 기록 | 상세 입력·일괄 정리 | 1~2문장·사진·음성 입력 |
| 지원 관리 | 공고 비교·문서 버전 | 마감·면접 알림·상태 변경 |
| 포트폴리오 | 레이아웃 편집·미리보기 | 공개 페이지 확인·공유 |

모바일에서도 핵심 기능을 막지 않되 복잡한 대량 편집을 억지로 축소하지 않는다.

## 6. 상태 설계

모든 데이터 화면은 필요한 상태를 제공한다.

- 기본/조회 중
- 빈 상태(무엇이 비었는지 + 다음 행동)
- 저장 중/저장 완료
- 오프라인 전송 대기
- 충돌/확인 필요
- 권한 없음/비공개
- 외부 연결 만료/미연결/제공자 장애
- AI 생성 중/초안 검토/생성 실패
- 공개/비공개/공개 만료

미완료 상태를 벌점처럼 표현하지 않는다. “경력 기록이 부족합니다”보다는 “최근 업무 성과를 추가하면 문서에 활용할 수 있어요”처럼 다음 행동을 설명한다.

## 7. 접근성·반응형 체크

- 최소 폭 320px에서 콘텐츠가 viewport 밖으로 밀리지 않는지 확인한다.
- 390px 모바일, 768px 태블릿, 1024px 소형 데스크톱, 1440px 데스크톱을 검증한다.
- 200% 확대에서 본문과 주요 컨트롤을 사용할 수 있어야 한다.
- 키보드만으로 이동·선택·모달 닫기·저장할 수 있어야 한다.
- 모든 아이콘 버튼에 accessible name을 제공한다.
- 선택/완료/실패를 색상만으로 나타내지 않는다.
- `aria-live`는 실제로 상태 변화가 필요한 영역에만 사용한다.
- reduced-motion 설정을 존중한다.
- 터치 대상 크기는 모바일 접근성 기준을 별도 확인한다.

## 8. 화면 개편 작업 프롬프트 템플릿

```text
Timebar Diary의 [화면/컴포넌트]를 [신규 구현/개선/버그 수정]한다.

먼저 읽을 문서:
- DESIGN.md 전체
- AGENTS.md 및 사용하는 경우 CLAUDE.md
- docs/design/README.md
- 관련 화면, router, store, API client, CSS, 테스트

사용자와 목적:
- 대상 사용자: [취업준비생/이직 준비 직장인/일반 사용자]
- 해결할 문제: [문제]
- 성공 기준: [사용자가 완료할 행동]

화면 요구:
- 필수 정보: [목록]
- 주요 행동: [1개]
- 보조 행동: [목록]
- 상태: 기본/로딩/빈 상태/오류/성공/비활성/선택/오프라인/충돌

기술 제약:
- 기존 프레임워크·라우팅·상태관리·API 계약을 유지한다.
- 기존 공통 컴포넌트와 design token을 우선 재사용한다.
- 서버 저장/로컬 저장/시연 데이터를 명확히 구분한다.
- 새로운 의존성은 필요성과 번들 영향을 설명한 뒤 추가한다.
- 관련 없는 파일을 수정하지 않는다.

반응형·접근성:
- 1440, 1024, 768, 390, 320px 검증
- 200% 확대, 키보드, focus-visible, accessible name, 색상 외 상태 표시
- reduced-motion 확인

완료 보고:
- 변경 파일과 이유
- 실행한 테스트/빌드/계약 검사 명령과 결과
- 실제 브라우저 검증 결과
- 미검증 항목과 남은 위험
```

## 9. 디자인 리뷰 체크리스트

- [ ] 화면의 목적과 주 행동이 명확하다.
- [ ] 기존 기능이 사라지거나 경로가 끊기지 않았다.
- [ ] 실제 데이터와 시연 데이터가 구분된다.
- [ ] 저장 상태·충돌·오류·권한 상태가 표현된다.
- [ ] 기존 디자인 시스템을 재사용한다.
- [ ] 과도한 카드·장식·뱃지·색상을 추가하지 않았다.
- [ ] 개인 정보·회사 기밀이 기본 공개되지 않는다.
- [ ] 데스크톱/태블릿/모바일에서 사용 가능하다.
- [ ] 키보드·화면낭독기·대비·확대 검증을 수행했다.
- [ ] 테스트·문서·화면 경로 목록을 함께 갱신했다.
