## 2. 근거 우선순위 제안

기능 구현 상태를 판단할 때 다음 순서를 권장한다.

1. 현재 작업 브랜치의 실제 소스 코드 및 최신 실행 테스트 증거
2. 최신 기능개발 목록서와 테스트 결과서의 해당 RUN/TS 기록
3. 최신 메뉴기능 목록서의 API 연결/저장 방식 기록
4. 요구사항 명세서의 요약 상태
5. 이전 날짜의 아키텍처·DB 스냅샷
6. 목표 ERD·향후 설계 문서

정적 소스 확인은 실제 운영 배포 성공을 뜻하지 않는다. 테스트 통과도 provider 실제 계정·프로덕션 환경 연동을 뜻하지 않는다.

## 3. 기준일이 다른 아키텍처 문서

2026-09-26 문서에는 다음 상태가 기록되어 있다.

- Vue 3/Vite, Capacitor, Electron 설정
- Spring Boot 모듈형 모놀리스
- MariaDB/JPA/Flyway 설정
- 일부 API stub 및 공용 메모리 PlannerService
- 최근 작성·WBS·커뮤니티 기능의 로컬 시연
- `/api/v1`을 설계 경로로 보고 실제 Controller mapping과 구분

2026-11-20 기능 문서에는 다음이 기록되어 있다.

- 일정·루틴·할 일·다이어리·메모·D-Day·머니로그의 서버 연결 일부/완료
- WBS·업무 위키·업무 기록의 서버 연결
- 경력·이력서·포트폴리오 기본 저장
- 친구·공유 그룹·커뮤니티·챌린지·채팅·첨부 기능 연결
- AI·결제·외부 캘린더·소셜 로그인 등 일부 기능은 미연결/설계

두 문서는 시점이 다르므로 9월 스냅샷의 “로컬 시연” 상태를 11월 현재 기능에 그대로 적용하지 않는다. 반대로 11월 기능 원장도 실제 운영 배포·모든 화면·모든 사용자 시나리오에서 검증됐다고 과장하지 않는다.

## 4. DB 문서 정합성

9월 ERD/DDL 조각의 테이블 표기는 다음과 같이 혼재한다.

- CREATE: `tbl_users`, `tbl_events`, `tbl_task`, `tbl_routine`, `tbl_cal_group`, `tbl_sticker_pack`
- FK/JPA target: `users`, `events`, `task`, `routine`, `cal_group`, `sticker_pack`
- 최근 기능 문서에 나타나는 후속 엔티티: `feature_record`, `record_link`, `idempotency_key`, chat V5, challenge V12 등

따라서 제공된 37개 테이블 목록을 현재 DB 전체라고 말할 수 없다. 최신 Flyway 파일과 실제 DB schema history를 대조해야 한다. 운영 DB를 확인하기 전 CREATE/RENAME/DROP/repair를 실행하지 않는다.

## 5. 요구·메뉴·기능 ID 정합성

- 기존 요구 ID: `REQ-F01~F23`, `REQ-N01~N10` 보존.
- 기존 메뉴 ID: `MN-01~MN-127` 보존.
- 기존 기능 ID: `FD-01~FD-84` 보존.
- 기존 구현방안 ID: `IM-01~IM-14` 보존.
- 신규 ID는 원문 문서에 등록하기 전까지 “후보”로만 표기한다.
- 삭제한 ID를 재사용하지 않는다.
- 새 메뉴는 기존 경로 alias/redirect 여부와 화면 경로 생성기를 함께 갱신한다.

## 6. 상태 용어 통일

| 상태 | 의미 |
|---|---|
| 구현 | 서버 코드 또는 저장 로직이 존재함. 화면 연결/운영 검증을 자동 의미하지 않음 |
| 서버 | 화면이 실제 서버 API를 호출하고 계정별로 저장·조회함 |
| 일부 | 화면 일부 기능만 서버 연결 |
| 로컬 | 브라우저 저장 중심 |
| 서버·로컬 | 로그인/로그아웃 상태에 따라 저장 경로가 다름 |
| 시연 | 고정 또는 임시 예시 데이터, 서버에 저장하지 않음 |
| 상태 표시 | provider capability/연결 상태만 표시 |
| 미연결 | 외부 제공자·실행 경계가 실제 연결되지 않음 |
| 설계 | 문서·계약·구조 제안 단계 |
| 검증 | 해당 환경/시나리오에서 테스트 증거가 있음. 검증 범위를 명시해야 함 |

## 7. 문서 반영 시 주의

- 메뉴 기능 목록을 수정할 때 router 실제 경로와 저장 방식이 일치하는지 확인한다.
- 기능개발 목록서의 `검증 테스트`는 테스트 이름뿐 아니라 최근 실행 결과서의 RUN/TS와 연결한다.
- API 경로 예시는 실제 Controller 매핑과 설계 경로를 구분한다.
- DB ERD에 표시된 FK는 실제 DDL과 Entity에 존재하는지 확인한다.
- AI/외부 connector는 capability 조회와 실제 동작을 구분한다.
- 관리자 콘솔의 시연 화면은 실제 저장/조치가 구현된 것으로 표현하지 않는다.
