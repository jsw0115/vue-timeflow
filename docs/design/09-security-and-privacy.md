# 보안·개인정보·데이터 공개 정책

- 문서 버전: v2.1
- 기준일: 2026-11-20
- 목적: 경력·업무·프로젝트·AI·클라우드 연동 확장에 따른 보안 요구를 통합한다.

## 1. 보호 대상 데이터

| 데이터 | 위험 | 기본 보호 |
|---|---|---|
| 계정·인증정보 | 계정 탈취 | 비밀번호 해시, refresh token 해시/회전, 세션 폐기 |
| 경력·지원 정보 | 인사·연봉·이직 의사 노출 | PRIVATE, 사용자 소유권 검사, 최소 수집 |
| 회사 업무 기록 | 회사 기밀·내부 시스템 정보 | 민감 표시, 기본 비공개, 공개 전 사용자 확인 |
| 프로젝트·소스 링크 | 비공개 코드·고객 정보 노출 | GitHub scope·repo 선택, 외부 권한 재확인 |
| 첨부 파일 | 악성 파일·기밀 유출 | 비공개 object storage, 검사, signed URL |
| 커뮤니티·채팅 | 사칭·괴롭힘·무단 공유 | 멤버십 ACL, 신고·차단·관리자 감사 |
| AI 입력·출력 | 외부 제공자 전송·허위 내용 | 동의·범위 제한·근거 연결·초안 승인 |
| 외부 API 토큰 | 제3자 계정 접근 | 서버 암호화·최소 scope·철회 |
| 관리자 로그 | 과도한 개인정보 수집 | action/target 중심, 본문·토큰 마스킹 |

## 2. 기본 보안 원칙

- 모든 사용자 소유 자원은 JWT subject 기준으로 소유권을 확인한다.
- 다른 사용자의 자원 존재 여부를 노출하지 않도록 민감 리소스 접근 실패는 정책에 따라 404로 응답한다.
- 관리자 권한은 서버에서 매 요청 확인한다. 프런트 역할값/메뉴 숨김은 보안 통제가 아니다.
- 요청 본문의 ownerId/userId를 권한 판단에 사용하지 않는다.
- 수정 가능한 자료는 version 충돌을 처리한다.
- 생성·외부 전송·비동기 작업은 멱등 키와 상태 원장을 갖는다.
- 삭제·공유 철회·계정 전환 후 cache/index/outbox도 일관성 있게 정리한다.

## 3. 커리어 데이터 공개 정책

기본 공개 범위는 `PRIVATE`다.

| 공개 범위 | 설명 | 사용 예 |
|---|---|---|
| PRIVATE | 본인만 접근 | 회사 업무 기록, 연봉, 지원 내역 |
| SELECTED_USERS | 특정 사용자에게 허용 | 멘토·협업자에게 일부 포트폴리오 공유 |
| PROJECT_MEMBERS | 특정 프로젝트 멤버만 | 프로젝트 산출물·팀 작업 |
| UNLISTED_LINK | 주소를 아는 사람만 | 비밀번호/만료 정책을 갖춘 포트폴리오 |
| PUBLIC | 검색·외부 공개 | 사용자가 명시적으로 공개 승인한 포트폴리오 |

- 공개 범위는 기록별·파일별·포트폴리오 항목별로 구분한다.
- 회사명·고객명·서버 주소·계정 ID·내부 화면·소스코드 등 기밀 가능성이 있는 정보는 공개 전 경고한다.
- 팀 프로젝트는 개인 참여자 한 명이 전체 결과물을 무단 공개하지 못하도록 프로젝트 소유권/공개 동의 정책을 적용한다.
- 공유 링크의 만료·폐기·다운로드 권한·조회 로그를 제공한다.

## 4. GitHub·클라우드 자격 증명

- access/refresh token은 브라우저 localStorage/sessionStorage에 평문 저장하지 않는다.
- 서버 측 암호화 보관 시 key version과 rotation 절차를 설계한다.
- provider scope는 필요한 최소 범위로 신청한다.
- 연결 해제 시 토큰 revoke 및 내부 credential 폐기, 동기화 job 중지를 수행한다.
- 외부 provider에서 권한이 철회된 경우 `NEEDS_REAUTH`로 표시하고 이전 데이터를 계속 외부 동기화하지 않는다.
- GitHub 로그인 자격과 Repository 자료 접근 자격은 별도 관리한다.

## 5. 파일 업로드·다운로드

- 확장자만이 아니라 MIME, magic bytes, 크기, 저장소 결과를 검사한다.
- SVG/HTML/실행 파일은 기본 허용 목록에서 제외하거나 안전한 변환 경로를 사용한다.
- 업로드 완료와 검사 완료 상태를 구분한다.
- CLEAN 이전 파일을 공개 포트폴리오·커뮤니티 게시글에서 제공하지 않는다.
- signed URL은 짧은 만료 시간을 가지며 요청 시 사용자 권한을 다시 검사한다.
- 파일명은 저장 경로로 직접 사용하지 않는다.
- 다운로드·공유 첨부의 기존 10 MiB 제한 등은 현재 API/프록시 설정을 확인한 후 일관되게 적용한다.

## 6. AI 개인정보 보호

- AI 전송 전 사용자가 자료 범위·목적·제공자·보존 정책을 확인할 수 있어야 한다.
- 회사 업무 기록, 개인 일기, 연봉·인사 자료는 기본적으로 AI 전송 제외 또는 별도 명시 동의 대상으로 검토한다.
- AI prompt에 필요한 내용만 최소 추출하고 불필요한 이름·이메일·전화번호·사내 주소를 마스킹한다.
- 제공자별 데이터 보관·학습 사용·국외 전송 조건을 확인한 뒤 활성화한다.
- 동의 철회 이후 신규 job을 중단하고 queued job/credential/cache 처리 정책을 적용한다.
- AI 생성 내용은 초안이며 실제 사실과 일치하는지 사용자가 확인해야 한다.

## 7. 관리자 허용 사이트·자동화 안전

- 승인된 connectorId만 실행 가능하다.
- 사용자 입력 URL은 기본 실행 경로가 아니다.
- host allowlist, DNS/IP 검증, redirect 제한, method/path/schema allowlist를 적용한다.
- SSRF 위험이 있는 loopback/private/link-local/cloud metadata 주소를 차단한다.
- 전송 전에 대상, 채널, payload, 첨부, 게시 권한을 사용자에게 보여준다.
- 외부 전송은 사용자의 명시적 승인 후 실행한다.
- 관리자 승인·변경·비활성화는 감사 로그에 남긴다.

## 8. 팀 프로젝트·커뮤니티 권한

- 커뮤니티 회원과 프로젝트 멤버는 서로 다른 membership이다.
- 프로젝트 내 역할(소유자/관리자/멤버/읽기 전용 등)에 따라 WBS·파일·문서 접근을 제한한다.
- 멤버 탈퇴·추방 시 신규 접근을 즉시 차단한다.
- 이미 공개된 공동 결과물의 사용권·개인 포트폴리오 반영은 사전에 합의한 정책을 따른다.
- 기여도는 자동으로 단정하지 않고 참여자 확인·리뷰 기록을 지원한다.

## 9. 로그·감사·보존

- requestId, operationId, actorId(필요 시 pseudonymous), action, target, result, timestamp 중심으로 기록한다.
- token, password, raw prompt, 일기·업무 본문, 민감 파일 내용은 일반 로그에 남기지 않는다.
- 관리자 계정 조치, 공유 권한 변경, 포트폴리오 공개/철회, credential 연결/해제, 자동화 전송을 감사 대상으로 둔다.
- 데이터 보관·삭제 기간은 법률·운영 정책과 사용자 기능 요구를 확인한 후 확정한다. 30일 휴지통 등은 법정 기준이 아니라 제안값일 수 있다.

## 10. 보안 수용 테스트

- 계정 A가 계정 B의 경력·파일·문서·지원 내역을 조회/수정할 수 없는지 확인
- 다른 프로젝트/커뮤니티 멤버가 비공개 활동에 접근할 수 없는지 확인
- 포트폴리오 공유 철회 후 공개 링크가 차단되는지 확인
- OAuth state 재사용·redirect 조작·scope 초과를 거부하는지 확인
- token이 DB·브라우저·로그에 평문 노출되지 않는지 확인
- 파일 MIME 위조·초과 크기·만료 URL·감염 파일을 거부하는지 확인
- AI 동의 범위를 벗어난 자료가 prompt/retrieval에 들어가지 않는지 확인
- 허용되지 않은 host·redirect·private IP 자동화 요청을 차단하는지 확인
- 중복 retry로 외부 게시가 반복되지 않는지 확인
