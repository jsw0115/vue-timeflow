## 1. 서버 4개 구성 검토(11/27 22:56)

**질문:** AI 연동 서버, 취준생·이직러를 돕는 사람(이름도 정해 달라)이 인증 후 가입해 팁을 나누고 스카우트·공고를 올리는 웹·앱 서버, 모든 것을 확인하는 관리·통계 화면을 만들고 싶다. 기존 취준생·이직러 서버를 포함해 서버가 4개 필요해 보이는데, 이 구성이 괜찮은지 검토해 달라.

**답변:** 화면을 나누는 건 좋지만, 백엔드 서버까지 4개로 나누는 건 지금 단계에서 권하지 않았다. 메인 API와 AI 서버 2개로 시작하는 안을 추천했다. 저장소의 05 문서("모듈형 모놀리스 유지, AI는 별도 서버")와 08 문서("데이터 권한과 동의는 Main API가 통제")도 같은 방향이다.

| 제안한 서버 | 추천 | 이유 |
|---|---|---|
| ① 취준생·이직러 서버(지금 앱) | 메인 API로 유지 | 계정·기록·커리어·커뮤니티·채팅이 이미 여기 있다 |
| ② AI 서버 | 별도 서버 | 실행 환경(Python·GPU·외부 AI 키), 비용, 확장 방식이 다르다. 지금 AI 요청은 503으로 막혀 있어 붙일 자리가 있다 |
| ③ 선배(도움자) 서버 | 서버는 메인 API에 합치고 화면만 따로 | 취준생과 선배가 데이터를 계속 주고받는다 |
| ④ 관리자·통계 서버 | API는 메인의 관리자 모듈, 화면은 따로 배포 | 관리자 창(`AdminApp`)과 `/api/admin`이 이미 메인에 있고, 운영 Nginx가 외부의 `/api/admin` 요청을 막는다 |

③을 나누지 않는 이유:
- 한 사람이 두 역할을 함께 가질 수 있다(이직러가 현직자로서 선배 활동).
- 스카우트는 취준생의 포트폴리오·이력 공개 범위를 확인해야 한다. 09 문서에도 "멘토에게 일부 포트폴리오 공유" 범위가 있다.
- 팁 공유와 질문은 지금의 커뮤니티·채팅과 이어진다.
- 서버를 나누면 계정·권한·공개 범위·차단 목록을 두 곳에서 맞춰야 한다. 메인 API에 모듈을 하나 더하고 역할에 선배를 추가하는 편이 단순하다(지금 역할은 `USER`, `ADMIN` 두 가지).

④ 통계는 처음에 관리자 API의 집계 쿼리로 시작하고, 데이터가 커지면 야간 배치 집계 테이블, 그래도 부족하면 읽기 전용 복제 DB 순서로 키운다.

추천 구성:
- 백엔드: 메인 API(Spring Boot, 지금 서버), AI 서버(별도), 나중에 Worker(알림·통계 집계·AI 작업)
- 화면: 사용자 앱(웹·Capacitor·Electron), 선배 화면(처음에는 같은 앱 안 역할별 "선배 메뉴"), 관리자 웹(외부에 열지 않는 주소나 허용 IP)

도움자 이름 후보:

| 이름 | 장점 | 단점 |
|---|---|---|
| **선배**(추천) | 취준생 눈높이에 맞고 따뜻하다. "인증 선배" 배지로 신뢰도를 보여 줄 수 있다 | 영어 화면에서는 "Mentor"로 옮긴다 |
| 현직자 | 무엇을 하는 사람인지 정확하다 | 퇴사자·프리랜서·채용 담당자가 빠진다 |
| 멘토 | 익숙하다 | 교육 플랫폼 느낌이 강하고 흔하다 |
| 길잡이 | 브랜드 느낌이 있다 | 무엇을 하는 사람인지 바로 알기 어렵다 |

팁을 나누는 사람과 공고·스카우트를 올리는 사람(인사담당자·헤드헌터)은 다를 수 있으니, 역할을 나눌지 먼저 정하자고 했다.

만들기 전에 정할 것 5가지:
1. 선배 인증 방법: 회사 이메일 인증(간단하지만 소규모 회사·프리랜서는 어렵다) 또는 재직증명서 업로드와 관리자 심사(정확하지만 보관 기간·파기 기준이 필요하다)
2. 공고·스카우트의 법적 확인: 채용 정보 제공·직업 소개는 직업안정법상 신고·등록 대상이 될 수 있고, 무료·유료에 따라서도 다르다. 판단할 수 있는 영역이 아니어서 출시 전에 전문가 확인이 필요하다
3. 개인정보 동의: 스카우트 받기를 사용자가 직접 켜는 방식(opt-in)과 프로필 공개 범위, AI로 넘기는 자료의 동의
4. 신뢰·안전: 허위 공고·스팸 스카우트·부적절한 조언을 신고·차단·심사하는 기능. 기존 커뮤니티 신고·관리자 심사를 확장해 쓸 수 있다
5. 수익 모델: 공고·스카우트를 유료로 하려면 결제 연동이 필요하다. 지금 결제는 미연결(503)이다

| DEC-21 | AI 서버 기술 | Python(FastAPI)과 외부 AI API. 어느 제공자를 쓸지는 기존 DEC-08에서 정한다 |
| DEC-22 | 관리자 통계 첫 범위 | 운영 지표: 역할별 가입자 수, 선배 인증 대기, 신고 처리 대기, 최근 7일 글·답변 수 |
| DEC-23 | 진행 순서 | S1 역할 → S2 선배 인증 → S3 팁·답변 → S4 통계. S1이 끝나면 S6 AI 서버를 나란히 시작 |

```text
S1 역할 구조 ──▶ S2 선배 인증 ──▶ S3 선배 팁·답변 ──▶ S4 관리자 통계
      │
      └──▶ S6 AI 서버 (S1 뒤에 나란히 시작)

S5 공고·스카우트: 법률 확인 뒤 다시 정한다
```

남은 것으로 세 가지를 짚었다.
- S1부터 시작하는 게 좋다. 지금 계정에는 역할이 하나만 저장되므로(`USER` 또는 `ADMIN`) 여러 역할을 가지려면 DB 구조를 바꿔야 한다. 기존 계정은 그대로 두고 역할을 더하는 방식으로 설계한다.
- AI 제공자 선택(기존 DEC-08)은 아직 정하지 않았다. S6 전에 어느 회사 모델을 쓸지, 데이터 전송·보관 정책을 정해야 한다.
- 공고·스카우트를 다시 시작할 때 법률 확인이 필요하다.

## 3. 필요한 모듈(11/27 23:16)

**질문:** 그럼 총 필요한 모듈은 어떤 것들인가?

**답변:** 백엔드 패키지와 화면 기능 폴더를 확인해서 '지금 있음'은 실제 소스 기준으로, 나머지는 제안으로 나눴다.

메인 API(Spring Boot)에서 그대로 쓰는 모듈:

| 패키지 | 하는 일 |
|---|---|
| `planner`, `task`, `routine`, `event`, `records`, `feature` | 일정·할 일·루틴·기록·메모·D-Day 등. `records`에 첨부 파일도 있다 |
| `career`, `work` | 경력·활동·문서 버전·포트폴리오·업무 |
| `social`, `chat` | 커뮤니티, 채팅 |
| `contract` | 관리자, 공유, 설정, 프로필, 리포트 등 |
| `operations` | 신고 심사, 고객지원, 백업 |
| `common`, `config`, `security` | 공통 응답·오류, 설정, 보안 |

고칠 모듈 3개:

| 모듈 | 바뀌는 점 | 단계 |
|---|---|---|
| `auth` + `security` | 역할을 한 개(`USER`/`ADMIN`)에서 여러 개로 바꾸고(선배·채용 파트너 추가) 권한 검사를 맞춘다 | S1 |
| `contract`(관리자) | 역할 관리, 선배 심사 목록, 운영 지표 API를 더한다 | S1·S2·S4 |
| `integration` | 지금 503을 돌려주는 AI 요청을 AI 작업 모듈로 연결한다 | S6 |

새로 만들 모듈 5개:

| 모듈 | 하는 일 | 단계 | 재사용하는 기존 기능 |
|---|---|---|---|
| mail(메일 발송) | 회사 메일 인증 코드 발송 | S2 이전 | 없음 |
| mentor(선배 인증) | 신청 → 회사 메일 인증 또는 증빙 → 관리자 심사 → 배지. 증빙은 심사 후 파기 | S2 | 첨부(`records`), 감사 로그 |
| advice(선배 활동) | 팁 글, 질문·답변, 신고 | S3 | 커뮤니티 글·댓글(`social`), 신고(`operations`) |
| stats(운영 지표) | 역할별 가입자, 인증 대기, 신고 대기, 최근 7일 글·답변 수 | S4 | 관리자 통계 API |
| aijob(AI 작업) | 동의·범위 확인, 작업 생성·상태·취소, 결과 권한, 작업 큐에 넣기 | S6 | 문서 버전(`career`) |

> 메일 발송은 S2 전에 꼭 필요하다. 지금은 메일 서비스가 연결되어 있지 않고, 비밀번호 재설정 화면도 같은 이유로 "메일 발송 준비 중"으로 막혀 있다. 메일 발송 업체를 정해 연결하는 일이 S2의 선행 작업이고, 연결하면 비밀번호 재설정도 함께 풀 수 있다.

AI 서버(Python FastAPI, 새로 만듦, S6)의 모듈 7개:

| 모듈 | 하는 일 |
|---|---|
| api | 메인 API의 내부 요청만 받고, 작업 접수와 상태를 알려 준다 |
| worker | 큐에서 작업을 꺼내 처리한다 |
| documents | 이력서·경력기술서·자기소개서 초안 규칙과 프롬프트 |
| citation | 초안 문장마다 근거 기록을 연결하고, 근거 없는 주장을 표시한다(08 문서) |
| provider | 외부 AI API 연결. 제공자는 아직 정하지 않았다(DEC-08) |
| usage | 작업별 사용량·비용 기록과 상한 |
| guard | 입력 검증, 프롬프트 공격 방어, 내부 인증 |

작업 큐는 메인 API와 AI 서버를 잇는다. Redis는 이미 있지만, 무엇으로 큐를 만들지는 S6에서 정한다.

화면(Vue):

| 위치 | 새 모듈 | 단계 |
|---|---|---|
| 사용자 앱 | 역할에 따라 메뉴 보이기 | S1 |
| 사용자 앱 | `mentor`: 선배 신청, 인증 상태, 팁·답변 쓰기 | S2·S3 |
| 사용자 앱 | `advice`: 취준생이 선배 팁을 보고 질문하기 | S3 |

## 4. 서버 개수(11/27 23:21)

**질문:** 그러니까 서버가 총 몇 개 있어야 하나?

**답변:** 직접 만들어야 하는 서버는 **2개**다. 선배 서버와 관리자 서버는 따로 만들지 않고 메인 API 안에 모듈로 들어간다.

| # | 서버 | 지금 | 하는 일 |
|---|---|---|---|
| 1 | 메인 API 서버(Spring Boot) | 있음 | 취준생·이직러, 선배, 관리자 기능을 모두 처리 |
| 2 | AI 서버(Python FastAPI) | 새로 만듦 | AI 문서 초안 생성 |

운영에서 함께 띄우는 것까지 세면 이렇다. 지금 배포 설정(`infra/deploy/compose.yml`)에는 `db`, `redis`, `api`, `web` 4개가 있고, HTTPS를 쓰면 `edge`(Caddy, `infra/deploy/compose.https.yml`)가 붙는다.

| 구성 | 개수 | 내용 |
|---|---|---|
| 직접 만드는 서버 | 2 | 메인 API, AI 서버 |
| 화면 파일 제공 | 1 | `web`(Nginx): 사용자 앱·관리자 웹 화면을 내려주고 `/api` 요청을 메인 API로 넘긴다 |
| 데이터 저장 | 2 | MySQL, Redis |
| HTTPS 입구(선택) | 1 | Caddy |
| **합계** | **5~6개** | 지금 4~5개에 AI 서버 1개가 더해진다 |

나중에 늘 수 있는 것:
- Worker: 알림·통계 집계·AI 작업이 많아지면 메인 API에서 뗀다. 그때 서버는 3개(메인 API, AI, Worker)가 된다.
- 선배 전용 웹: 화면을 따로 떼어도 늘어나는 건 화면 파일뿐이고, 서버는 그대로 메인 API를 쓴다.

메일 발송이나 외부 AI처럼 밖에서 빌려 쓰는 서비스는 직접 띄우지 않으므로 개수에 넣지 않았다.

## 5. git 저장소 개수(11/28 01:43)

**질문:** git 저장소를 추가하려는데 총 몇 개 만들어야 하나?

**답변:** 새 저장소는 **0개, 많아야 1개**다. 지금 `vue-timeflow` 저장소 하나에 `frontend/`, `backend/`, `infra/`, `docs/`가 모두 있고, 선배 기능과 관리자 통계는 메인 API와 지금 화면 안에 들어간다. 새로 생기는 건 AI 서버뿐이다.

| 안 | 새 저장소 | 구성 | 맞는 경우 |
|---|---|---|---|
| **A. 지금 저장소에 폴더 추가(추천)** | 0개 | `vue-timeflow/ai-server/` | 한 팀(또는 혼자)이 전부 만들 때 |
| B. AI 서버만 따로 | 1개 | `vue-timeflow` + 별도 AI 저장소 | AI를 다른 팀·외주가 맡거나, AI 코드와 외부 AI 키 접근 권한을 따로 관리해야 할 때 |

A를 추천한 이유:
- 메인 API와 AI 서버가 주고받는 작업 요청·결과 형식을 같은 커밋에서 함께 고치고 시험할 수 있다. 저장소를 나누면 버전을 맞추는 일이 따로 생긴다.
- 설계 문서(`docs/design`)와 배포 설정(`infra/deploy`)이 이미 이 저장소에 있다.
- 지금도 언어가 다른 두 프로젝트(Vue·Spring)를 한 저장소에서 관리한다. CI에는 AI 서버 빌드·시험 단계만 더하면 된다.

B로 가야 하는 경우: AI 서버를 다른 사람·외주가 만들어 메인 서비스 코드 접근을 주고 싶지 않을 때, 또는 AI 서버의 배포 주기나 권한을 완전히 따로 관리해야 할 때. 이 세션에서는 저장소를 새로 만들 수 없어서, B로 정하면 GitHub에서 직접 만들어야 한다고 안내했다.

## 6. A안 확정(11/28 01:46)

**질문:** 그럼 A로 작업 진행할게.

**답변:** A안을 DEC-24로 확정해 15 문서 3-1절과 12 결정 기록에 남겼다(커밋 220e638). 새 저장소는 만들지 않고, 폴더나 코드도 아직 만들지 않았다. 외부 AI 키는 저장소에 넣지 않고 배포 환경의 비밀값으로 관리한다고 함께 적었다.

```text
vue-timeflow/
├── frontend/    사용자 앱(선배 메뉴 포함)·관리자 웹 (Vue)
├── backend/     메인 API (Spring Boot)

├── infra/       배포 설정 (AI 서버 추가 예정)
└── docs/        설계·개발 문서
```

다음 순서는 DEC-23에 따라 **S1 역할 구조**다. 계정 하나가 사용자·선배·채용 파트너·관리자 역할을 여러 개 가질 수 있게 DB와 권한 검사를 바꾸고, 기존 계정은 그대로 둔 채 역할만 더한다. `ai-server/` 폴더는 S1이 끝나고 S6을 시작할 때 만든다.
